Review the plan from the previous session — or the next step of a numbered proposal — and, if it is clean, implement it for the Maestro project.

This command takes a unit of work, validates that every claim in it still holds against today's tree, and — only when the review comes back clean — implements it step by step and runs the quality gates. It stops before commit/push; review the result with `/review-changes` (which hands off to `/polish`), then ship with `/commit-push` or `/create-pr`. The unit of work is either a **plan file** (`~/.claude/plans/*.md`, written by a prior session) or, when `$ARGUMENTS` is a proposal number, the **next unimplemented step** of a proposal at `docs/proposals/**/NNN-*.md`.

`$ARGUMENTS` is optional:
- *(empty)* — auto: implement the most recently modified plan file
- `<proposal-number>` — a positive integer, optionally zero-padded (e.g. `58`, `058`), naming a proposal at `docs/proposals/**/NNN-*.md`. Implement that proposal's **next unimplemented step** (see *Proposal mode*). A bare positive integer is **always** treated as a proposal number, never as a plan slug.
- `<slug>` — resolve to `~/.claude/plans/<slug>.md` (with or without the `.md` extension)
- `<absolute-path>` — use that file as the plan

## Locate the work

1. **Detect the mode.** Strip surrounding whitespace from `$ARGUMENTS`. If the result is a bare positive integer (digits only, optionally zero-padded — e.g. `58`, `058`), this is **Proposal mode**: skip the rest of this section and go to *Proposal mode* below, which resolves the proposal and selects the next step, then routes back into *Review the plan against today's tree* with that step as the unit of work. For every other argument shape (empty, `<slug>`, `<absolute-path>`) this is **plan-file mode** — continue with the steps below.
2. **Resolve the plan file.**
   - If `$ARGUMENTS` is non-empty:
     - If it looks like an absolute path (starts with `/`), use it directly.
     - Otherwise treat it as a slug and resolve to `~/.claude/plans/<slug>.md` (append `.md` if absent).
     - If the resolved file does not exist, stop with `error=plan_not_found` and list the five most recent files in `~/.claude/plans/` so the user can re-invoke.
   - If `$ARGUMENTS` is empty, resolve the plan in two tiers — the per-folder pointer first, the global most-recent plan as fallback:
     - **Folder pointer.** Read `~/.claude/last-plan-by-folder.json` (per *Plan pointer file* below) and look up the entry for the current working directory's absolute path. If an entry exists and its `plan` file still exists and is non-empty, use it, and announce `Plan pointer: <plan path> (written <written_at>)` so the user sees the pick was anchored to this folder.
     - **Fallback.** Otherwise — no pointer file, no entry for this folder, or the recorded plan was deleted or is size-zero — pick the most recently modified non-empty `*.md` file in `~/.claude/plans/`, and warn `No folder plan pointer — falling back to the most-recent plan globally` so the user knows the pick was not folder-anchored.
     - If the fallback also finds nothing (the directory is empty or every file is size-zero), stop with `error=no_plan_found`.
3. **Read the plan in full.** Plans vary in layout — proposal plans use `# Plan: <Title>` / `## Context` / `## Implementation steps` / `## Critical files`; ad-hoc plans may use other shapes. Extract the substance: what is the plan trying to do, which files does it touch, which symbols does it cite, which utilities does it reuse, what verification does it specify.
4. **Sanity-check that the plan belongs to this project.** If most cited paths do not exist in the current tree (suggesting the plan was written for a different repo), stop with `error=plan_project_mismatch` and tell the user — do not auto-pick a different plan.

## Plan pointer file

`~/.claude/last-plan-by-folder.json` is a shared JSON file that the plan-writing commands (`/plan`, `/plan-proposal`, `/bug-fix`, `/backlog`) update after they write a plan, recording the most-recent plan per working directory:

    {
      "<absolute path of a working directory>": {
        "plan": "<absolute path of the plan file last written from that directory>",
        "written_at": "2026-05-24T12:34:56Z"
      }
    }

`/impl` reads this file **read-only** to resolve the empty-argument auto-pick to the plan last written from *this* working directory, so sibling checkouts that share `~/.claude/plans/` do not pick each other's plans. A missing file, malformed JSON, a missing entry for this directory, or a recorded plan that no longer exists all fall back to the global most-recent plan; `/impl` never writes this file. An explicit `<slug>` or `<absolute-path>` argument bypasses the pointer entirely. Proposal mode does not touch the pointer file at all.

## Proposal mode

Run this section only when *Detect the mode* classified `$ARGUMENTS` as a proposal number. It resolves the proposal, picks the single next unimplemented step, and produces a self-contained **unit of work** (a step title, the files it touches, its description, its dependencies, and its acceptance criteria). That unit then flows into *Review the plan against today's tree* exactly as a plan file would: read "the plan" as "the selected step" throughout the rest of this command. This command **never hand-edits** the proposal document — checkbox and status reconciliation is `/update-proposals`' job. When a check below finds the document drifted from today's tree, this command delegates that reconciliation to `/update-proposals NNN` (see *Auto-reconcile the proposal document*) rather than editing the doc itself.

1. **Resolve the proposal.** Mirror `/plan-proposal`'s resolution: zero-pad the number to 3 digits (`58` → `058`), then glob `docs/proposals/**/<NNN>-*.md` (recursive — proposals live in `core/`, `security/`, `publication/`, `audience/`, `income/`, `research/`, `ux/`, `technical-plan/`, `operations/`).
   - Zero matches → stop with `error=proposal_not_found`; suggest the user check `docs/proposals/README.md` for available numbers.
   - Multiple matches → stop with `error=ambiguous_proposal_match` and list the matches.
   - Read the matched file in full, including its metadata table (`Status`, `Affects`, `Depends on`) and any `What landed` / `What is missing` rows or sections.
2. **Locate the step list.** Proposals lay out their work as an ordered checkbox list — `N. [x] **<Title>.** …` for shipped steps and `N. [ ] **<Title>.** …` for pending ones — usually grouped under `### Phase` headings, each step carrying `*Depends on:*` and `*Acceptance:*` sub-bullets (and sometimes a `*Status:*` note). If the proposal has **no** checkbox step list (e.g. a docs-only / service-offering proposal, or a narrative-only body), stop with `error=no_step_list` and tell the user this proposal is not step-structured — `/plan-proposal NNN` then `/impl` is the path for it.
3. **Select the next step.** Walk the step list in document order and pick the **first** step still marked `[ ]`. This is the unit of work. Then validate the pick:
   - **Burn-in proposals are human-gated.** A *deferred graduation step* is a graduation / cut-over / collapse / decommission step held behind a burn-in observation window — its prose reads "after … proven in production", "await the graduation PR", "observation gate before …", or it only flips a default to its shipped posture or deletes the retired logic a landed path superseded. Stop with `error=proposal_in_burn_in` when the metadata `Status` token *starts with* `burn-in` — the typed substates are `burn-in:ready` / `burn-in:observing` / `burn-in:graduated`, and matching on that prefix rather than on an exact bare `burn-in` is what keeps the refusal firing now that no doc carries the bare token — **or** when every remaining `[ ]` step is a deferred graduation step. Explain that the proposal's behaviour-code has fully landed; its remaining steps are deliberately held for a separate human-reviewed graduation PR gated on the burn-in evidence, so `/impl` does not implement them — the human decides when the window licenses the flag flip / logic deletion. (Do **not** run *Auto-reconcile* for this stop: the checkboxes are not stale, they are intentionally deferred.) But do **not** refuse the whole proposal on the *first* `[ ]` step alone: when the proposal is still `partial` and the selected first-`[ ]` step is a deferred graduation step while a **later** `[ ]` step still writes behaviour-code, that deferred step is not yet implementable — skip it and select the next `[ ]` step that is not a deferred graduation step (e.g. 117 orders a deferred flag-collapse ahead of unbuilt code, so `/impl 117` skips the deferred step and reaches the code), then re-run the validations below against the newly selected step.
   - **Dependencies satisfied.** Read the step's `*Depends on:*` list. Every cited prerequisite step must be marked `[x]`. If any dependency is still `[ ]`, the first-`[ ]` step is not actually next — stop with `error=step_dependency_unmet`, name the blocking step, and tell the user (the proposal's step order or checkbox state is inconsistent; resolve it before implementing).
   - **Corroborate against the metadata.** Cross-check the selected step against the `What landed` / `What is missing` rows. If the checkboxes and the prose disagree about whether this step has shipped (a stale `[ ]` on work the prose says landed, or vice-versa), do not guess — run *Auto-reconcile the proposal document* to let `/update-proposals NNN` re-derive the checkboxes and status from the code, then re-select. If the contradiction survives reconciliation, stop and surface it so the user can reconcile the doc by hand.
   - **No pending step.** If every step is `[x]`, there is nothing to implement. Read the proposal's README status row: if it already says `shipped`, stop with `error=proposal_complete`. If it has not yet been flipped to shipped, run *Auto-reconcile the proposal document* (which flips the README via `/update-proposals NNN`) and let its *Re-select* step decide the terminal outcome — do **not** pre-commit to `proposal_complete` here. `/update-proposals` re-derives the checkboxes from code and may flip a previously-shipped step `[x]`→`[ ]` (its work was reverted out of the tree); that is genuine pending work to implement, which *Re-select* surfaces and continues into. *Re-select* reports `proposal_complete` (with reconciliation noted) only when every step is still `[x]` after reconciliation.
4. **Extract the unit of work.** From the selected step capture: its number `M` and title, the file paths and line ranges it names, its 1–3 sentence description, its `*Depends on:*` steps, and its `*Acceptance:*` criteria (these become the binding success criteria for the review and the implementation — treat them the way a plan's `Verification` section is treated). Record `NNN`, the proposal slug (filename part after `NNN-`, without `.md`), and the step number `M` for branch naming and the final report.
5. **Continue to the review.** Hand the extracted step to *Review the plan against today's tree*. *Create the implementation branch* (below) names the branch from the proposal and step, not from a plan filename.

## Auto-reconcile the proposal document (proposal mode)

Several checks below detect that the proposal document's checkboxes or status row no longer match today's tree — a stale `[ ]` on work that has already shipped, every step `[x]` while the README still lists the proposal as open, or a checkbox/prose disagreement. These are exactly the drifts `/update-proposals` exists to fix. Rather than stopping and asking the user to run it by hand, this command reconciles the document itself by invoking `/update-proposals NNN`, then resumes. This is the **only** way `/impl` ever causes a write to `docs/proposals/`: it never hand-edits the document — it delegates to `/update-proposals`, whose own safety rules (code stays read-only, drift flows one way from code into the proposal) still apply. The delegated run touches `docs/proposals/**` only and never clobbers the user's uncommitted code, so it is safe to invoke regardless of other working-tree state.

Run this routine only in proposal mode, and **at most once per `/impl` invocation** (guard against loops): if a trigger fires again after reconciliation has already run this invocation, do not re-run `/update-proposals` — fall back to the original stop for that trigger and surface that reconciliation was already attempted but did not resolve the drift, so the human can judge it.

1. **Ensure a shippable branch first (before any write).** This is the **sole exception** to the rule that no branch is created before *Decide* returns Go. `/update-proposals` leaves uncommitted edits in `docs/proposals/**` (including `docs/proposals/README.md`), and those edits must never be left on `main` — a terminal `proposal_complete` outcome below stops *before* *Create the implementation branch* ever runs, and `/commit-push` refuses to push from `main`, so edits orphaned on `main` have no clean path to ship. So before invoking `/update-proposals`, first apply the **Dirty-tree gate (*Review*'s 1a)**: two of this routine's triggers (*Corroborate against the metadata* and *No pending step*, in Proposal-mode step 3) fire *before* the flow reaches *Review*, so 1a would otherwise be skipped entirely on those paths and the branch created over whatever is in the working tree — surface and confirm any clearly-unrelated uncommitted changes (excluding the not-yet-made `docs/proposals/**` reconcile edits, which are plan-related by definition) and do not create any branch while an unrelated dirty tree remains, preserving 1a's 'never auto-branch over an unrelated dirty tree' invariant. With the tree clean or its changes confirmed plan-related, run `git rev-parse --abbrev-ref HEAD`: if HEAD is `main`, first fast-forward local `main` to `origin/main` per *Refresh `main` before branching*, then auto-create a feature branch now (the same `git checkout -b` as *Create the implementation branch* step 3, sanitized and given the same unique suffix per *Unique branch suffix*) — name it `feat/<NNN>-step<M>-<step-slug>-<uid>` when a step is already selected, otherwise `feat/<NNN>-reconcile-<uid>` (the all-steps-done / pre-selection case, where no step number exists yet). If HEAD is already on a non-`main` branch, leave it. Record the branch for the report. This guarantees the reconciliation edits have a shippable home whether the flow then continues into an implementation PR or terminates at `proposal_complete`.
2. **Invoke `/update-proposals NNN`** for the single proposal NNN being implemented. It re-derives the proposal's checkboxes, `What landed` / `What is missing` rows, and `Status` from the code, and reconciles `docs/proposals/README.md` — editing `docs/proposals/**` only, never code, tests, or config.
3. **Treat its edits as plan-related.** The reconciliation touches `docs/proposals/**` and nothing else; the Dirty-tree gate (*Review*'s 1a) must never classify these `/impl`-initiated edits as "clearly unrelated." Step 1 already ensured a non-`main` feature branch holds them, so the checkbox/status flip is shippable on its own: it rides the implementation PR when a step is implemented, and remains a clean, pushable branch when the run terminates at `proposal_complete` with no implementation. If *Create the implementation branch* later runs it finds HEAD already on this feature branch and leaves it — no second branch is created.
4. **Re-read the proposal in full** — its checkboxes and status may have moved.
5. **Re-select.** Return to *Proposal mode* step 3 (*Select the next step*) and walk the reconciled document from the top:
   - **A pending `[ ]` step now exists and validates** → that step is the unit of work; continue. If a feature branch was auto-created this invocation (in step 1, or by a prior trigger) whose name does not match the newly selected step — a `feat/<NNN>-reconcile-<uid>` branch, or one named for a *different* step number — and it carries no commits yet, rename it to match (`git branch -m feat/<NNN>-step<M'>-<step-slug'>-<uid>`, sanitized per *Create the implementation branch* step 3 and reusing this invocation's unique suffix per *Unique branch suffix*) and record the rename for the report; if the branch was pre-existing or already has commits, leave it and surface the step/branch mismatch as a concern.
   - **Every step is now `[x]`** → there is nothing to implement; report `proposal_complete` with reconciliation noted (the README has been flipped to shipped) and stop. The reconciliation edits sit on the feature branch from step 1, ready to review with `/review-changes` (which hands off to `/polish`) and then ship via `/commit-push` or `/create-pr` — the same pre-ship workflow the *Next step* report recommends, even though this path's diff is docs-only (`docs/proposals/**` checkbox + README edits). This is a clean completion, not an error the user must resolve.
   - **The document is still internally contradictory** (checkbox/prose still disagree after reconciliation) → fall back to the original stop and surface; `/update-proposals` could not resolve it, so the human must reconcile by hand.

## Unique branch suffix

Every feature branch this command auto-creates ends in a short **unique suffix** (`<uid>`) so branch generation never collides with an existing branch and never has to ask the user for a name. Generate it **once per invocation**, at the moment of the first branch create, as a git-safe lowercase token that **must carry random entropy** — a UTC timestamp `date -u +%y%m%d%H%M%S` (12 digits) **followed by** a few random hex characters (`openssl rand -hex 3`). The random component is mandatory, not optional: a bare second-granularity timestamp is not collision-free (two invocations can land in the same wall-clock second), and — because the collision-retry in *Create the implementation branch* regenerates the suffix — a timestamp-only generator would reproduce the *identical* value within that same second and loop without progress. The random hex is what makes every generated **and** regenerated suffix distinct, so the retry always advances. Sanitize it the same way branch slugs are sanitized (lowercase, only `[a-z0-9]`, no separators of its own) and join it to the sanitized base slug with a single `-`. In the shell snippet that generates it, **never assign to a variable named `UID`** — bash treats `UID` as read-only (the real user id), so the assignment fails and `$UID` silently expands to a numeric uid, yielding a branch like `feat/...-1003` with no entropy; use a non-reserved name such as `SUFFIX`. **Reuse the same suffix** for any `git branch -m` rename within the same invocation (Auto-reconcile re-selection) so the branch keeps one stable identity across the run. This suffix is the mechanism that replaces every former "branch already exists / empty slug → stop and ask the user" behaviour: branch naming is fully automatic.

## Refresh `main` before branching

Whenever a run will ultimately **auto-create a feature branch from `main`**, first fast-forward local `main` to `origin/main` so both the review and the branch cut see the latest merged code, not a stale local `main`. This runs **only** on the HEAD==`main` path — when `git rev-parse --abbrev-ref HEAD` is `main` and the working tree is clean (the precondition the branch auto-create already requires). It never runs when HEAD is on a non-`main` branch (that branch is the user's, left untouched — no fetch, no fast-forward) or when the tree is dirty.

It is invoked at whichever of these points comes first — normally just once, though one ordering re-runs it idempotently (see the note below the bullets):
- **Plan-file / normal path:** up front, at the start of the review (*Review the plan against today's tree* step 1c), *before* the drift checks — so the review validates the plan against the same `origin/main` tree the branch will be cut from. Because fetch + fast-forward creates no branch, running it here does **not** undo the branch-creation deferral: *Create the implementation branch* still cuts the branch only after *Decide*, from the local `main` this step already advanced (it does not re-fetch).
- **Proposal mode's *Auto-reconcile the proposal document*, fired before *Review*** (its *Corroborate against the metadata* / *No pending step* triggers, in Proposal-mode step 3): in Auto-reconcile's own step 1, immediately before pre-creating the reconcile branch (that path must branch early to hold its `docs/proposals/**` edits). The review's 1c then sees a non-`main` HEAD and skips, so on this ordering the refresh runs only in Auto-reconcile.

**One ordering runs the refresh a second time, by design.** Because `git fetch` + `--ff-only` is **idempotent**, this section does **not** guarantee the refresh runs at most once — only that it fast-forwards local `main`, rewrites no history, and creates no branch. On the HEAD==`main` path 1c refreshes first (creating no branch, so HEAD stays `main`), and then a *later* Review drift check — step 7 *Already implemented* — can trigger *Auto-reconcile* in proposal mode, whose step 1 fast-forwards again over the still-`main` HEAD. That second fetch is harmless: it re-advances an already-current local `main`, and *Auto-reconcile*'s *Re-select* re-runs the whole review afterwards, so the implementation is still validated against the tree the branch is cut from. This is why *Create the implementation branch* step 3's later 'do not re-fetch' bar does not apply to it — that bar guards a fetch with no re-validation, whereas Auto-reconcile always re-runs the review after refreshing.

1. **Refresh `origin/main` (best-effort).** Run `scripts/with-env.sh git fetch origin main` — the wrapper loads `GITHUB_TOKEN` from `.env` before exec'ing the fetch. On failure (no `.env`/token, offline, fetch error), skip the fast-forward and leave local `main` as-is; warn that the review and the branch run against a possibly-stale `main`.
2. **Fast-forward local `main`.** Run `git merge --ff-only origin/main`. On success both the review and the eventual branch cut see the freshly-merged code. If the fast-forward fails (local `main` has diverged from `origin/main`), do **not** force it — warn that local `main` could not be advanced and both run against local `main` as-is.

This is the only remote operation `/impl` performs; it mutates only local `main` — a fast-forward, never a history rewrite. On the HEAD==`main` path it runs during the review, so a run that then stops on a blocker may have fast-forwarded local `main` (still no branch, no history rewrite); on any non-`main` path it is a no-op.

## Review the plan against today's tree

This step is a critique pass. Every cited fact in the plan must still hold; every step must still be implementable as written. Findings flow into a Go/No-Go decision below — they are **never** written back to the plan file (nor, in proposal mode, to the proposal document). In proposal mode, "the plan" throughout this section means **the selected step** from *Proposal mode*: its cited files/line ranges, its description, and its `*Acceptance:*` criteria are what must still hold.

1. **Working-tree sanity.** Run `git status --porcelain` and `git rev-parse --abbrev-ref HEAD`, then apply these gates **in order**:
   - **1a — Dirty-tree gate (run first).** If the working tree has uncommitted changes that are clearly unrelated to the plan, surface them and ask before proceeding (mixing concerns makes the eventual PR harder to review). Do not proceed while an unrelated dirty tree remains — never auto-branch over it. Exception: uncommitted `docs/proposals/**` edits from a reconciliation of *the proposal being implemented* are plan-related by definition — never treat them as unrelated. Two reconciliations qualify, both carried forward the same way: (a) edits this command produced via its own *Auto-reconcile the proposal document*, and (b) edits produced upstream by `/plan-proposal`'s *Reconcile completed steps into the proposal* step — the completed-step checkbox flips and status/README promotion `/plan-proposal` deliberately leaves uncommitted (its report even notes the `docs/proposals/` diff "is expected") for `/impl` to carry onto the feature branch. Both are recognized as plan-related only under this confinement: the plan being implemented is that proposal's plan (basename `proposal-NNN-*`), and the uncommitted `docs/proposals/**` edits stay confined to proposal `NNN`'s own file and its own `docs/proposals/README.md` entries — its status row plus any track-narrative sentence naming that proposal's just-changed status, i.e. every README axis `/plan-proposal`'s *Reconcile completed steps into the proposal* legitimately touches for this one proposal (a fully-shipped flip's row move to the **Shipped** table is not reachable here — `/plan-proposal` stops before writing a plan on a shipped flip), never a different proposal's entries. Edits meeting that test belong on the feature branch — the branch cut in *Create the implementation branch* carries them forward and they ship with the implementation PR, exactly as the *Auto-reconcile* edits already do. Edits that fail the confinement test — a different proposal's file, a README edit about a different proposal, or an ad-hoc `/plan` plan whose basename is not `proposal-NNN-*` — stay unrelated: never auto-branch over an unrelated dirty tree.
   - **1b — Record HEAD, do not branch yet.** Note whether HEAD is `main` or a non-`main` branch, purely so the final report can attribute the branch. A non-`main` HEAD here is **not** necessarily pre-existing: record it as *pre-existing when the command started* only when *Auto-reconcile the proposal document* has not run this invocation, and otherwise as *created this invocation by Auto-reconcile* — two of that routine's triggers (*Corroborate against the metadata* and *No pending step*, in Proposal-mode step 3) fire before this section, so it may already have branched. Getting this wrong mis-attributes an *Auto-reconcile* branch as one the user chose in step 4's provenance record and the *Report* `Branch:` line. This record is **not** the input to the branch decision — *Create the implementation branch* re-reads HEAD itself, because *Auto-reconcile the proposal document* may create a branch after this observation. **No branch is created in this section.** Branch creation is deferred until after *Decide* returns Go, so a review that stops on a blocker never leaves a stray empty branch behind. The sole exception is proposal mode's *Auto-reconcile the proposal document*, which must pre-create the branch to hold its `docs/proposals/**` edits; if it already ran this invocation, HEAD is on that branch and *Create the implementation branch* will leave it alone.
   - **1c — Refresh local `main` before the drift checks (HEAD==`main` only).** If 1b saw HEAD on `main` and 1a left the tree clean, run *Refresh `main` before branching* now — `git fetch origin main` + `git merge --ff-only origin/main` — **before** the drift checks below, so steps 2–8 validate the plan against the same `origin/main` tree the branch will be cut from (*Create the implementation branch* cuts from this already-refreshed local `main` without re-fetching). This fast-forwards local `main` only; it creates **no** branch, so the deferral of branch creation past *Decide* is intact. Skip it when HEAD is non-`main` (the user's branch — no fetch) or the tree is dirty; a skipped or failed refresh means the review and the branch both run against local `main` as-is (warn per *Refresh `main` before branching*).
2. **Cited files exist.** For every file path the plan names, confirm it exists. If a file was renamed or deleted, try to locate the current path by name + neighbouring symbols; if you cannot, that is a blocker.
3. **Cited line ranges and symbols still match.** For every `path:line` reference, read that span. Confirm the named function, class, branch, or string is still there. Line numbers shifting is fine (note as a concern); a symbol that was rewritten or removed in a way that invalidates the planned change is a blocker.
4. **Reused functions and utilities still exist.** For every helper the plan claims to reuse (look under `Reuse map`, `Reused functions`, `Reusable artifacts`, or inline mentions), grep for it. A missing reuse target is a blocker.
5. **Config keys.** For every TOML key the plan adds, grep `maestro.toml`, `maestro/config.py`, and `maestro/toml_config.py`. If a key the plan introduces already exists, partly exists, or conflicts with a sibling, that is a blocker until the plan accounts for it.
6. **Dependencies.** For any `Depends on` proposals or prerequisite work the plan calls out, confirm the prerequisite has shipped (read `docs/proposals/README.md` status, or grep for the prerequisite symbol). An unshipped dependency is a blocker.
7. **Already implemented.** Look for evidence the plan's end state already exists (the new function, the new config key, the new file). If most of the plan is already in place, stop — there is nothing to implement. Tell the user; do not re-do work. In proposal mode this is the stale-checkbox case: the step is marked `[ ]` but its `*Acceptance:*` criteria are already met in the tree. Rather than re-implementing, run *Auto-reconcile the proposal document*: `/update-proposals NNN` flips the stale checkbox(es), and re-selection then advances to the genuine next `[ ]` step (renaming the auto-created branch to match). If no pending step remains after reconciliation, report `proposal_complete` and stop.
8. **Architecture invariant compatibility.** Cross-check the plan against the invariants documented in `CLAUDE.md` (context bloat caps, `atomic_write` for JSON / append-only JSONL, identity prompt cap, dashboard thinness, stage model integrity, human-in-the-loop). If the plan would violate any invariant, that is a blocker until the plan accounts for it.

## Decide

Group findings into three buckets:

- **Blockers** — drift, missing dependencies, conflicting state, invariant violations, plan/project mismatch. Any blocker means NOT clean.
- **Concerns** — non-blocking drift the user should know about (line numbers shifted, helper renamed but still present at a discoverable path, an adjacent test was deleted). Surface but do not stop on these alone.
- **Clean** — every cited fact holds and the plan is implementable as written.

Decision rules:

- **Any blocker → stop.** Print a `Plan review` report listing blockers (with the plan section, or proposal step, each one affects), concerns, and a one-line recommendation: revise the source (in plan-file mode, re-run `/plan-proposal NNN` if it is proposal-derived, otherwise edit the plan file by hand) and re-invoke. Do not implement. In proposal mode, doc-drift blockers — a stale checkbox or status row — are auto-reconciled earlier via *Auto-reconcile the proposal document* and do not reach here; only drift that `/update-proposals` cannot fix (e.g. a cited symbol rewritten so the planned change no longer applies) stops here for manual revision.
- **Concerns only → ask.** Surface concerns in the same report shape and ask the user to confirm before implementing. Do not assume yes.
- **Clean → proceed.** Print a one-line `Plan review: clean — proceeding to implementation` and continue to the next section.

## Create the implementation branch

Run this section **only once *Decide* has returned Go** — clean, or concerns the user explicitly confirmed — and **before the first implementation edit**. The deferral is the point: creating the branch here rather than during the review means a run that stops on a blocker leaves no stray empty branch behind, while every run that reaches implementation is guaranteed to be off `main` before a single file changes. Proposal mode's *Auto-reconcile the proposal document* is the only path that creates the branch earlier — it must, because its `docs/proposals/**` edits need a shippable home even when the run terminates at `proposal_complete` without implementing anything.

1. **Re-confirm the working tree first (before any branch operation).** *Review*'s dirty-tree gate (1a) ran before the whole review pass, and *Decide* may have paused for the user to confirm concerns — so an unrelated change can have appeared in the window since. Re-run `git status --porcelain` and apply 1a's test again: if anything clearly unrelated has appeared, surface it and ask rather than branching over it, preserving 1a's 'never auto-branch over an unrelated dirty tree' invariant. **If the user does not confirm the change is plan-related, stop here** — do not create the branch and do not implement, exactly as 1a does not proceed while an unrelated dirty tree remains; the run ends without a branch rather than falling through to step 3. This re-check must complete **before** the `git checkout -b` in step 3 — a confirmation made after the branch exists cannot prevent branching over an unrelated tree.
2. **Re-read HEAD; if it is on a non-`main` branch, leave it.** Read HEAD fresh here (`git rev-parse --abbrev-ref HEAD`) rather than trusting the value *Review*'s 1b recorded — in proposal mode *Auto-reconcile the proposal document* may have created a branch *after* 1b observed `main`, so the recorded value can be stale and acting on it would cut a second, redundant branch. On a non-`main` HEAD, either the user chose it — they are responsible for it being the right one for this plan — or *Auto-reconcile* created it earlier this invocation. Either way no second branch is created, and no fetch or fast-forward runs.
3. **If the freshly-read HEAD is `main`, auto-create the feature branch.** *Refresh `main` before branching* already ran up front during *Review*'s step 1c, so local `main` is already fast-forwarded to `origin/main` and the branch is cut from the same tree the review validated — do **not** re-fetch here (a second fetch could pull commits merged during the review and cut the branch from code the review never saw). Every auto-created name ends in a **unique suffix** (see *Unique branch suffix* above) so the checkout can never collide with an existing branch and this command never has to ask the user for a name:
   - **Plan-file mode:** name it `feat/<plan-slug>-<uid>`, where `<plan-slug>` is the plan file's basename without the `.md` extension and `<uid>` is the unique suffix.
   - **Proposal mode:** name it `feat/<NNN>-step<M>-<step-slug>-<uid>` (matching the project's existing proposal-step branch convention, e.g. `feat/058-step10-openai-tool-adapter-2607101230009a3f1c` — the `<uid>` is a 12-digit timestamp followed by `openssl rand -hex 3`, matching the documented format), where `NNN` is the zero-padded proposal number, `M` is the selected step number, `<step-slug>` is derived from the step title, and `<uid>` is the unique suffix.
   - In either case, sanitize the base slug (everything before `<uid>`) into a git-safe slug the same way the plan-writing commands generate filenames (see `/bug-fix`'s **Write the plan file** section): lowercase, replace non-alphanumeric runs with `-`, trim leading/trailing `-`, collapse repeated `-`. This matters because the basename can be an arbitrary user-supplied `<slug>`/`<absolute-path>` filename (or a free-text step title), not only already-sanitized names — characters git rejects in refs (spaces, `:`, `~`, `^`, `?`, `*`, `[`, `..`, leading `-`/`/`, trailing `.`, `.lock`) would otherwise make `git checkout -b` fail with a raw git error. Append the `-<uid>` suffix **after** sanitizing the base slug, then run `git checkout -b <name>`. **Never ask the user for a branch name.** If sanitization yields an empty or ambiguous base slug, do not stop — fall back to a generic base (`feat/plan` in plan-file mode, `feat/<NNN>-step<M>` in proposal mode) and let the unique suffix carry the identity; the branch is still created without user input. The suffix's mandatory random component (see *Unique branch suffix*) makes a collision with an existing local branch effectively impossible; in the vanishingly unlikely event `git checkout -b` still reports the branch exists, regenerate the suffix — drawing **fresh random hex** so the new token differs even within the same wall-clock second — and retry rather than stopping; never ask the user to pick a name, and never clobber or reuse pre-existing work.
4. **Record the outcome.** Note whether the branch was auto-created here, pre-created by *Auto-reconcile*, or pre-existing when the command started, so the final report can say so.
5. **Confirm before implementing.** Print a one-line `Branch: <name> (<auto-created from main | pre-created by auto-reconcile | pre-existing>)` — all three outcomes step 4 records, so a branch *Auto-reconcile* created is never mis-reported as one the user chose — and only then continue. Implementation must never begin with HEAD on `main`.

## Implement the plan

1. **Create a TodoWrite list** with one todo per implementation step in the plan, in the plan's order. In proposal mode the unit of work is the **single selected step**; break its described changes (and the discrete `*Acceptance:*` criteria it must satisfy) into one todo each, in a build order that keeps the tree working. Mark each `in_progress` before starting it and `completed` immediately when done — do not batch the completion marks.
2. **Implement step by step.** For each step:
   - Use `Edit` / `Write` to apply the change. Reuse the existing patterns the plan named under `Reuse map` instead of reimplementing.
   - If the step introduces or changes behavior, add the matching tests in the same step. Tests must use `mem_fs`, mock all externals (subprocess, network, sleep), and never touch the real filesystem (per the testing principles in `CLAUDE.md`).
   - If the step adds or removes a module, alters a CLI command, or changes a load-bearing design decision, update `CLAUDE.md` and `docs/modules.md` in the same step.
   - Order matters: keep steps so that an interrupted run leaves the tree in a working state. Do not stage a half-finished step at the end.
   - If a step turns out to be infeasible as written (drift the review missed, an assumption that does not hold once you start writing the code), stop and surface to the user. Do not improvise around the plan in a way that materially changes scope — bring the user back into the loop.
3. **Self-review the working tree.** Run `git diff` once after every step lands, and check for: leftover debug code, `breakpoint()` / `pdb` calls, hard-coded paths, secrets, dead branches, tests that only exercise the happy path, missing error handling on new code paths.
4. **Run the quality gates** that match the touched packages. Detect from the diff which packages were touched.

   **Core (run if `maestro/` or `tests/` were touched):**
   ```
   python3.14 -m ruff check maestro/ tests/
   python3.14 -m mypy maestro/
   python3.14 -m maestro.cli gate-lease -- python3.14 -m pytest tests/ -v {worker_args}
   ```

   **Classify a failed core-suite run.** If the parallel core-suite run above fails, do not blindly re-run it — pipe its combined output to `python3.14 -m maestro.cli gate-classify --tool tests --returncode <rc>` (pass the run's exit status as `<rc>`), which prints one classification token. `FAILED` / `COLLECTION_ERROR` are an *answered* red: the run already enumerated the failures, so fix them rather than re-running. `COVERAGE` / `TIMEOUT` / `UNAVAILABLE` are resource artifacts — an OOM-killed xdist worker's lost coverage tripping `--cov-fail-under=100`, or a runner that was killed or could not start — so re-run the suite once through `python3.14 -m maestro.cli gate-lease` and let that result decide, rather than "fixing" a coverage drop that only appears under contention. This mirrors `scripts/quality-gates.sh gate_maestro`, which the agent may also invoke directly instead of the raw command. The `python3.14 -m maestro.cli` module form (rather than a bare `maestro`) mirrors that script's `maestro()` shell function so the CLI self-resolves to *this* checkout — a stale `~/.local/bin/maestro` from a sibling checkout would otherwise load its own config models against this checkout's `maestro.toml` and raise a spurious pydantic `extra_forbidden`.

   **Review (run if `maestro_review/` or `tests/test_maestro_review/` were touched):**
   ```
   python3.14 -m ruff check maestro_review/ tests/test_maestro_review/
   python3.14 -m mypy maestro_review/
   python3.14 -m pytest tests/test_maestro_review/ -v --no-cov
   ```

   **Browser (run if `maestro/dashboard/` or `tests/browser/` were touched):**
   ```
   python3.14 -m pytest tests/browser/ -v -m browser --no-cov --browser chromium
   ```

   Plus any plan-specific verification listed in the plan's `Verification` section. In proposal mode, treat the selected step's `*Acceptance:*` criteria as that verification — each criterion must be demonstrably met before the work is done.

   **Run each of these in the foreground** with an explicit `Bash` `timeout` of `600000` (the 10-minute max) — never `run_in_background: true`. A backgrounded gate run is reaped when the turn yields, so the suite dies silently and the work stalls with nothing continued. Run the package groups as separate foreground calls so each fits the ceiling. If a run is ever backgrounded anyway, poll it with `BashOutput` until the shell exits before doing anything else, and never end your turn while a gate run is still pending.

5. **Fix gate failures at the root cause.** Do not silence errors with `# noqa`, `# type: ignore`, pytest skips, or `Any` escape hatches unless there is a real, narrow reason and you tell the user. After each fix, re-run the failing gate plus any gates whose inputs changed. Repeat until every relevant gate passes. If the same gate fails three times on the same root cause, stop and surface to the user — do not keep guessing.

## Report

End with a plain-text summary:

- **Implemented** — in plan-file mode: the plan path and title. In proposal mode: the proposal (`NNN — <Title>`, with its path) and the step that was implemented (`step <M> — <step title>`).
- **Branch** — name, starting commit short SHA, and whether it was auto-created from `main` at *Create the implementation branch* (after the review passed), pre-created earlier by *Auto-reconcile the proposal document*, or already in use when the command started. When auto-created, note whether local `main` was fast-forwarded to `origin/main` first or the refresh was skipped (fetch failure or divergence) so the branch was cut from a possibly-stale `main`. Every auto-created branch carries a unique suffix, so report the full branch name. If the base slug was sanitized or fell back to a generic base (so it differs from the plan basename or the step title), say so.
- **Review verdict** — `clean` / `clean-with-concerns`, and any concerns that were surfaced.
- **Files modified** — bullet list, one line per file with its purpose.
- **Tests added or changed** — bullet list, with what each test covers.
- **Quality gates** — which gates ran, which passed, how many fix iterations were needed.
- **Acceptance criteria** *(proposal mode)* — list each of the step's `*Acceptance:*` criteria with how it was met.
- **Proposal reconciliation** *(proposal mode)* — whether `/update-proposals NNN` was auto-run during this invocation and why (stale checkbox, all-steps-done with a stale README, or a checkbox/prose contradiction), what it changed (checkbox flips, status promotion, README row), and that those edits are part of the working-tree diff. Separately, when the branch also carries `/plan-proposal`-produced `docs/proposals/**` reconciliation edits for this proposal — the completed-step checkbox flips and status/README row `/plan-proposal` left uncommitted for this run to carry (per the *Review* 1a exception) — say so and that they are part of the branch diff and ride the implementation PR, so the operator is not surprised by doc changes they did not make this run. Note any branch rename triggered by re-selection.
- **Deviations from the plan** — anything implemented differently than written, with the reason.
- **Next step** — point the user at `/review-changes` in a fresh session to review the freshly-implemented branch before shipping — do **not** send them straight to `/create-pr`. `/review-changes` inspects the branch diff against the plan, records a review-findings ledger, and hands off to `/polish`; only once that review comes back clean does the user run `/commit-push` or `/create-pr` to ship. In proposal mode: if the proposal document was auto-reconciled this run, say so and that the checkbox/status edits are already in the branch diff; if it was not, add that `/update-proposals NNN` reconciles the proposal's checkbox and README status after the step merges.

## What to skip

- Do not edit the plan file. Drift findings inform the review; they are never written back to `~/.claude/plans/`.
- Do not hand-edit the proposal document (proposal mode). `/impl` never writes `docs/proposals/` directly. When the document's checkboxes or status have drifted from today's tree, it reconciles them by invoking `/update-proposals NNN` (see *Auto-reconcile the proposal document*) — at most once per invocation — which performs the edit under its own safety rules; `/impl` itself still makes no manual edit to the proposal or its README.
- Do not implement more than the one selected step (proposal mode). If later steps look trivial, stop after the selected step and let the user re-invoke `/impl NNN` for the next one — one step, one PR.
- Do not refactor code outside what the plan touches. Implement what the plan says, nothing more.
- Do not commit, stage, push, or create a PR. Leave shipping to `/commit-push` or `/create-pr`.
- Do not switch branches once implementation has begun. The only branch operations this command performs are the auto-create from `main` described in *Create the implementation branch* (or its pre-branch in *Auto-reconcile the proposal document*) and, when re-selection after *Auto-reconcile the proposal document* changes the target step, a `git branch -m` rename of that same just-created, commit-free branch to match; if the user is already on a non-main branch, leave it alone.
- Do not invent steps the plan does not specify. If the plan is silent on a small detail (logging level, error message wording, helper-function name), make a minimal, contained choice consistent with surrounding code; if the silence is on something load-bearing, ask the user.
- Do not run `/plan-proposal` or otherwise rewrite the plan as part of this command. If the plan is unsalvageable, say so and stop.

## Safety

- If the review surfaces any blocker, stop — do not start implementation, do not "implement what is implementable". Surface and let the user revise.
- If a step would violate an architecture invariant during implementation (something the review missed), stop and surface — do not silently relax the invariant.
- If the working tree contains files that look like secrets (`.env`, credentials, tokens), stop and tell the user — never edit, stage, or delete them.
- If the same gate fails three times on the same root cause, stop and ask the user rather than continuing to guess.
- Do not bypass a quality-gate failure with a workaround (`# noqa`, `# type: ignore`, pytest skip) — fix the root cause.
- Do not run destructive git operations (`reset --hard`, `checkout --`, `clean -f`, branch deletes, force-push).
- Read-only against `~/.claude/plans/` and the pointer file `~/.claude/last-plan-by-folder.json`. `/impl` writes code and tests under the working directory; it does not hand-edit `docs/proposals/`. The only git-state changes it makes are the branch auto-create from `main` (*Create the implementation branch*, or its pre-branch in *Auto-reconcile the proposal document*) and a best-effort `git fetch origin main` plus a `git merge --ff-only origin/main` of local `main` (see *Refresh `main` before branching*) — a fast-forward only, never a history rewrite, and only on the HEAD==`main` path (the refresh runs up front during the review, so a run that stops on a blocker may still have fast-forwarded local `main`). In proposal mode it may delegate a one-time reconciliation of the proposal document to `/update-proposals NNN` (see *Auto-reconcile the proposal document*), which edits `docs/proposals/**` under its own safety rules — that delegated write is the only way this command touches the proposal document or its README.

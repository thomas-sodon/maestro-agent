# Loop Lifecycle

Detailed documentation for the `run_loop()` phase orchestration, crash handling, shutdown, and deployment hooks. For the high-level overview, see [CLAUDE.md](../CLAUDE.md).

## Startup

### Shutdown/Startup Awareness

`shutdown()` persists a timestamp to `{memory_dir}/lifecycle.json` via `atomic_write`. On startup, `run_loop()` reads and consumes that file, computes downtime duration, and writes a journal milestone (`triggered_by="startup"`) describing how long Maestro was offline. This gives Maestro temporal continuity across restarts.

### Post-Restart Merge Detection

Merged/closed evolution PRs are detected on the **first loop iteration after restart** and, since proposal 155 step 4, on **every iteration that has an `implemented` plan** (`LifecycleController.phase_will_run`), so a merged gap plan is marked merged within one tick without waiting for a restart. On each such iteration: if merged → status `"merged"` + journal milestone; if closed without merging → status `"rejected"` + `learn_from_rejection()` (journal realization + self-model update). A fuelled `propose_plan()` prompt lists the newest human rejections and the end reasons of earlier plans on the same gap, so future proposals avoid repeating rejected approaches.

### Pre-Deploy Notification

`scripts/safe-deploy.sh` invokes `maestro notify-pre-deploy --from-ref $ROLLBACK_HEAD --ref $DEPLOY_TARGET --run-id $GITHUB_RUN_ID` via `docker compose exec` immediately before `docker compose stop loop`. The CLI enumerates merged PRs in the deploy window via `SubprocessVCS.get_commits_between()` (parsing `Merge pull request #N` and squash `(#N)` trailers), fetches each PR's title/body via `SubprocessCodeHost.get_pr_info()`, and writes:

1. A durable `Message(sender="thomas", message_type="info")` summarising which PRs are landing — picked up by the next `process_messages` phase or on first iteration after restart.
2. A journal milestone event (`Journal.record_event`, `triggered_by="pre_deploy"`, in `events.jsonl`) so the event is recorded even if SIGTERM arrives before the loop processes the message. It is an operational record, so it never enters the inner-thought journal the planning prompts read.

The notice informs contemplation (as a message) but never triggers a `respond_to_messages` reply: `_process_messages` excludes it (`is_pre_deploy_notice`, keyed on the shared `PRE_DEPLOY_MESSAGE_ID_PREFIX`) from the reply context that gates and feeds that phase, so a notice-only batch skips the reply and a mixed batch replies to Thomas's typed messages only.

Best-effort throughout: failures log warnings but never fail the deploy. Turns post-restart merge detection from a surprise into an expected, contextualised event.

## Running

### Gate Execution Lease — Width, Deadline, Scope, Runnability

Three facts govern a local quality-gate run: how **wide** it may be (the xdist worker count), how **long** its pytest command may take (the enforced subprocess deadline), and **which** suite it executes (the whole tree, or the impacted subset). All three are derived by a single owner rather than restated at each gate site — `gate_capacity` grants the width and the deadline through one lease, and `gate_scope` decides the suite — and each reaches the gate reader through exactly one seam. A site that re-derives any of the three beside its owner diverges silently: a run killed by a ceiling calibrated for another machine, or a subset-green promoted to a terminal verdict.

A fourth fact sits beneath all three: whether the gate can reach a verdict **at all**. A first-party sibling package that resolves only as a half-empty PEP 420 namespace, a suite pytest cannot collect, a suite that measurably cannot finish inside its granted deadline — none of these is a red any diff can clear, and width, deadline and scope all presuppose an environment that can answer. `gate_environment` owns that fact as a closed `GateRunnabilityKind` verdict, and its three in-loop consumers read it before an implementation attempt is spent, when a red is attributed, and at the lease's own admission. The fit reading is deliberately conservative about the deadline it judges against: both its arms are measured against the budget that was *actually enforced* — the lease-derived one only while `[loop] gate_budget_lease_owned_enabled` is on, else `[timeouts] selfcheck`, which is what `_run_gate_command` kills a run at when the flag is down — and, when a cap is known, a suite is called `UNFIT` only once the escalation has reached `[timeouts] selfcheck_max`. `derive_deadline` escalates run by run, so the intermediate rungs are the runs whose job is to discover how long the suite takes; reading them as a broken environment would hold every approved plan while the escalation that would have rescued them was still in progress. A reading spared only by that climb surfaces as `SOUND` / `escalating`.

Two operator commands put the same fact on the command line, so the person who can actually repair a broken environment can ask about it. `maestro preflight` routes its startup sibling check through the oracle's `probe_provisioning` — pure, no subprocess, so the deploy script's timed smoke test is unaffected — covering every declared sibling and failing loud with the owner's own wording, which closes with the editable-install command that repairs it. `maestro gate-check`, already about to spend a full suite run, refreshes the whole verdict first under `[loop] gate_environment_oracle_enabled`, prints one line on stderr (stdout stays the single parseable `--json` line, whose payload gains one `runnability` key), and *writes the cache the loop reads next* — so a repair the operator has just proved locally releases the lease seam's refusals without waiting for the loop's own next probe. Flag off, `gate-check` is byte-identical to before: no probe, no line, no row.

That single-owner property is enforced by the test suite, not by convention. `tests/test_gate_lease_owner.py` is the guard for the first three nouns, scanning the gate sites the shared `tests/support/gate_sites.py` names; `tests/test_gate_environment_owner.py` is the guard for the fourth, including the pin that no module outside the oracle calls `find_spec` on a first-party sibling name — the rival spelling `preflight` used to carry. The lease guard's scope rules additionally pin the two reads that must stay whole — the fix loop's fresh full-scope certification read, the only path to a green terminal, and the convergence terminal's re-read that re-derives an outcome before a plan is demoted. See [modules.md](modules.md) for the mechanism behind each owner.

### Phase-Level Loop Progress Persistence

The body of `run_loop()` is an ordered list of named phases (`_LOOP_PHASES` in `maestro/loop/iteration.py`):

1. `ensure_main_branch`
2. `check_contributions`
3. `process_messages`
4. `tend_evolution_prs` — top-priority PR tending; runs every iteration immediately after `process_messages` so an open evolution PR gets attention before any new SDK-spending phase fires (see [Evolution PR Tending](#evolution-pr-tending) below).
5. `attend` — the conscious-workspace observer; runs only while `[loop] conscious_workspace_observe_enabled` is on (off in the base).
6. `contemplate`
7. `respond_to_messages`
8. `implement_approved_plans`
9. `check_merged_plans`
10. `review_artifacts`
11. `execute_approved_publications` — zero-SDK-cost executor (proposal 033) that turns approved `PublicationProposal` rows into public GitHub repos. Not in `_BUDGET_GATED_PHASES` so the queue drains during burn-rate throttle. Each tick runs three ordered passes: stale-executing reconcile, resume-after-checkpoint, and at most one fresh `_publish()` (FIFO by `reviewed_at`). The durable checkpoint is `published_url` — once `gh repo create` returns, the URL is persisted before the first `git push` so a crash routes the proposal through `_resume_publish()` next tick instead of double-creating the repo.
12. `process_rejected_plans`
13. `generate_task`
14. `run_task` — drains one work item per iteration via `_run_task_phase`, in priority order `pending_user_requests` → `pending_pr_requests` → task-queue head.
15. `evolve`
16. `audit_self_model` — runs every `[loop] audit_self_every` iterations (default 10, 0 disables, skipped under `--smoke`). Zero-SDK-cost deterministic rules from `maestro/audit_checks.py`. Not in `_BUDGET_GATED_PHASES` because it has no SDK spend. A rule bug or an I/O error propagates to `run_loop`'s crash boundary (fail-loud), so that iteration skips `dream` and the loop shuts down with `crashed=True`. Findings write `audit_observation` journal entries (distinct `entry_type` so provenance survives narrative re-reads), append `[audit] …` to `open_questions`, and persist an `AuditResult` row (zero-finding cycles included). The next `contemplate()` pulls `memory.get_most_recent_audit()` and threads the findings into `update_self_model()` as an INTEGRATE / REFUTE / KEEP section — rules are self-extinguishing once integrated.
17. `curate_pending_plans` — opt-in (both `[loop] curate_enabled` and a positive `curate_every` required); refines or marks obsolete the oldest unrefined `pending_review` plan (proposal 060), and under `[loop] plan_feedback_enabled` also fires off-cadence (needing `curate_enabled` but not `curate_every`) while a pending plan holds unaddressed reviewer feedback (proposal 145; [self-evolution](self-evolution.md#reviewer-feedback-on-pending-plans)).
18. `dream` — every `dream_every` iterations (skipped under `--smoke`). Runs only zero-SDK passes (phase-cost report refresh, archive); the priced digest was deleted. Not in `_BUDGET_GATED_PHASES` nor suppressed by the `external_delivery` focus profile, and deduped through `_last_phase_iteration` so a frozen throttled iteration runs the passes once.

After every phase the loop calls `_persist_progress(iteration, next_phase)`, which atomically writes `{"iteration": N, "next_phase": "..."}` to `lifecycle.json`. Only then is the shutdown event checked: an in-flight phase always runs to completion before the loop bails out.

On restart, `_read_lifecycle_progress()` returns the saved `(iteration, next_phase)` and `run_loop()` re-enters the same iteration at the saved phase instead of replaying it from scratch (`next_phase=None` means the iteration finished cleanly and the next iteration starts fresh). `check_merged_plans` is gated by a separate `first_iteration_after_restart` flag, not by `iteration == 1`, so it still runs once per restart even when the absolute iteration counter has advanced — and is skipped on resume if the saved cursor sits past it. The `max_iters` boundary uses a separate `iterations_run` counter so a resumed iteration counts toward the budget.

### Resume-In-Place for Rate-Limited, Stale-Session, and CLI-Crash Failures

When a phase raises `SDKError` with `category=RATE_LIMIT`, `run_loop()` does **not** bump the iteration counter or replay already-completed phases. Instead:

1. The loop records `retry_phase_index = phase_index` (the for-loop variable is still in scope inside the `except` handler).
2. `_consecutive_rate_limits` is incremented. If it exceeds `_MAX_CONSECUTIVE_RATE_LIMITS` (5), the handler hands off to **rate-limit extended idle** instead of crashing (see below).
3. Otherwise, `_capture_session_id("a"/"b", session)` mirrors the live `ClaudeSDKClient` session ids into `self._iter_session_a_id` / `self._iter_session_b_id`, and `_persist_progress(iteration, _LOOP_PHASES[retry_phase_index])` writes the cursor pointing at the failed phase plus the ephemeral per-iteration state (`message_context`, `reflection`, `iteration_usage`, `session_a_id`, `session_b_id`) into `lifecycle.json`.
4. The loop sleeps `_RATE_LIMIT_COOLDOWN_SECONDS` (300) on the shutdown event, then re-enters the same iteration at `start_phase_index = retry_phase_index`. `iterations_run` is **not** incremented — retries don't count toward `max_iters`.
5. On a clean iteration end, `_consecutive_rate_limits`, `_consecutive_cli_crashes`, `_consecutive_stream_stalls`, `_iter_message_context`, `_iter_reflection`, `_iter_session_a_id`, `_iter_session_b_id`, and `_resume_phase` are all cleared so the next iteration starts truly fresh.

`STALE_SESSION` errors (raised by `query_on_session` when the first turn on a resumed session fails with an error that isn't rate-limit and the stored `_maestro_last_session_id` was never updated from `None`) follow the same retry-in-place path with two differences: **no cooldown is slept**, and the `_consecutive_rate_limits` counter is **not** bumped. The persisted `session_a_id` / `session_b_id` are cleared so the retry creates fresh sessions instead of re-resuming the dead one.

`CLI_CRASH` errors (`SDKError` with `category=CLI_CRASH`, typically raised when the Claude CLI subprocess dies mid-conversation — e.g. `ProcessError: exit code 1`) follow the same retry-in-place path as `RATE_LIMIT` with three differences: **no cooldown is slept** (CLI crashes are not capacity-driven), a **separate** `_consecutive_cli_crashes` counter is bumped with a **lower ceiling** (`_MAX_CONSECUTIVE_CLI_CRASHES` = 3, vs. 5 for rate limits) so a deterministic crash loop fails fast into the crash-detection path, and the persisted `session_a_id` / `session_b_id` are **preserved** (not cleared): the iteration-end `finally` disconnects the dead `ClaudeSDKClient`, and the retry opens a fresh client with `resume=<last_session_id>` so the server-side transcript picks up where the crash happened. When a CLI crash fires before any successful turn captured a `session_id`, the mirrored slot stays `None` and the retry simply opens a cold session. The journaled milestone uses `triggered_by="cli_crash"`. On a clean iteration end, `_consecutive_cli_crashes` is cleared alongside `_consecutive_rate_limits`.

`STREAM_STALL` errors (`SDKError` with `category=STREAM_STALL`) follow the same retry-in-place path as `CLI_CRASH` with two differences: persisted `session_a_id` / `session_b_id` **are** cleared so the retry creates fresh sessions (a stalled stream is not recoverable by resume), and the bump uses a **separate** `_consecutive_stream_stalls` counter with ceiling `_MAX_CONSECUTIVE_STREAM_STALLS = 3`. The trigger is `_consume_messages` detecting SSE idleness — either the `asyncio.wait_for` guard firing at `[sdk] stream_idle_timeout_seconds` (default 180s, or `[sdk] tool_stream_idle_timeout_seconds` for tool-using callers, default 1800s — a cross-field validator pins it strictly above `[timeouts] selfcheck_max`, so a caller that shells out to run the quality gates cannot have its stream declared stalled before the longest permitted gate run can answer) or a `ResultMessage` arriving with `num_turns=0` and zero input/output tokens (upstream SSE drop). **No cooldown is slept** — stream stalls are transport-layer anomalies, not capacity pressure. The journaled milestone uses `triggered_by="stream_stall"`. On a clean iteration end, `_consecutive_stream_stalls` is cleared alongside the other transient counters.

### Rate-Limit Extended Idle

When `_consecutive_rate_limits` exceeds `_MAX_CONSECUTIVE_RATE_LIMITS` (5), the loop transitions out of the fast-retry path (300s cooldown between attempts) into an extended idle state instead of crashing — sustained Anthropic-side capacity pressure is treated as an unavailability, not a bug, so no crash.

1. **Enter** (`_enter_rate_limit_idle(iteration, phase)`): sets `_rate_limit_idle_entered_at = datetime.now(UTC).isoformat()`, calls `_persist_progress(iteration, phase)` so `lifecycle.json` records both the failed-phase cursor *and* the idle flag, sends a Telegram notification, and journals a `rate_limit_idle_enter` milestone. Notification and journal failures are caught and logged so a transient outage during entry doesn't bypass idle.
2. **Probe** (`_run_rate_limit_idle_probe()`): an exponential-backoff loop that sleeps `min(base * 2**attempt, cap)` between probes (`[sdk] rate_limit_idle_probe_interval`, default 300s; `[sdk] rate_limit_idle_max_probe_interval`, default 3600s). Sleeps are chunked by `_STANDBY_MAX_SLEEP_SECONDS` so `_write_heartbeat()` ticks during long waits and the Docker healthcheck stays green. Each probe is a low-effort single-turn `query("Reply with OK.", caller="rate_limit_idle_probe")`. Any exception (`SDKError`, generic `Exception`) counts as a failed probe and continues the loop; only shutdown or a clean probe exits.
3. **Exit** (`_exit_rate_limit_idle()`): clears `_rate_limit_idle_entered_at`, resets `_consecutive_rate_limits` to 0, sends a Telegram notification, and journals a `rate_limit_idle_exit` milestone. The existing resume-in-place cursor (`_resume_phase`) is left intact, so the next iteration body resumes at the failed phase exactly as if the original retry had succeeded.

**Restart-into-idle**: `_read_lifecycle_progress()` returns `rate_limit_idle_entered_at` as part of its tuple. On startup (or any iteration top), if that value is set and we're not in `--smoke` mode, the loop drops directly into `_run_rate_limit_idle_probe()` *before* attempting any SDK phase work — a hard kill or container restart during idle resumes paused rather than blindly retrying the failed phase. Smoke mode bypasses both entry and the restart-into-idle gate so deploy-validation stays deterministic.

**Telemetry caveat:** on any retry (rate-limit, stale-session, CLI-crash, or stream-stall), the phase that raised is re-run from scratch. `IterationUsage.per_caller` (and the top-line `calls` / `input_tokens` / `output_tokens` counters) therefore double-count the sub-calls inside that phase that succeeded before the failure fired. Counts may exceed actual distinct work by up to one phase-retry's worth per iteration. This is accepted for simplicity; snapshot-on-retry would require persisting pre-phase usage, which is more plumbing than the telemetry accuracy warrants.

**Phase idempotence:** because a retry re-runs the phase from the top at the same iteration, any phase that writes once-per-cycle state must key those writes to the iteration so the retry re-reads what its first attempt stored instead of adding to it — `contemplate()` registers its `reflection-{iteration}` bet, owned-backlog snapshot, and sensor-readings row at most once per iteration (#4106). Still re-applied on retry, and accepted: usage telemetry, the journal reflection entries `contemplate()` and `evolve()` write, the workspace broadcast receipt, and `evolve()`'s `introspect` call.

### Loud Loop Phase Failures

`run_loop()` does **not** wrap its phase dispatch body (the phases in `_LOOP_PHASES`) in broad `except Exception:` handlers. When any phase raises, the exception unwinds through the outer `try`/`finally`, `sys.exc_info()` classifies it as a non-`SystemExit`/`KeyboardInterrupt` unwind, `shutdown(crashed=True)` is called which **skips** writing `last_shutdown` to `lifecycle.json`, and on the next startup `_read_lifecycle_progress()` reports `crashed=True` — triggering the crash-detection path (Telegram ping, journal milestone, log warning).

The surviving exception handlers inside the phase dispatch body are narrow and intentional:

1. `run_loop`'s `except SDKError` around the phase dispatch re-enters the failed phase in place for `STALE_SESSION`, `STREAM_STALL` and `CLI_CRASH`, each under its own small consecutive ceiling (`_MAX_CONSECUTIVE_STALE_SESSIONS`, `_MAX_CONSECUTIVE_STREAM_STALLS`, `_MAX_CONSECUTIVE_CLI_CRASHES`) past which it re-raises. `RATE_LIMIT` sleeps a `_RATE_LIMIT_COOLDOWN_SECONDS` cooldown and, once `_MAX_CONSECUTIVE_RATE_LIMITS` is exceeded, hands off to `_enter_rate_limit_idle` extended-idle probing — this is the normal operational state, not a bug. Every other category re-raises into the crash path.
2. `EvolutionEngine.evolve()`'s internal `except SDKError` / `except ProposalParseError` blocks are documented evolution skips that journal an `evolution_skip` entry.

Method-internal best-effort handlers elsewhere also survive unchanged: `contemplate()`'s diagnostic-snapshot and reflection-journal writes in `maestro/loop/contemplation.py` (the main `introspect()` call is **not** wrapped), and in `maestro/agent.py` `ask_thomas()`'s Telegram-notify catch, `_process_messages()`'s journal-write catch, in `maestro/loop/implementation.py` `implement_plan()`'s per-plan cleanup-on-failure and its environment-hold `evolution_note` write (a narrow `except (OSError, ValueError)` that logs loudly and falls through — the hold stamp is already persisted, so the plan stays held either way), and startup best-effort paths, `shutdown()`'s internal best-effort handlers, `_read_lifecycle_progress()`'s corrupt-file default, and `maestro.sdk.query()`'s `except BaseException` cancel-containment.

The inherited hold's sibling bookkeeping no longer lives in `agent.py` at all: it moved to `loop/plan_holds.py::record_inherited_hold`, where the self-model load, the `evolution_note`, and the base-repair directive save each carry their *own* narrow `except (OSError, ValueError)` and their own WARNING, and a fourth guarded write ahead of them — the `maestro:gate` gap issue opened through `self_health.open_inherited_gate` (proposal 155) — carries its own `except (sqlite3.Error, OSError, GapStoreSchemaError)`, and is skipped while `[loop] evolve_every` is `0`, since its only closer is the red-main detector in evolve's pre-step. The four fail for different reasons and cost different things, so each names what was lost. None of the four may propagate. That is a deliberate divergence from issue #3814's wording, which asked for the directive write to propagate to the per-plan handler: `implement_plan()`'s outer handler routes through `classify_attempt` → `ABANDON` and demotes the plan before re-raising, which would destroy the hold stamped moments earlier — so the loud, named WARNING is the correction, not the raise.

A dedicated regression test (`test_run_loop_phase_crash_invokes_crash_handler_on_restart`) pins the phase-crash → crash-handler wiring end-to-end.

### Evolution Iteration Stability

`MaestroAgent.evolve()` is hardened against two classes of waste / crash:

1. **Bounded gap inputs**: `evolution_fuel.render_gap_block` caps every input `propose_plan()` interpolates at its `GAP_CONTEXT_CAPS` entry with a truncation marker. There is no priority-based pre-flight skip; bug triage stays human, and only a trusted gap issue fuels the call — with none, evolve makes no SDK call and runs no gate subprocess.

2. **Structured proposal failures**: `EvolutionEngine.propose_plan()` raises `ProposalParseError` on JSON decode failure instead of falling back to a junk plan. The caller in `evolve()` catches the exception and journals the skip. SDK rate-limit errors (`SDKError`) raised inside `propose_plan()` are similarly caught and journalled as `evolution_skip` notes.

3. **Telemetry for `auto_fix`**: `evolution_quality.auto_fix()` sets `caller="auto_fix"` and `effort="high"` on its `QueryOptions`.

### Rejection-Aware Evolution (Detail)

PRs created as normal (non-draft). Both closed-PR and dashboard/Telegram rejection paths trigger the same learning flow. The auto review process (`maestro_review`) handles CI failures and review comments.

Rejection learning is **best-effort and loud**: `EvolutionEngine.learn_from_rejection()` still short-circuits if a `realization` journal entry tagged `triggered_by=rejection:{plan_id}` already exists (idempotent on the learning side), but `MaestroAgent._process_rejected_plans()` and the `check_merged_plans` phase now run `learn_from_rejection()` followed by `mark_rejection_learned()` as plain sequential calls with no `try`/`except`/`finally` wrapping either one. If `learn_from_rejection()` fails, the loop crashes through the outer `finally` and the crash-detection path fires.

The gap prompt shows the LLM recently rejected approaches, and `EvolutionEngine.submit_for_review()` enforces a **7-day cooldown** (`_REJECTION_COOLDOWN_DAYS`) on resubmitting any plan whose normalized title matches a recently-rejected plan — the cooldown counts from the rejected plan's `reviewed_at` (falling back to `created_at`); unparseable / missing timestamps fail open so a corrupted entry can never block submission forever. An issue-bearing (gap) plan the cooldown refuses is recorded `obsolete` as `[deferred:cooldown:<rejected id>]` — a deferral, not an attempt — and fuel selection skips that gap until the cited rejection's cooldown elapses (`evolution_submission.gap_cooldown_until`).

### Evolution PR Tending

`EvolutionEngine.tend_evolution_prs()` is a dedicated loop phase (index 4, between `process_messages` and `contemplate`) that keeps open evolution PR branches healthy without human intervention. It is **purely mechanical** — no SDK calls, no `tend_session`, no LLM-driven conflict resolver or post-merge auto-fix — and runs *before* any SDK-spending phase so a drifting PR gets attention first. Every open `maestro/evolve/*` PR gets one of four treatments per tending pass:

1. **Clean / ahead of main** — no-op.
2. **Behind main** — fetch `origin/main`, merge into the PR branch (merge-only, never rebase, never force-push), run subprocess quality gates, push. Preserves review history and reviewers' line comments.
3. **DIRTY / BLOCKED / UNSTABLE (conflicts)** — detect the conflicted file list mechanically via a dry `merge --no-commit` probe (immediately aborted) and append `(pr_number, pr_title, conflicted_files, plan_id, pr_body, pr_url)` to `TendPRsResult.conflicts_routed`. The LLM never touches a conflicted tree here; a cooldown stamp (`last_conflict_resolution_attempt_at`) suppresses re-routing the same wedged PR every iteration.
4. **Post-merge gate breakage** — when subprocess gates fail after a clean merge, the branch is reset hard to `origin/<branch>`, a cooldown stamp (`last_quality_fix_attempt_at`) is set, and `(pr_number, pr_title, gate_summary, plan_id, pr_body, pr_url)` is appended to `TendPRsResult.quality_gates_routed`.
5. **Quiet** (no activity in 48h/72h/168h) — post a tapered reminder comment on the PR. The anchor is `max(pr.updated_at, last_pr_reminder_at)` so reminders don't spam after a reviewer posts a comment.

PRs accumulated in `conflicts_routed`, `quality_gates_routed`, or `changes_requested_prs` are appended to `SelfModel.pending_pr_requests` by `_route_pr_feedback_to_pending_requests` as multi-section Markdown remediation prompts. Each entry has the same stable section order — `Remediate PR #<n>: <title>` header, `## Problem` (per-reason block, multiple blocks when several categories fire on the same PR within one tend pass), `## Original Evolution Plan` (rendered from `Memory.get_plan(plan_id)`, with an "archived" fallback note when the plan has rolled out of hot storage), `## Original PR Description` (PR body verbatim, with `(none — PR was opened without a body)` literal when empty), and `## Remediation Guidance` (branch hint, PR URL, "stay on this branch / preserve acceptance criteria" footer). Entries are appended in ascending PR-number order so the oldest PR is drained first. Per-PR dedup across tend cycles uses the unified `Remediate PR #<n>:` header marker. The next `_run_task_phase` pops the head and executes the remediation task directly — bypassing `generate_task`'s cadence and idea-generation cost so urgent PR work reaches execution within one iteration regardless of `[loop] task_every`. When the head-CI diagnosis path ran, the pre-rendered `## CI Failure` block (`ci_diagnosis.render_ci_failure_section`) is placed between `## Problem` and `## Original Evolution Plan`, so the concrete failing line sits beside the failing-check name. When *that* excerpt names the source-size guard (`tests/test_source_file_size.py`), `prompts/remediation.py::size_pin_cure_hint` appends one bounded line directly beneath it stating that every file stays below `SPLIT_BUDGET`, which is never raised, and that the cure is moving the addition into a concern-named `<parent>_<concern>` sibling module — never a trim of comments, logs or names — the one gate whose cure is counter-intuitive enough that the symptom alone strands a self-clearable red. The hint is prompt text only: no flag, no new state, no extra log fetch, and any other failing gate's excerpt leaves the composed directive byte-identical. Because these entries are kilobyte-scale prompts, `pending_pr_requests` is exempt from the per-item `MAX_ITEM_CHARS` cap that still applies to `pending_user_requests`.

**Cadence** — runs every `[loop] tend_prs_every` iterations (default 1, i.e. every iteration) *plus* the first iteration after restart so a deploy or restart during an open-PR window picks the work up immediately even if a non-default cadence is configured. A regression test pins the default at 1 because tending is top-priority — any wedged or behind PR should be tended before any new SDK-spending phase runs in the same iteration. Disabled entirely when `[loop] tend_prs_enabled = false`. Skipped under `--smoke`. **Not budget-gated** — because the phase spends zero tokens, peak-throttle and burn-rate windows leave it running.

**Ordering** — PRs are visited in `pr.created_at` ascending order (oldest PR first). The JSONL insertion order of plans is incidental — under any partial interruption (an exception from `_tend_single_pr` propagates out of the for-loop, a `CancelledError` from shutdown) the oldest PRs must have had their turn first, since those are most likely to be drifting from `main` and needing help. Plans whose PR is no longer in the open-PR snapshot sort last (they are skipped anyway).

**Main-branch tamper refusal** — before touching any PR, the phase verifies `origin/main` is not behind `local main` via `commits_ahead_behind(remote_ref="origin/main")`. If the local main has unpushed commits (a human or script made a direct change), the phase refuses to run and records an error. Prevents accidentally merging un-reviewed main-branch state into a PR.

**CHANGES_REQUESTED skip** — PRs whose latest review decision is `CHANGES_REQUESTED` are skipped *only when the review is still fresh against the current head*. `_review_decision_is_stale()` checks the host adapter for `review_decision_head_sha` (the commit the reviewer actually saw) or the `review_decision_at` / `head_committed_at` timestamp pair: if the head has advanced past the reviewed commit, tending resumes and `TendPRsResult.stale_review_resumed` is incremented. Non-stale `CHANGES_REQUESTED` PRs land on `changes_requested_prs` for directive routing. When neither signal is exposed by the adapter, the gate falls back to today's strict skip and emits a `logger.debug` naming the missing field so the gap is visible without breaking the loop.

**Orphan branch reconciliation** — the phase also inspects `origin`'s `maestro/evolve/*` branches that have no open PR. If the branch belongs to a plan that is still `approved`, the phase re-opens a PR. This catches the gap where `implement_plan` committed and pushed but crashed before calling `code_host.create_pr()`.

**Counters** — `TendPRsResult` returns per-phase counters (`tended`, `merged_updated`, `conflicts_routed`, `quality_gates_routed`, `conflicts_cooldown_skipped`, `stale_review_resumed`, `reminders_sent`, `orphans_repaired`, `skipped_for_review`, `changes_requested_prs`, plus an `errors: list[str]`) for journal/telemetry. The phase itself never raises for per-PR failures; errors accumulate into the result and the next PR is still processed.

**Persistence** — `EvolutionPlan` carries `last_pr_reminder_at: str | None`, `last_conflict_resolution_attempt_at: str | None`, and `last_quality_fix_attempt_at: str | None` (all ISO-8601 UTC). On startup `ensure_schema()` advances the schema fingerprint on a mismatch; the dataclass loaders fill the removed conflict-streak fields' defaults when each row is next read (no whole-file rewrite).

### Dequeue-Face Merged-PR Exclusion (`_gate_pr_remediation_merged`)

The **first** zero-SDK-cost check on a dequeued `pending_pr_requests` entry, ordered ahead of *both* the merge-block gate and the preflight gate. Where the merge-block gate asks "is the blocker something Tend PR clears?" and preflight asks "has the problem self-resolved?", this gate asks the most basic question first: **has the PR already merged into `main`?** A merged PR has nothing left to remediate, so routing it is pure waste — and worse, the downstream sites *stamp* it: the merge-block gate explicitly passes a merged PR through (`_probe_pr_merge_block` reports `landed_ok` → the gate returns `False`), and preflight, finding the merged branch green, records a `success` `TaskRecord`. Either way a merged PR became a counted remediation lap, feeding the false-success-recurrence and unlanded-remediation sensors that have read git-merge-truth and indicted exactly this re-routing for many cycles without any actuator to stop it. This gate is the owed eviction edge.

**Mechanism.** Immediately after `model.pending_pr_requests.pop(0)` (the pop *is* the eviction — the entry is already removed from the queue and is only ever restored by the graceful-shutdown re-queue, which runs after `run()`, never reached here), `_run_task_phase` calls `_gate_pr_remediation_merged(goal, pr_branch)`. The gate parses the PR number from the `Remediate PR #<n>:` directive (a regex miss returns `False` without consulting merge state) and reads `is_pr_settled(pr_num).branch_landed` **at most once** — the shared, provenance-stamped `MergeTruth` chokepoint (proposal 087) that `git fetch origin`s first (fail-loud), observes host-API-first with a git-subject (`_git_pr_merged`) fallback only when the host call raises, and memoizes the observation for the rest of the iteration so every PR-servicing face shares one fetch. `branch_landed` is `True` exactly for a `MERGED` PR. When it reports landed, the gate logs the eviction and returns `True`; `_run_task_phase` then returns **before routing a `Remediate PR #N` task or recording any `TaskRecord` stamp** — starving the false-success counter at its source. A still-open PR reads not-landed and proceeds to remediation; because the fetch is fail-loud, no verdict is ever authored on unfreshened refs. The chokepoint is AST-enforced as the only door to a merge decision by `tests/test_structural_guards.py`.

This gate produces **no** `TaskRecord` and **no** `RemediationTracker` entry — unlike the merge-block skip (a zero-cost `partial` no-op, #2543) and the preflight skip (a zero-cost `success` no-op), which each record one. The distinction is intentional: a merged PR is not a no-op remediation to account for, it is a non-event to exclude before any counting begins.

### Dequeue-Face Commit-Ancestry Eviction (`_gate_pr_remediation_landed`)

The commit-ancestry complement to `_gate_pr_remediation_merged`, slotted **immediately after** it in `_DEQUEUE_GATE_TABLE` (and ahead of stand-down / merge-block / branch-resolved / preflight). The merged-exclusion gate keys on the **PR object** — host-API `is_pr_merged` with a git-log subject fallback — so it never evicts the **#2662 phantom**: a PR whose substantive commits have already landed in `origin/main` (via squash, a sibling PR, or a prior Tend merge) while the PR object itself still reads `OPEN`. The merged gate asks "is the PR object merged?"; this gate asks the one settling question it skips — **"is the branch HEAD already an ancestor of `origin/main`?"** — turning `git merge-base --is-ancestor` from recital into the dequeue control path's machinery.

**Mechanism.** Wired into the chain via `_run_landed_gate(ctrl, ctx)`, which dispatches through the agent shim `_gate_pr_remediation_landed(entry, source)` (the patchability seam the test suite monkey-patches; the conftest `agent` fixture defaults it to "not landed" so existing remediation tests skip the real `git fetch`). The gate body parses the `Remediate PR #<n>:` header (a miss returns `False` without git I/O) and requires a `pr_branch` (a branchless request returns `False`). Its **first physical act** is `git fetch origin` with `check=True` — fetch-before-word made literal: a fetch failure **propagates loudly** (no swallowing handler, satisfying the no-silenced-exceptions invariant) so no merge-truth verdict is ever authored on stale refs. It then calls `_branch_merged_into_main(f"origin/{pr_branch}")` (`git merge-base --is-ancestor` against the freshly-fetched remote-tracking ref). A non-ancestor head — including the fail-closed `False` from an empty/unreadable branch — returns `False`, so genuine remediation proceeds untouched through to the preflight gate.

On a confirmed ancestor the cure has already landed, so the gate records a zero-cost `partial` `TaskRecord` stamped `[landed]` (`Marker.LANDED`) — `partial`, never `success`, because **this task caused nothing**; a `success` here would feed the very false-success-recurrence sensor the eviction exists to starve — counts it as a `RemediationTracker` no-op so a PR that keeps re-presenting an already-landed head stops being re-routed, and returns `True` to evict before any SDK session opens.

### Dequeue-Face Host-Closed Terminal (`_gate_pr_remediation_host_closed`)

Slotted in `_DEQUEUE_GATE_TABLE` **immediately after** the commit-ancestry landed gate (and ahead of ready / stand-down / merge-block / branch-resolved / preflight). Both settled arms above key eviction on the branch having *reached* `main` — the merged gate on the PR object (`is_pr_merged`), the landed gate on `git merge-base --is-ancestor`. Neither fires on the categorically distinct failure this gate owns (#3112): a PR the **human already CLOSED without merging**. Such a PR reads `mergedAt` null → not-landed → the settled arms pass it through → it is re-admitted as a full remediation lap **every iteration**, running the LLM against a PR no lap can land. This is not giving up on a live PR (a pattern Thomas has rejected with "Stop giving up"); it is *reading* a terminal the human's own hand already authored.

**Mechanism.** Wired via `_run_host_closed_gate(ctrl, ctx)`, which dispatches through the agent shim `_gate_pr_remediation_host_closed(entry, source)`. The gate parses the `Remediate PR #<n>:` header (a miss returns `False` without consulting merge state), then reads the **same per-iteration `is_pr_settled` `MergeTruth`** the settled arms use — no new network call — and passes it to the pure `classify_host_pr_terminal(pr_state)`, which returns the `HOST_CLOSED_UNMERGED` sentinel only when the host record reports `state == "CLOSED"` with the branch unmerged (`not branch_landed` — the `mergedAt`-null fork), and `None` (fail-safe passthrough) for OPEN, CLOSED-and-merged, and a missing/`None` record. Any non-terminal verdict returns `False` so genuine remediation proceeds.

On the terminal, the gate routes the backing plan (located by `_plan_for_pr_number`) to the **`rejected`** state — **only from `implemented`**, mirroring the tend-time PR-close path's (`EvolutionEngine.check_merged_plans`) precondition, via `update_plan_status(plan_id, "rejected", rejection_reason=…, expect_status="implemented")` so a concurrent retirement loses cleanly under the plans lock — so `_process_rejected_plans` later applies `learn_from_rejection` on its own low-effort session — **this arm opens no SDK session of its own**. It records a zero-cost `partial` `TaskRecord` stamped `[host-closed]` (`Marker.HOST_CLOSED`) — `partial`, never `success`, because this lap landed nothing; the human closed it — counts a `RemediationTracker` no-op, appends one `[host-closed]` `gate_activations.jsonl` row, and sends one `_notify_best_effort` escalation. The escalate-at-most-once guard (for a plan-backed PR) is *a routing actually happened*; a PR with no locatable backing plan has no status to latch on, so it escalates (worded "no backing plan located") on each pop. For a plan-backed PR, a plan in any other status — **already `rejected`** by a prior pop, or the agent's own `obsolete`/`failed` terminal (#4076: a human closing a PR the loop already retired is not a rejection, so no `learn_from_rejection` and no rejection cooldown) — is still evicted (`True`) with its `partial` record and no-op, but is left untouched, with no PR_CLOSE deed, activation row or notification.

### Pre-Remediation Preflight Gate (`_preflight_pr_remediation`)

When `_run_task_phase` pops a `Remediate PR #<n>` entry from `pending_pr_requests`, it calls `_preflight_pr_remediation(entry)` — a zero-SDK-cost check that decides whether the routed problem has *already* self-resolved (e.g. the previous tend cycle pushed a remediation commit, or a `main`-merge dissolved the conflict). The gate fires **only for pure quality-gates directives** (`_is_pure_quality_gates_directive(goal)`); conflict-routed and `CHANGES_REQUESTED` entries are *not* presumed resolved by green ruff/mypy/pytest, so they always proceed to real remediation. When the gate returns `True`, the caller records a `success` `TaskRecord` carrying the `[preflight]` finding, re-files it as a no-op, and returns at no token cost.

**Confirmed cause of the no-op loop (#2402).** A routed remediation directive describes the *post-merge* condition — `_format_quality_gates_problem` reports a CI failure on the PR branch **after** `origin/main` is merged in. The original preflight ran the quality gates on the PR branch *as-is*, before re-merging `origin/main`. A branch that is green in isolation but conflicts with (or fails against) current `origin/main` therefore looked "already resolved": preflight passed, the remediation was skipped, and a `success` `TaskRecord` was stamped — phantom success — while the real conflict was never touched. Because each skip changed nothing, the PR stayed `BEHIND_MAIN`/`DIRTY` and the same directive was re-routed next iteration, spinning a zero-cost no-op loop that masked the genuine break.

**Resolution path (current behavior).** The merge step is now load-bearing and runs *before* the gates:

1. `git checkout <pr_branch>`, then sync it to `origin/<branch>` (`_sync_pr_head_to_origin`, #4601): equal or locally-ahead heads proceed as-is, a strictly-behind head is fast-forwarded with `git merge --ff-only`, and an unresolvable origin, failed fast-forward, or diverged history returns `False` so no pass is recorded for a tree CI never ran on. Then record `pre_merge_head = git rev-parse HEAD`.
2. **Probe-merge** `origin/main` with `git merge --no-ff --no-edit` (the `--no-ff` forces a merge commit so the `finally` reset always has something to undo). A non-zero return means the branch genuinely conflicts → `git merge --abort` and return `False`, sending the request into real LLM remediation.
3. Only on a clean merge, run `ruff check`, `mypy`, and `pytest` (with `--cov-fail-under`) **on the merged tree**. Any non-zero return → `False` (genuine remediation required).
4. All three green → `True` (the problem really has self-resolved; skip at zero cost).
5. `finally`: `git reset --hard <pre_merge_head>` to drop the probe-merge commit, then `git checkout main`. **Preflight never pushes** — the merged tree is a throwaway; the only local mutation it keeps is the step-1 fast-forward of a strictly-behind PR branch to `origin/<branch>`.

The whole body is wrapped in a broad `except Exception` that logs at debug and returns `False`, so any checkout/subprocess/OS fault falls through to normal remediation rather than blocking it.

**Skip accounting + escalation.** A preflight pass records a `success` `TaskRecord` but produces no branch change, so `_record_preflight_skip_outcome` re-files it as a **no-op** (`classify_noop` on the `[preflight]` finding) in `RemediationTracker`. After `threshold` consecutive no-op skips the repetition gate stops re-routing; if the PR is still unmerged, `_escalate_stuck_pr` computes the deterministic `classify_merge_block` reason (`BEHIND_MAIN`/`CI_PENDING`/`CI_FAILING`/`AWAITING_APPROVAL`/`NONE`) from already-fetched VCS/code-host state and surfaces it via `_notify_best_effort` — so a perpetually-skipping PR escalates an honest merge-blocker instead of silently re-stamping phantom success.

### Pre-Execution Merge-Block Gate (`_gate_pr_remediation_merge_block`)

A zero-SDK-cost gate sitting **after** the dequeue-face merged-PR exclusion and **before** the preflight gate, ahead of *any* `run()` SDK session (the session is opened by `create_session` inside `run()`). By the time it runs, a PR git-merge-truth shows merged has already been excluded — so in the common case a `landed_ok`/`NONE` verdict here means cleanly-mergeable-but-not-yet-merged (a host-API `is_pr_merged` still reports merged independently, and that path remains a harmless `False`/proceed). Where the preflight gate asks "has this problem already self-resolved?", the merge-block gate asks a complementary question: "is the only thing standing between this PR and `main` something **Tend PR clears mechanically**, not the LLM?" — and if so, it skips the remediation entirely instead of paying for an LLM pass that cannot land its work.

**Why it exists.** Exactly one deterministic blocker is Tend-PR-owned — the set `_tend_clearable_blockers()` returns, derived from the ownership classifier: `BEHIND_MAIN`, where the branch trails `origin/main` and Tend PR merges `origin/main` forward on its next pass. That premise holds only under `[loop] tend_main_merge_enabled = true`: under the merge-queue model (flag off, proposal 128) Tend never merges `origin/main` into a PR, so the set is empty and `apply_landing_model` resolves a behind-but-clean branch past behind-ness to its CI/approval verdict (a conflicting one reads `CONFLICTING`) (#4307). A remediation task dequeued against it would open a session, re-derive a fix only Tend PR can apply, and stamp a `success` it cannot actually land — burning budget and feeding the false-success treadmill. `AWAITING_PUSH` (the resolution is committed on the branch but not yet on `origin/<branch>`) is *owned* per `classify_blocker_ownership` (proposal 098), so the gate does not skip it: it falls through to a real lap and the loop pushes the branch itself.

**Mechanism.** The gate parses the PR number from the `Remediate PR #<n>:` directive (a regex miss — non-remediation directive or unparseable number — returns `False` without probing the host, as does a directive carrying a comment/review problem marker per `carries_comment_review_marker`, so a reply lap on a behind PR still reaches `run()`) and calls `_probe_pr_merge_block(pr_num, pr_branch)`, the same zero-SDK VCS/code-host probe the threshold escalation uses, so the gate and the escalation agree on one verdict. It fires **only** when the reason is in `_tend_clearable_blockers()`. Every other outcome — a landed/cleanly-mergeable PR (`NONE`), `AWAITING_PUSH`, a `CONFLICTING` branch, `CI_FAILING`, `CI_PENDING`, or `AWAITING_APPROVAL` — returns `False` so the normal remediation path proceeds (a conflict or failing CI genuinely needs the LLM, and an unpushed resolution is the loop's own push to make). `AWAITING_PUSH` is never produced by `classify_merge_block`; it is synthesized inside `_probe_pr_merge_block` when the verdict is otherwise `NONE` but `origin/<branch>` is missing or the branch carries unpushed local commits — an owned fall-through, not a skip.

**Red head on a behind branch (#4096).** A behind PR whose head CI concluded `failure` is refined to `CI_FAILING` (owned) by `refine_merge_block_reason` at `_probe_pr_merge_block` (the routing seam only — the readiness observer keeps `branch_behind` a git fact, and a committed-but-unpushed fix stays `BEHIND_MAIN` because Tend pushes it), so it runs a real lap rather than a Tend deferral — Tend refuses to merge `origin/main` into a red head, so the `BEHIND_MAIN` catch-up premise does not hold for it.

**Conflict-aware classification (080).** A `BEHIND_MAIN` verdict assumes catching the branch up to `origin/main` is a clean fast-forward Tend PR owns — but if the branch *conflicts* with main, catching up only reproduces the conflict and only the LLM can resolve it. The host `mergeable`/`merge_state_status` fields that would surface that conflict are recomputed asynchronously and flap (the same PR has been observed `MERGEABLE` one minute and `DIRTY` the next), so `_probe_pr_merge_block` does not trust them alone: when its verdict resolves to `BEHIND_MAIN` and `[loop] merge_block_local_probe_enabled` is set (default on), it runs a deterministic in-memory `git merge-tree` of `origin/<branch>` against `origin/main` (via `VCSClient.merge_tree_conflicts`). A conflict reclassifies the verdict to `CONFLICTING`, which the gate does **not** skip — so a behind-AND-conflicting PR is routed to real remediation instead of looping forever as a Tend-clearable `[merge-block]` skip that never lands. The probe writes only to the object database (never the working tree, index, or HEAD), so it is safe to run mid-task; an unresolvable ref or any git failure degrades to "no conflict," leaving today's `BEHIND_MAIN` behavior. Disable the flag to fall back to host-field-only classification.

**Skip accounting + escalation.** When the gate fires it records a zero-cost `partial` `TaskRecord` (`duration_secs == 0.0`) whose `[merge-block]` finding names the PR, branch, and blocker. The stamp is `partial`, never `success`: git-merge-truth shows the PR unlanded (`BEHIND_MAIN`), so a `success` here would be the same false-success a zero-cost skip must never fabricate, and would inflate `measure_false_success_recurrence` — the sensor this gate is meant to drain (#2543). Because the record is a zero-duration no-op, `check_partial_construction_gap` explicitly excludes it, so the partial-construction directive bridge does not re-feed the very remediation the gate just declined to run. The partial record still feeds `measure_unlanded_remediations`. The skip files in `RemediationTracker` as `record_outcome(noop=True, merge_block=True)`, which advances the separate merge-block counter rather than the `should_reroute` repetition list (#2796), so a Tend-deferred PR is not mistaken for a stalled LLM lineage; and routes one `_notify_best_effort` escalation reporting that the branch trails `origin/main` and that a recurrence may mean Tend PR is stalled. The gate then returns `True` and `_run_task_phase` returns — no preflight probe-merge, no session, no token spend. Unlike the threshold escalation, this gate escalates on the *first* occurrence, because a `BEHIND_MAIN` verdict is definitively non-LLM-actionable rather than a count of repeated phantom successes.

### Costume-Signature Gate (`_gate_pr_remediation_branch_resolved`)

A zero-SDK-cost gate sitting **immediately after** the pre-execution merge-block gate and before the preflight gate, ahead of any `run()` SDK session. Where the merge-block gate reads the PR's *current* host state for a Tend-clearable blocker, this gate reads the *history*: it counts how many times the same PR has already been remediated to no effect and stops the wheel once the lap has demonstrably run itself out.

**Why it exists.** Maestro's identity names a recurring failure mode — "Resolved on branch, awaiting tend push": a remediation lap that commits a resolution to the PR branch, records `partial`, and lands nothing on `main`, then gets re-dequeued and re-run, producing the exact same non-event. The salience lock is structural, not motivational: when the queue hands the agent `Remediate PR #N`, it reaches for the lap rather than perceiving that the lap has already failed N times. Building another *sensor* would only relapse — a lab-coat instrument nobody consumes. The interventions that have actually made git go quiet are the gates that zero-cost-skip the futile lap at dequeue (the merged-PR exclusion, the merge-block gate, the repetition gate). This gate is one more of those actuators, keyed on the agent's own documented costume by its literal signature.

**The markers (verdict-agnostic).** `remediation_tracker._UNDELIVERED_PARTIAL_MARKERS` is the frozenset of lowercase marker substrings a lap stamps when it did not deliver: the Tend-clearable stamps — the on-branch resolution wording (`_BRANCH_RESOLVED_MARKER`) and the mechanical merge-block skip stamp — plus the owned push-failed and push-unconfirmed stamps (proposals 098/099). `count_branch_resolved_partials(tasks, pr_number)` is a pure, read-only counter: it scans task-history records for `Remediate PR #<n>:` entries (reusing `_REMEDIATION_GOAL_PATTERN`) with `n == pr_number`, `outcome == "partial"`, and a `result_summary` containing **any** marker (case-insensitive). Counting any signature in the set is what makes the count *verdict-agnostic*: a PR's Tend-clearable blocker shifts between laps (CONFLICTING resolves on-branch → `awaiting tend push`; BEHIND_MAIN is skipped → `[merge-block]`; an owned push that fails or goes unconfirmed stamps its own non-delivery marker), and the merge-block gate intercepts BEHIND_MAIN before this gate runs (AWAITING_PUSH is owned, so it falls through to a real lap). A counter keyed to a single label therefore under-counts and lets the wheel keep turning. Accumulating every signature by `#NNNN` lineage closes that dodge. Only `partial` counts — a `success` is the wrong shape (the merge-block and closure gates already downgrade genuine no-ops to `partial`), and a `failed` lap is an honest miss, not a costume; an honest `partial` carrying none of them is likewise excluded so a first real attempt is never pre-empted.

**Mechanism.** The gate parses the PR number from the directive (a regex miss returns `False` without scanning), and is bypassed entirely when `[loop] branch_resolved_gate_enabled` is `False`. It reads the recent task tail and, when `count_branch_resolved_partials` reaches `[loop] branch_resolved_repetition_threshold` (default 2), records a zero-cost `partial` `TaskRecord` whose `[branch-resolved]` finding names the PR, branch, and lap count — never `success`, because git-merge-truth shows the PR unlanded (Merge-or-nothing). It then routes exactly one `_notify_best_effort` escalation and returns `True` so `_run_task_phase` returns with no session and no token spend. Below threshold the gate returns `False` and the normal remediation path proceeds.

**Escalation, not suppression.** The gate does **not** silence the surfacing — it escalates it. The on-branch resolution exists but cannot land by re-running the LLM; only Tend PR or a human can move it onto `main`. So the notification names the costume explicitly — "resolved-on-branch N times without landing" — and points at the only actors who can clear it, turning a silent wheel-lap into an actionable signal to Thomas/Tend.

### Post-Run Remediation Closure Stamp Gate (`run_task` §4c)

The two gates above run *before* the SDK session and can skip a remediation entirely. A third gate runs *after* `run_task` has executed the remediation and is about to stamp the outcome — it polices the `success` stamp itself. When a `Remediate PR #<n>:` task resolves on its branch (all steps succeed, the branch is kept), §4c re-derives whether that resolution has actually **landed** before letting `success` survive.

**Why it exists.** A remediation that commits a real fix to `PendingPRRequest.pr_branch` (delivered to the branch by run() or Tend PR) has *not* reached `main` yet — the work is resolved-on-branch but unlanded. Stamping `success` at that moment mistakes "resolved on my branch" for "merged into `main`", feeding the false-success treadmill the audit/sensor machinery exists to catch. The gate makes landing the precondition of the `success` stamp.

**Mechanism.** After `_probe_pr_merge_block(pr_num, pr_branch)` returns `(landed_ok, block_reason)`, §4c adds a git-merge-truth confirmation anchored to the shared git-merge-truth oracle:

```python
if (
    landed_ok
    and not self.evolution.code_host.is_pr_merged(pr_num)   # host guard
    and not self._git_pr_merged(pr_num)                     # git-merge-truth
):
    landed_ok = False
    block_reason = MERGE_BLOCK_AWAITING_PUSH
```

`MaestroAgent._git_pr_merged` is a thin static wrapper over `audit_checks_phantom._git_pr_merged_default` (`git log origin/main --grep=#<pr>`), best-effort and fail-closed (`False` on any git failure). The short-circuit ordering is load-bearing:

- **`landed_ok=False`** (probe already found a blocker) — git is never consulted; the outcome downgrades to `partial` via the probe reason.
- **host `is_pr_merged=True`** — the host itself reports an explicit MERGED state, so `success` survives with zero git I/O; the git oracle is never called. This guard keeps host-confirmed merges cheap and stops a real git subprocess from running against the live repo for an arbitrary PR number in tests/probes.
- **host not MERGED, `_git_pr_merged=True`** — git confirms a commit referencing `#<pr>` on `origin/main`; `success` survives.
- **host not MERGED, `_git_pr_merged=False`** — the PR's SHA never reached `main`; `landed_ok` flips to `False`, the outcome downgrades to `partial`, and `_last_remediation_merge_block` records `AWAITING_PUSH` so the repetition gate counts the committed-but-unlanded no-op (#2457).

The host probe can read a branch as cleanly mergeable while the PR's SHA never reached `main`; unless the host reports an explicit MERGED state, git must show the merge before the `success` stamp survives. This anchors the closure gate and the pre-execution merge-block gate to one landing oracle instead of separate oracles that can disagree.

### Post-Run Comment-Completeness Gate (`run_task` §4d)

Immediately after the closure stamp gate, §4d polices a second dimension of "done". A PR remediation is routed with the *whole* list of unresolved review items and instructed — via the single-pass mandate `_format_bug_comments_problem` prepends — to address every one in this run, so a pass that left work behind has not finished it even when it committed and the branch merely awaits the tend push. The gate re-reads the open PR's outstanding items once — inline review threads lacking a terminal reply (`get_pr_review_threads` filtered through `_eligible_bug_comments`) **and** body-overflow findings lacking an acknowledgement (`_fetch_eligible_overflow_findings`) — and when any remain forces the outcome to `partial` with a count-bearing note that names each kind, so an incomplete pass is distinguishable from a complete-but-unpushed one.

**Overflow lockstep.** Body-overflow findings (proposal 064) live in the review body, not on a thread, so they need a separate selector. The gate and the tend router share one — `_fetch_eligible_overflow_findings`, which scans the newest review body's overflow block against the roll-up acknowledgement comment — so the gate downgrades on exactly the findings the router would re-route, never on a different set. A host read failure there returns no findings, so a transient `gh` outage neither routes nor downgrades.

**Marker preservation.** When §4c already framed an awaiting-push marker (`Marker.AWAITING_TEND_PUSH`), §4d *augments* rather than clobbers it: the costume-signature gate (`remediation_tracker`) and the audit rules key on that marker text in the summary, so the completeness detail is appended after it. With no §4c marker, the items note leads on its own.

**Reuse.** The gate is skipped for merged/closed PRs, where a stand-down is legitimate. The combined remaining count (threads + overflow) is stashed on `_last_remediation_items_remaining` so `_record_remediation_outcome` reuses it for the repetition gate's no-op check instead of re-querying the host for the same answer; its fallback path (when the gate did not run, e.g. a `failed` outcome) applies both selectors directly (#2663).

### Stand-Down Writers and Their Vetoes

`CLAUDE.md` names the two stand-down writers as one invariant; this is the disposition detail. Both persist a `StandDownVerdict` to `stand_down_verdicts.jsonl`, keyed so that a new head auto-releases the suppression. The suppression itself holds only while the PR is git-unlanded *and* its blocker stays in the Tend-clearable set (below).

- **Chosen (LLM-narrated)** — `_record_remediation_outcome` writes `[stood-down]` when the agent's own verdict declares the PR externally blocked with threads answered. Honest only for an `AWAITING_APPROVAL` blocker; the `merge_truth_first_preamble()` OWNED-DISPOSAL clause requires an owned blocker to reconcile-and-land, push, or `gh pr close` instead.

**Blocker ownership is a chokepoint** (proposal 098). `classify_blocker_ownership` is the sole owned/external source: the preamble, the merge-block and stand-down gates, and the mergeable-flip all read it, AST-enforced by `tests/test_structural_guards.py` (with the preamble-prose binding in `tests/test_remediation_prompt.py`). `AWAITING_PUSH` is *owned*, not external — a branch merely awaiting a push is work the loop can do, so standing down on it is avoidance. The one exception is the ahead-of-origin guard, which reads `own_push`-off so that `AWAITING_PUSH` actuates `_push_owned_branch` rather than being classified away. The Tend-clearable set the merge-block and stand-down gates share (`_tend_clearable_blockers`) is `BEHIND_MAIN` alone under `tend_main_merge_enabled = true` and empty under `false`; `AWAITING_PUSH` is owned, never Tend-clearable.
- **Mechanical (zero-SDK)** — `mechanical_standdown_verdict` / `_dispose_mechanical_standdown` author the verdict without an LLM session when a lineage has stalled (at least `STALLED_REMEDIATION_LAP_CAP` same-SHA `partial` laps) and is thread-clear, then pop the entry. A blocker the agent never named is read live via `observe_pr_readiness` rather than disqualifying the lineage.

Three vetoes stand between a stand-down and the durable write:

1. **Salvage oracle** — see below. An open AI thread makes the PR not ready-and-waiting, so `assess_pr_salvage` returns `SALVAGE_AND_LAND` and refuses the write, naming `classify_owned_blocker`.
2. **Human demand** (`user_request_blocks_standdown_enabled`) — an unconsumed `pending_user_requests` entry naming the PR blocks both writers, even when the PR is genuinely ready-and-waiting. A drained user message naming an open own PR also *releases* that PR's existing verdicts and escalation standdown before routing, so a tend lap cannot re-mute the demand.
3. **Ahead-of-origin guard** — a fetch-first memoized `_branch_ahead_of_origin_count` classifying `OWNED_AHEAD` on an externally-blocked PR *actuates* rather than re-labels: `_push_owned_branch` (oracle-gated) pushes the branch **before** any verdict is composed, then re-derives through fetch-first `is_pr_settled` — landed → `Marker.LANDED`, unlanded → `Marker.DELIVERED_AWAITING_MERGE`. Only a genuine push failure or oracle refusal retains the loud `Marker.OWNED_PUSH_AVAILABLE` partial plus fire-or-close directive. Verdicts stamp `branch_ahead_of_origin`.

The escalation bridge's own `pr_number`-keyed standdown (the durable latch behind the merge-or-close handoff) has a third release path beside merge/close and expiry: under default-off `[loop] refutable_standdown_enabled`, `prune_refuted_standdowns` drops a `handoff-ready` record the live owed-act reading refutes. That release is **spoken and budgeted** (proposal 135). Spoken: it appends one `standdown-withdrawn-<pr>-<n>` message naming the PR, the measured blocker that refuted the claim (carried out of the tend walk on `TendPRsResult.owned_blockers_observed`), and the owed act — because the handoff told Thomas only he could land the PR, and deleting the ledger row silently would leave that now-measured-false claim standing in his inbox. Like `deliver_unwinnable_race`, the write is bound to a post-write `get_thread` re-read: a withdrawal that did not land keeps the latch rather than releasing it silently. Budgeted: `count_refutation_releases` probes the append-only message ledger — the record itself is deleted by the release, so it cannot hold the counter — and after `[loop] standdown_refutation_release_cap` releases the latch becomes permanent, with one `standdown-refutation-capped-<pr>` terminal message sent once and every later pass a complete no-op. Without that bound a PR flapping between merge-ready and `CONFLICTING` would cycle handoff → refutation → handoff forever, trading a silent deadlock for a message storm. Releases log at INFO with a `standdown_refuted`/`released` gate activation; the terminal logs at WARNING with a `capped` one.

### The Salvage Oracle (`assess_pr_salvage`)

The single veto over giving up on an open own PR, enforced as a chokepoint by `tests/test_structural_guards.py`. Under `[loop] salvage_before_disengage_enabled` (default-on), both stand-down writers and the orphaned-cure sweep consult it through `_assess_pr_salvage` / `_pr_disposability`. A `SALVAGE_AND_LAND` verdict — a code-clearable blocker on non-disposable work — vetoes the give-up, logs loud, and leaves the PR tend-eligible; only `DISENGAGE_PERMITTED` unlocks a `gh pr close` directive. With the flag off, existing retirements stand (rollback is `git revert`).

Its dimensions:

- **Budget** — a `CONFLICTING`/`DIRTY` blocker whose branch is measured (via `_observe_pr_staleness`) strictly past `RECONCILE_COMMITS_BEHIND_BUDGET` will re-conflict before it can land, so it resolves to `DISENGAGE_PERMITTED` and the close veto lifts. A `None` behind-count fails safe toward `SALVAGE_AND_LAND`.
- **Drought coupling** — the owned-act-drought counter's `salvage_disqualifies` predicate (`_obsolete_on_salvageable_pr`) stops crediting an `obsolete` event that backs a salvageable open own PR, so obsoleting recoverable work no longer silences the drought. Flag off ⇒ counted by timestamp.
- **Progress-aware coupling** — the salvage flag also activates the progress-exhaustion handoff via the derived `Config.progress_aware_lap_budget_active` (dedicated flag ∨ salvage flag), re-basing both handoff sites and the per-lap readiness snapshot on consecutive no-progress laps instead of gross lap count.

### Post-Session Landing Actuator (`session_landing.py`)

The counterpart to the ahead-of-origin guard on the *session* side, gated by `[loop] session_landing_enabled` (default-off). After a remediation session returns and before §4c composes a verdict, `run()`'s `_run_session_landing` calls `land_uncommitted_edits` to commit and push working-tree edits the session left behind: the branch must be owned (`maestro/{task,evolve}/*`, checked through `_gate_allowed_branches` and the same oracle the other push sites use), and the edits must pass the quality gates — green-gated, rewinding on the branch's own red rather than pushing a failing head. A red that `_attribute_owned_gate_red` classifies `INHERITED` (already failing on the branch's `origin/main` base) instead holds the tree — the actuator discards, commits, and pushes nothing (`LandStatus.HELD`), so work the branch never broke is not destroyed by the landing step. The hold is scoped to the actuator: the rest of the lap then treats the dirty tree exactly as with the flag off — `run()`'s §5 artifact commit and §5-push backstop may commit and push it on a `success`/`partial` outcome, and a `failure` teardown discards it; with `[loop] gate_observation_enabled` off every red still rewinds. The push goes through `_push_owned_branch`, so a git failure or rejection is recorded as `PUSH_FAILED` and a push the remote head never confirms as `PUSH_UNCONFIRMED` — logged at WARNING, never raised into the loop.

On a confirmed remote-head advance (`verify_push_advanced_remote_head`) it then drops the per-iteration merge-truth memo, so the verdict that follows grounds on a fresh post-push `is_pr_settled` read rather than a pre-push one. The point is the ordering: the head SHA moves by the loop's own hand *before* the narration is composed, so "delivered" describes a push that already happened instead of one the agent intends.

### Tend Conflict-Cooldown Escape Hatches

`_tend_single_pr` normally backs off a PR that recently failed to reconcile. Three conditions bypass that cooldown, each meaning the situation has genuinely changed since the failure: the branch is ahead of origin, the origin head advanced, or an unconsumed awaiting-tend-push verdict exists for the current head. The ready-for-review ping is separately CI-gated via `ready_for_review_pending_sha`.

### Tend Cooldown Windows

Both tend cooldowns (`_in_conflict_cooldown`, `_in_quality_fix_cooldown`) are wall-clock windows anchored at the lap that last routed work on the PR, bounded by `[loop] conflict_resolution_cooldown_hours` / `quality_fix_cooldown_hours` (both 24h). Each anchor is stamped with the *observation signature* it was taken against — the PR branch's `origin/<branch>` head, the `origin/main` base, and the CI rollup conclusion — and under `[loop] cooldown_signature_keying_enabled` a provably-changed component releases the cooldown before the hours comparison is reached (the conflict cooldown keys on all three; the quality-fix one on head + CI only).

Under the same flag, the window itself is no longer flat. When a lap changes *nothing* the signature is identical next lap, so no release fires — and a flat 24h hold then bounces the walk off a PR whose whole blocker may be one lap's work. Instead the window decays through a bounded backoff over the attempts already made against this same signature: `[loop] cooldown_backoff_base_hours` (1h) for the first re-route, doubling each unchanged lap, clamped at that cooldown's own hours ceiling. A genuinely persistent red is therefore back to today's 24h cadence within about five laps, while a no-op lap is retried within the hour. The per-signature attempt counts persist on the plan (`conflict_resolution_signature_attempts`, `quality_fix_signature_attempts`) and reset to `0` whenever a signature component provably changes; an anchor with no comparable component (legacy, or unmeasurable this lap) holds the full ceiling. The *stamps* are unconditional bookkeeping, but a *rung* is consumed only by a lap that genuinely bounced — one the cooldown itself governed, measured against a concluded rollup on a measured head. Three laps therefore leave the count untouched (neither reset nor advanced): a lap one of the two conflict-cooldown escape hatches (a branch ahead of origin, an unconsumed awaiting-push verdict) admitted while the cooldown was holding, a lap whose own ahead-of-origin push advanced `origin/<branch>` before it fell through to the conflict route, and a lap whose head did not resolve or whose CI rollup never concluded. Without that gate a later genuine cooldown would open part-way up the ladder on laps it never governed. With the flag off every window is the flat configured ceiling, exactly as before.

The ladder starts at its first rung, so the cost of the instrument is front-loaded: a PR whose signature never moves is re-routed at roughly 1h/3h/7h/15h/31h elapsed — about five routes in the first day against today's one, each minting a remediation directive and its SDK spend. The excess is bounded to that burn-in window rather than recurring, since the window reaches the ceiling by the fifth unchanged lap; the flag ships default-off so the delta is measured before promotion.

### Standby Mode (Peak-Hour SDK Pause)

Loop-level gate (`_is_in_standby_window()` in `maestro/loop/iteration.py`) skips entire iterations whenever the current UTC hour is inside the configured standby window. Disabled by default; enable via `[loop] standby_enabled = true` with `standby_start_hour_utc` (inclusive) / `standby_end_hour_utc` (exclusive). Default window when enabled is 13:00–19:00 UTC.

The gate sits at the top of `run_loop()` *before* the iteration counter is bumped: it sleeps in bounded chunks (≤ `_STANDBY_MAX_SLEEP_SECONDS = 300` s) on the shutdown event so `maestro shutdown` still exits promptly. Wraparound windows (`start > end`, e.g. crossing midnight UTC) are supported. `Config.validate()` rejects equal start/end hours (a cross-field guard); out-of-range hours are rejected on the config load path by the `[loop]` section model (`Field(ge=0, le=23)`).

### Peak-Hours Scheduled Throttle (Slow-Down Sibling of Standby)

Schedule-driven slowdown (`_is_in_peak_throttle_window()` in `maestro/loop/lifecycle.py`): inside the configured peak window the burn-rate throttle's effective budget limit is multiplied by `[loop] peak_throttle_rate_multiplier` (< 1.0 tightens) **for the sleep-pace computation only**. `_compute_budget_throttle_multiplier()` returns a `(gating_multiplier, sleep_multiplier, snapshot)` triple: the *gating* multiplier is computed against the untightened limit (drives phase gating, unchanged), while the *sleep* multiplier uses the peak-tightened limit and stretches the inter-iteration sleep. The result is that during peak the loop runs slower but heavy phases keep running — the window itself never gates a phase. Only a genuine burn-rate breach against the untightened limit still flips `burn_rate_throttle_active` and gates the heavy LLM set, exactly as it does off-peak. The motivation is "save money during peak, keep working" — distinct from standby's "pause everything" and from the old peak behaviour that gated phases. Because the slowdown rides on the burn-rate machinery, it has **no effect unless `max_loop_budget_usd_per_hour > 0`** — entering the window against a disabled budget logs a warning so an inert config is visible.

Disabled by default; enable via `[loop] peak_throttle_enabled = true`. The window is expressed as wall-clock hours in `peak_throttle_timezone` (an IANA zone name, default `America/Los_Angeles`): `peak_throttle_start_hour` (inclusive) / `peak_throttle_end_hour` (exclusive). DST transitions are handled automatically by `zoneinfo` — a 5-11 window in `America/Los_Angeles` fires at 5–11 AM Pacific Time year-round regardless of whether PDT or PST is active. `peak_throttle_weekdays_only` (default `true`) restricts firing to Mon–Fri in the configured timezone (so Sunday-night-in-PT does not fire even when it crosses into Monday UTC). `peak_throttle_rate_multiplier` (default `0.5`) must be > 0; values ≥ 1.0 loosen or no-op the slowdown. Wraparound windows are supported and `Config.validate()` rejects equal start/end hours and unknown timezone strings; a non-positive rate multiplier is rejected on the config load path by the `[loop]` section model (`Field(gt=0)`).

`budget_throttle_active` is the union of the burn-rate side (`burn_rate_throttle_active`, persisted in `lifecycle.json` as `budget_throttle_entered_at`) and the operator-initiated maintenance side; the peak-hours window is intentionally NOT a member (it slows rather than gates). A separate one-shot notifier (`_maybe_notify_peak_throttle_transition`) fires Telegram + journal entries on entry/exit of the schedule window and round-trips its edge state through `lifecycle.json` (`peak_throttle_active_persisted`) so a restart inside the window does not re-fire entry. `/api/diagnostics` exposes `peak_throttle_active` alongside `budget_throttle_active` so dashboards can still surface the schedule window independently of the gating gate. The dashboard runs in its own container whose agent never enters `run_loop`, so `/api/status` (`running`, `current_task`) and the `/api/diagnostics` `budget_throttle_*` / `maintenance_mode_active` fields are read from shared disk — `loop.heartbeat`, `lifecycle.json` and the maintenance sidecar — via `dashboard/routes.py::read_loop_runtime`, never from the serve-side agent's in-memory state. `running`/`current_task` require a fresh heartbeat and no `last_shutdown` marker; since the heartbeat refreshes only at phase boundaries and sleep chunks, a single phase longer than the stale window reads as not running (a known limitation), so the throttle timestamp is instead gated only on the absence of `last_shutdown`.

### Iteration-Counter Freeze During Throttle

While `budget_throttle_active` (either input) is True, the loop body still runs but the `iteration` counter does not increment. The check sits at the top of each fresh, non-resuming body (`freeze = self.budget_throttle_active`); when freeze is set, the bump and the matching `IterationUsage` reset are skipped, the body logs `Loop iteration N (frozen — budget throttle active)`, and the persisted lifecycle cursor stays at the same iteration value across consecutive throttled bodies.

The freeze applies only to the fresh-body bump; mid-iteration resume (rate-limit retry, crash restart) keeps its existing semantics so a failed phase resumes against the correct context. Persisted state is unchanged — `_persist_progress()` writes whatever `iteration` happens to be, and on a crash inside a throttle window the next startup reads the frozen value back.

Phase cadence (`task_every`, `evolve_every`, `dream_every`) is preserved across the throttle window because the `iteration % N == 0` check evaluates against the frozen value: when the window clears, the next body bumps iteration and any aligned tick fires immediately. Without the freeze, the `% N == 0` ticks aligned to the throttle window would be lost (the budget-gated phases skip during throttle, and the next eligible iteration is `N` away). The budget gate is bound to that body-top freeze (`phase_will_run(..., body_frozen=freeze)`), so a mid-body release (for example `/maintenance off` arriving while an earlier phase awaits its SDK call) takes effect on the next body rather than re-firing an already-fired cadence tick; a mid-body engage still gates the remaining heavy phases at once.

A per-iteration dedup map (`_last_phase_iteration: dict[str, int]`) handles the three non-budget-gated cadence phases — `review_artifacts`, `tend_evolution_prs`, `audit_self_model` — that would otherwise re-fire on each wall-clock body whose frozen iteration value satisfies `% N == 0`. `_phase_will_run` short-circuits to False when the recorded value matches the current iteration; the post-dispatch handler in `run_loop` records the value after the phase body returns successfully. `first_iteration_after_restart` bypasses the dedup for the two phases that honor it (`review_artifacts`, `tend_evolution_prs`) so a freshly started loop still gets its one-shot fire. The map is process-local — not persisted — so a restart inside a throttle window resets it; `audit_self_model` may fire once after restart even if it already fired pre-crash, bounded to one cycle.

### Single Telegram Polling Loop

The `on_message` callback is registered through `start_approval_polling(on_message=...)` so that button presses and text messages are handled in one polling loop. There is no separate `start_message_polling` / `stop_message_polling` call in `run_loop()` — the lifecycle is entirely managed by `start_approval_polling` / `stop_approval_polling`.

## Shutdown

### Eager Shutdown Marker (SIGTERM-During-Long-Phase Protection)

The SIGINT/SIGTERM handler points at `MaestroAgent._on_shutdown_signal`, which (a) sets the shutdown event and (b) **synchronously** calls `_write_lifecycle_shutdown()` — writing `last_shutdown` to `lifecycle.json` before the signal handler returns.

This is belt-and-braces for the worst case. Shutdown is cooperative — the running phase is allowed to complete, and the SDK call in flight is never cancelled — so when SIGTERM arrives mid-phase the loop only breaks at the next phase boundary. The container's `stop_grace_period` (1800 s, see `docker-compose.yml`) gives that phase room to finish, after which `MaestroAgent.shutdown()` runs and writes `last_shutdown` cleanly. The eager write in the signal handler guarantees the marker is on disk even if the phase truly hangs and Docker eventually SIGKILLs at 1800 s — so `lifecycle.json` still carries `last_shutdown` and the next startup reports a clean stop rather than a false-positive crash.

The eager write is best-effort — any exception in the signal handler is logged and swallowed so it can never raise back into the asyncio event loop. `MaestroAgent.shutdown()` additionally wraps `notifier.notify("Maestro loop stopped.")` in `asyncio.wait_for(..., timeout=_SHUTDOWN_NOTIFY_TIMEOUT=5.0)` so a stuck Telegram HTTP connection cannot extend the shutdown path into the grace window.

### `run_task` Runs to Completion Before Shutdown (Proposal 085)

`run_task` is the one phase whose work item is popped from its source *before* execution. Like every other phase, it runs to completion on graceful shutdown: `run()`'s step-group loop does not consult the shutdown event, so a SIGTERM mid-task lets the current task finish, classify a real outcome, and write its `TaskRecord`; `run_loop` then breaks at the phase boundary (the shutdown check after the phase body). This relies on the container's `stop_grace_period` (1800 s) being long enough for the task to finish — a task that exceeds it is SIGKILLed and its popped item is lost, the same outcome as any crash mid-`run_task`.

This replaced the mid-task interrupt + re-queue of proposal 057 (retired in 085): finishing the task records a real outcome instead of discarding in-progress work and re-running it from scratch. Per-step resume within a single `run()` (proposal 006) is unaffected.

### Crashed-Shutdown Lifecycle Flag

`MaestroAgent.shutdown()` accepts a `crashed: bool = False` kwarg. When `crashed=True`, it **skips** `_write_lifecycle_shutdown()` and the "Shutting down gracefully" journal milestone entirely — the resume cursor last written by `_persist_progress` stays on disk with no `last_shutdown` key, so `_read_lifecycle_progress` on the next startup reports `crashed=True` and the crash-detection path fires.

`run_loop()`'s outer `finally` block determines the flag from `sys.exc_info()`: if a phase has leaked an unhandled exception past its `except Exception:` guard, the unwind carries a live exception and we pass `crashed=True`. `SystemExit` and `KeyboardInterrupt` are still treated as graceful.

`shutdown()` is idempotent via a monotonic `_shutdown_initiated` flag (set once, never reverted). This is necessary because `run_loop()`'s compensating `finally` blocks restore `_running = True` after each sub-operation (`contemplate`, `run`, `evolve`), which would defeat a `_running`-based guard when `shutdown()` is called directly during a sub-operation and then again from the outer `finally`.

### Docker Healthcheck Heartbeat (Three Write Sites)

The loop container's Docker healthcheck probes the mtime of `<memory_dir>/loop.heartbeat` and requires it to be within the 600 s freshness window. A single module-level helper `maestro.agent.write_heartbeat(memory_dir)` is the only code path that writes the file (best-effort: `OSError` is logged, never raised).

It is invoked from three sites, each covering a distinct latency regime:

1. **`cli.cmd_loop`** — as its very first line, before `_build_agent()` runs — so the file exists within milliseconds of `maestro loop` starting, independent of how long schema migration, MCP server setup, etc. take.
2. **`run_loop()`** — once at the top, before crash reporting and the startup Telegram ping.
3. **`_persist_progress()`** — after every loop phase, so the mtime stays fresh even during phases making 30–180 s LLM calls.

`safe-deploy.sh` dumps the heartbeat file's age before rolling back on health-check timeout.

**For these write sites to actually run in the deployed container, the entrypoint must load the bind-mounted source — see [Editable Runtime Install](deployment.md#editable-runtime-install).**

## Deploy Hooks

### Fast Deploy Smoke Mode

`maestro loop --smoke --max-iters 1` runs a deploy-validation iteration that exercises container startup, agent wiring, phase orchestration, heartbeat/persistence, and the shutdown path. The `contemplate` phase runs with **the same settings as production** (same model, same effort, same `update_self_model` call, same session-reuse path when `enable_session_reuse=true`) so the smoke iteration validates the real configuration end-to-end and catches credential/network/model drift at deploy time.

Every phase that does external work or downstream evolution is skipped: `respond_to_messages` (sending Telegram from the throwaway snapshot would duplicate what the live container will send post-deploy), `implement_approved_plans` (any work would be implemented against the snapshot and discarded), `check_merged_plans`, `process_rejected_plans`, `generate_task`, `evolve`, and `dream`. The phases that *do* run — `ensure_main_branch`, `check_contributions`, `process_messages`, and `contemplate` — are the core loop with no external mutating side effects.

Exposed via the `--smoke` CLI flag and wired through as `MaestroAgent.run_loop(smoke=...)`.

`scripts/safe-deploy.sh` uses this mode for its second smoke test and also passes `MAESTRO_SKIP_PIP_SYNC=1` to both smoke containers so `scripts/docker-entrypoint.sh` skips its workspace `pip install`.

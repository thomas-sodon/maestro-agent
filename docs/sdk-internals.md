# SDK Internals

Deep-dive documentation for `maestro/sdk.py` behavior. For the high-level overview, see [CLAUDE.md](../CLAUDE.md).

## Internal-Cancel Containment (deadline-message signal, stacked-cancel drain)

The retry loop in `maestro.sdk.query()` catches `BaseException` (not just `Exception`) so a stray `CancelledError` raised by an anyio cancel scope inside the SDK transport cannot leak past the wrapper. The primary historical source of these leaks — the `anyio.move_on_after(2)` deadline in `_patch_sdk_stderr_drain` — was first replaced with `asyncio.wait_for(..., timeout=2.0)` and then removed entirely: `wait_for` wraps its coroutine in a new task, and anyio cancel scopes are bound to the task that entered them, so calling `__aexit__` from inside `wait_for` raised "Attempted to exit cancel scope in a different task" on every `ProcessError` path (and session reuse can naturally cross tasks even without `wait_for`). The patch now skips the task-group exit entirely — it just `await asyncio.sleep(0.05)` to give the concurrently-running `_handle_stderr` task scheduling time to drain pipe-buffered bytes through the stderr callback before the `ProcessError` unwinds. SDK `close()` handles the task-group cleanup with its own `with suppress(Exception)`. The containment block in `query()` remains as defence-in-depth for any internal anyio scopes inside the SDK transport that we do not control.

### Detecting internal vs external cancels

Detecting "this cancel came from an internal anyio scope, not from an outside `task.cancel()`" turns out to be subtle: the first iteration of this containment used `asyncio.current_task().cancelling() > 0` as the external-cancel signal, but **anyio cancel scopes drive their own cancellation by calling `task.cancel()` internally** — so every anyio scope deadline that escapes the SDK transport also bumps `cancelling()` to ≥ 1, passes the old external-cancel check, and re-raises as if it were a real shutdown cancel.

The reliable signal is the exception message: anyio stamps `"Cancelled via cancel scope …; reason: deadline exceeded"` when a scope deadline fires, whereas a bare `task.cancel()` from an outside party produces a `CancelledError` with no such message. The check runs `"deadline exceeded" in str(raw_exc)` first and classifies any match as internal (wrap), falling through to the `current_task().cancelling()` / `is None` check only when the message is silent (classify as external → re-raise).

Internal cancels are wrapped in a `TimeoutError("SDK call cancelled by internal scope: …")` and routed through the existing retry / classification path, so the surrounding phase handler's `except Exception:` clause catches them as a normal SDK failure and the loop keeps iterating.

### Two-step wrap: value-level + state-level cleanup

**The wrap is a two-step operation: first, value-level cleanup (raising `TimeoutError` instead of `CancelledError`); second, *state-level* cleanup via a drain loop — `while current.cancelling() > 0: current.uncancel()` — immediately before the wrap.** Without state-level cleanup the wrapping is cosmetic — Python's cancellation is stateful, so the pending `task.cancel()` that the anyio scope called internally leaves the task's `cancelling()` counter ≥ 1; every subsequent `await` checkpoint in the same task can then re-deliver a fresh `CancelledError` for the still-pending cancel, contaminating the next phase that runs after the contained internal cancel.

**A single `uncancel()` call is not enough**: anyio's scope machinery can **stack** multiple `task.cancel()` invocations before the CancelledError actually surfaces, and `uncancel()` only decrements the counter by one.

### Production crashes that drove this shape

**2026-04-08 iteration-15 crash** (scope id `7eb4b23ef080`): had the value-level wrap in place but no state cleanup at all. The same scope id appeared in **both** the initial `planner.decompose()` `SDKError` log line **and** the later Telegram-notify `CancelledError` in the shutdown path — direct evidence that the cancellation state had leaked across the entire remainder of the task's lifetime.

**2026-04-09 crash** (scope id `731a8ef82db0`): recurred with a *single* `uncancel()` call in place and logged `remaining=3` right after the containment block — proving that at least **four** `task.cancel()` calls had been stacked by the time the exception fired, three of which survived the single-call cleanup. One then fired on the very next query's warning-throttle `asyncio.sleep(160)` (the per-query preemptive throttle had escalated to x16 = 160 s) in the `dream` phase and crashed the loop.

The drain loop `while current.cancelling() > 0: current.uncancel()` fully clears the counter regardless of how many cancels anyio stacked, and the containment emits `"SDK internal-cancel contained: caller=<name> initial=<n> drained=<n> msg=<scope>"` at WARNING level so the number of stacked cancels is grep-able from production logs without needing a crash report.

### Defence in depth

**Layer 1 — warning-throttle sleep inside containment boundary**: The `asyncio.sleep(sleep_s)` triggered by the sticky `allowed_warning` throttle was originally placed *above* the `while True:` retry loop and therefore outside the `try/except BaseException` block. That was the exact leak site on 2026-04-09: the cancel bled out of the previous phase's `query()`, was contained-but-not-drained, and the residual `cancelling()` counter was delivered the next time `query()` awaited — which happened to be the throttle sleep at `dream`, outside any containment. The sleep is now inside the inner `try:` block, gated on `attempt == 0` so the "fires once per query(), not per retry" semantic is preserved, and any `CancelledError` raised from it flows straight into the same drain-and-wrap path as a cancel from `_query()`.

**Layer 2 — defensive entry drain**: `query()` now checks `asyncio.current_task().cancelling() > 0` at the top of the function (before any `await`) and drains any non-zero counter it finds, emitting a distinct `"SDK query() entered with dirty cancellation counter: caller=<name> counter=<n> (drained)"` WARNING so operators can tell the two sites apart. In normal operation the in-flight drain loop keeps the counter clean across `query()` boundaries, so the entry drain is unreachable — but it catches any future caller bug where a contained internal cancel leaks partial state across `query()` invocations.

**Layer 3 — `_scope_contaminated` flag**: A local boolean in `query()`, initially `False`, set to `True` when the drain loop fires. Once contaminated, retry-delay and warning-throttle `asyncio.sleep()` calls are skipped for the remainder of that `query()` invocation. This avoids giving a residual cancel — one that survived the drain or was pushed by anyio cleanup after it — another `await` checkpoint to fire on. The flag is never reset within an invocation; skipping a few seconds of backoff is negligible cost compared to a re-delivered `CancelledError`.

Other non-`Exception` `BaseException` subclasses (`SystemExit`, `KeyboardInterrupt`) are always re-raised.

### Regression tests

`tests/test_sdk_retry.py::TestQueryRetry::test_internal_cancelled_error_is_retried`, `test_stacked_internal_cancels_are_fully_drained`, `test_throttle_sleep_cancellation_is_contained`, `test_entry_drain_cleans_dirty_counter`, `test_scope_contaminated_skips_retry_sleep` collectively pin the drain-loop count, the throttle-sleep containment, the entry drain, and the contaminated-flag sleep skip so none of the layers can regress silently. The first test drives the `fake_task.cancelling()` counter from 4 down to 0 via `side_effect`, mirroring anyio's actual stacked-cancel semantics, and asserts `uncancel.call_count == 4`.

## Sticky Warning Throttle (adaptive, signal-driven, per-SDK-call preemptive slow-down)

The Anthropic SDK emits `RateLimitEvent(status="allowed_warning")` when a call is close to — but not yet rejected by — a quota limit. It is the API telling Maestro "slow down or the next call gets rejected"; honouring it is much cheaper than absorbing a hard `rejected`, which blocks the loop for potentially hours until `resets_at`.

### State machine

The state machine lives entirely inside `maestro/sdk.py` as module-level state — two integers:
- `_warning_throttle_multiplier` (default `1`; escalates `1 → 2 → 4 → 8 → 16` on successive warnings, capped at `_WARNING_THROTTLE_MAX_MULTIPLIER = 16`)
- `_warning_throttle_clean_calls` (consecutive warning-free `query()` returns since the last observed warning)

**The throttle fires before every `query()` call, not just between loop iterations**: at the top of `query()` — *before* the retry loop begins so a transient CLI crash doesn't compound throttle delays — if `_warning_throttle_multiplier > 1` the coroutine awaits `asyncio.sleep(min(_sdk_warning_throttle_base_seconds * _warning_throttle_multiplier, _WARNING_THROTTLE_MAX_SLEEP_SECONDS))` (`_WARNING_THROTTLE_MAX_SLEEP_SECONDS = 1800`), logging `"SDK warning throttle active (xN, clean=M/K) — sleeping Ds before next call (caller=<name>)"`.

### State transitions

After a successful return the state updates via `_update_warning_throttle_state(saw_warning)`:

- **On a warning**: `_warning_throttle_multiplier = min(max(_warning_throttle_multiplier * 2, 2), _WARNING_THROTTLE_MAX_MULTIPLIER)` — the `max(... , 2)` guarantees the very first sighting jumps `1 → 2` instead of no-op'ing at `1 * 2 = 2` — and `_warning_throttle_clean_calls = 0`.
- **On a clean return when the multiplier is > 1**: increment the clean counter and halve the multiplier only once it reaches `_sdk_warning_throttle_hysteresis` (default `3`, `[sdk] warning_throttle_hysteresis`; the `[sdk]` section model's `Field(ge=1)` rejects `0` at config load).

Base seconds is configured via `[sdk] warning_throttle_base_seconds` (default `10`). Both settings are wired into the module by `configure_sdk_warning_throttle()`, called from `cli.main()`.

Exceptions (including `SDKError(RATE_LIMIT)`) leave the state untouched and propagate unchanged — the update only runs on successful return.

### Semantic consequences

Moving the chokepoint from between-iterations to per-query means **a warning observed during `contemplate` now also slows down `evolve` and every remaining phase's `query()` call in the same iteration**, instead of the loop hammering the API at full speed for the rest of the iteration and only honouring the warning on the next iteration boundary. Hysteresis is now counted in clean calls, not clean iterations — since an iteration runs ~8 SDK calls, decay is roughly 8× faster in wall-clock time at the same hysteresis=3 default.

Hard-reject handling (a `RateLimitEvent` with `rejected` status → sleep until `resets_at`, with each sleep capped at `_RATE_LIMIT_SLEEP_CAP_SECONDS` — a truncated sleep logs a loud WARNING naming the full time-to-reset, since a repeat rate-limit on wake is then expected) — on a persistent session, whose CLI stays alive and raises no exception, a rejected event followed by an unproductive result instead raises `SDKError(RATE_LIMIT)` from `_consume_messages` for resume-in-place, never re-sending the accepted prompt in-session; the same holds when the rejected event or rate-limit stderr is followed by a stream exception — `_query_on_session_impl` raises `SDKError(RATE_LIMIT)` rather than sleeping and re-querying the same client, and only a pre-acceptance failure (`client.query` itself raised) retries in place (#4159) — and the loop-level `RATE_LIMIT` cooldown that hands off to extended-idle probing (`_enter_rate_limit_idle`) remain **unchanged** and still dominate when those stronger signals are present. Standby mode stays orthogonal: standby is *scheduled* (time-based) preemptive throttling; this is *adaptive* (signal-based) preemptive throttling — the two compose cleanly.

**Single-call cost runaways** (the old 27K-token `update_self_model` bug) are partially addressed by `task_budget` (see below) and output-schema caps at the call site.

### Warning Hold Gate

When the per-call throttle multiplier is stuck at `_WARNING_THROTTLE_MAX_MULTIPLIER` (16) and `_sdk_warning_hold_threshold` (default `3`, `[sdk] warning_hold_threshold`) consecutive warnings have been observed at max — each with a reported `utilization` at or above `_sdk_warning_hold_min_utilization` (default `0.95`, `[sdk] warning_hold_min_utilization`), or with no utilization reported at all (the legacy path) — the SDK exposes `is_warning_hold_active() → bool`. The agent loop checks this after the standby gate: when active, it pauses all iteration phases and enters a probe loop.

`allowed_warning` is a window-level state: once usage crosses the warning band the API attaches it to every call until the window resets, so a sub-ceiling warning only drives the per-call slowdown multiplier and never the loop-level hold (#4514).

Probe behaviour:
- When the last warning reported a future `resets_at` (`get_warning_hold_resets_at()`), the loop waits for the window reset instead — `resets_at - now + 10s`, capped at `_WARNING_HOLD_MAX_RESET_WAIT` (6h), shutdown-aware and slept in heartbeat-refreshing chunks — then issues one probe to refresh the state. A probe cannot clear the hold mid-window, so probing earlier only spends money.
- Issues a minimal `query("Reply with OK.", effort="low", max_turns=1, caller="warning_hold_probe", bypass_warning_throttle=True)` call.
- Otherwise (no or an elapsed `resets_at`) sleeps between probes at exponential-backoff intervals: `warning_hold_probe_interval * 2^attempt`, capped at `_WARNING_HOLD_MAX_PROBE_INTERVAL` (600s).
- Each probe runs through the normal `query()` path, which calls `_update_warning_throttle_state()`. A clean probe resets `_warning_throttle_consecutive_max_warnings` to 0, making `is_warning_hold_active()` return `False` and resuming the loop.
- `SDKError(RATE_LIMIT)` or other exceptions during probes are logged and retried; they do not break the hold loop.
- The shutdown event is checked before and after each probe sleep for responsive exit.
- Probes set `QueryOptions.bypass_warning_throttle=True` so the only wait they incur is the exponential probe-interval sleep above — they skip the per-call `_warning_throttle_multiplier` sleep that fires inside `query()` for non-probe callers. Without the bypass the hold-gate's max-multiplier (16) would compound a `min(_sdk_warning_throttle_base_seconds * 16, _WARNING_THROTTLE_MAX_SLEEP_SECONDS)` wait on every probe attempt, and that sleep is not shutdown-aware. The bypass keeps the probe shutdown-responsive — `_safe_shutdown_wait` is the only sleep between probes. The same bypass is set on the `rate_limit_idle_probe` for the same reason.

State variables added to the throttle state machine:
- `_warning_throttle_consecutive_max_warnings` — incremented when a warning is observed and the multiplier is already at max; reset to 0 on any clean call, any warning that escalates below max, or any warning whose utilization is below the ceiling.
- `_warning_last_resets_at` — the `resets_at` of the peak-utilization window on the last warned call (threaded through `_ConsumeResult.warning_utilization` / `warning_resets_at`); cleared on a clean call.

Configuration:
- `[sdk] warning_hold_threshold` (default `3`, min `1`) — consecutive max-multiplier warnings needed to activate the hold.
- `[sdk] warning_hold_probe_interval` (default `60`, min `10`) — base seconds between probes.
- `[sdk] warning_hold_min_utilization` (default `0.95`, `0`–`1`) — warned utilization below this slows calls but never holds the loop.

## SDK Telemetry

Every `QueryOptions(...)` call site sets `caller="<name>"` (e.g. `"contemplate"`, `"propose_plan"`, `"distill_findings"`). The caller label is recorded on `QueryUsage.caller` and emitted in the per-call `"SDK call: ..."` log line, alongside `tokens_in`, `tokens_out`, `cache_read`, `cache_create`, `cost`, `duration_ms`, `turns`, and `attempts`.

`agent.run_loop()` writes a `"SDK iteration: iter=N"` marker each iteration so `build_sdk_usage_stats` can group calls by iteration without keeping in-memory state. Telemetry is observation-only and does not affect retry, backoff, or effort selection. The dashboard exposes the rollup at `GET /api/diagnostics`.

Every `ResultMessage` received on the Anthropic path is booked exactly once: by `_finalize_usage` on success, or — when `_consume_messages` raises a categorized `SDKError` after a billed result arrived (schema exhaustion, terminal error, session rate-limit rejection, unproductive aggregate) — by the `query` / `query_on_session` re-raise arms via `_book_unbooked_error_result`, which also advances the session cost baseline so the spend is never folded into the next turn (#4572).

## Global SDK Model Override

`Config.sdk_model` (TOML `[models] default`, shipped as `model_profiles.DEFAULT_MODEL`) sets the default model for every Maestro SDK call. `cli.main()` calls `configure_sdk_model()` alongside `configure_sdk_logging()` for any command that may issue SDK calls (`run`, `contemplate`, `evolve`, `loop`, `serve`); inside `sdk.query()` any call whose `options.model is None` has its model substituted with the configured value.

### Model profile registry

`maestro/model_profiles.py` is the single owner of facts about the models Maestro can run: each `ModelProfile` carries the model id, its default and supported per-call efforts, and its published pricing (standard and, where a `[1m]` pricing label exists, 1M-context). `Config.sdk_model` defaults to `model_profiles.DEFAULT_MODEL`, and `Config.sdk_pricing`'s default is the `pricing_table()` projection — a non-empty `[sdk.pricing.*]` TOML group still replaces it wholesale, as an optional operator override that `maestro.toml` no longer ships. The `[1m]` pricing label itself (`LONG_CONTEXT_PRICING_SUFFIX`) lives there too, and `sdk._label_long_context_pricing` imports it.

Admission rule: a model gets a profile only if it takes adaptive thinking controlled by effort, since effort is how Maestro steers thinking depth. Budget-only models (Haiku 4.5, pre-4.6 models) get none. `Config._check_cross_field_and_subtable` refuses at config load any non-empty `[models] default` / `fallback` / `long_context` without a profile whenever an Anthropic-backed provider (`anthropic` or `cli_paced`, globally or per-phase) is routed; an empty value keeps its inherit/disabled meaning, and a pure-`openai` routing set is exempt.

### Fallback model

`Config.sdk_fallback_model` (TOML `[models] fallback`, default empty = disabled) sets a fallback model that the SDK transparently fails over to when the primary model is unavailable. `cli.main()` calls `configure_sdk_fallback_model()`. Per-call override via `QueryOptions(fallback_model="...")` always wins over the global default.

### Thinking configuration

The declared `effort` is passed directly to the SDK's native `effort` option and is the only thinking lever. Every effort-bearing call also sends `thinking={"type": "adaptive"}` (the CLI's `--thinking adaptive`): on current models omitting every thinking option disables thinking, so adaptive is the on-switch and effort decides the depth. A call with no effort sends neither option. No thinking-token budget exists — the fixed budget (`max_thinking_tokens`) is deprecated by the SDK, acts only as an on/off switch on adaptive-thinking models, and is rejected outright by newer ones (proposal 140).

### Task budget

`Config.sdk_task_budget_tokens` (TOML `[sdk] task_budget_tokens`, default `0` = disabled) sets a per-call token budget via `ClaudeAgentOptions.task_budget`. When enabled (> 0), the model is made aware of its remaining budget and paces tool use accordingly. Per-call override via `QueryOptions(task_budget_tokens=50000)`. `cli.main()` calls `configure_sdk_task_budget()`.

Validation: must be `0` (disabled) or `>= 1024`. This addresses the "single-call cost runaways" gap documented above.

### Per-call effort levels

The per-call `effort` level controls thinking depth:

| Effort | Callers |
|---|---|
| `low` | `distill_findings`, `respond_to_messages`, `generate_task` |
| `medium` | `introspect`, `planner`, `replan` |
| `high` | `propose_plan`, `self_review`, `update_self_model`, `auto_fix` |

Explicit `model=...` on a `QueryOptions` always wins. An empty-string TOML value is normalised to `None` and preserves the SDK default.

Under the default-off `[sdk] call_policy_resolution_enabled` (proposal 140) the public seam — `query`, `create_session`, `query_on_session` in `maestro/sdk.py` — decides effort instead of the call site: it replaces `QueryOptions.effort` with `call_policy.tier_effort(options.caller)` on a copy of the caller's options, refuses (raises `ValueError` before any provider dispatch) a call whose options or caller is missing or whose caller is not registered in `CALL_POLICIES`, tags each opened session with its resolved effort, and refuses a session turn whose caller's tier effort differs from that tag (or whose session carries none) rather than silently running it at the session's effort. Config load refuses the flag unless `[sdk] single_use_evolution_calls_enabled` and `[loop] self_review_own_session_enabled` are both on — without them slot B and the implementation session carry turns from a different tier. Flag off, the options reaching a provider are the caller's own object, unchanged. Flipping it on is an effort retune, not only enforcement: the tier effort differs from today's call-site literals for most callers (e.g. `implementation_session`/`auto_fix` high → low, `propose_plan` high → medium), observed under step 8. Call-site `QueryOptions` `effort=` literals are pinned shrink-only (`_EFFORT_LITERAL_SITES`, with a raw per-module count so a caller-less literal cannot slip past the pin), and model-id string literals live only in `maestro/model_profiles.py`; both are enforced in `tests/test_call_policy.py`.

## SDK Query Optimization

Identity context is passed as a `system` prompt (not embedded in the user prompt) to enable API-level prompt caching. Each query site specifies an `effort` level. With one exception (the no-tool startup / warning-hold / introspect probes that pin `max_turns=1`) call sites no longer set `max_turns` — they accept the SDK default so the conversation runs until the model is genuinely done. The deterministic dollar ceiling is loop-level: the burn-rate throttle (`[loop] max_loop_budget_usd_per_hour`) stretches the inter-iteration sleep when the rolling spend rate approaches the limit. Per-call cost is observed but not enforced — runaway calls flow through to the next iteration where the throttle responds to the higher window cost. Other loop-level safeguards (executor loop detection, warning-hold gate) catch broader regressions.

JSON-returning queries use `output_format` with a JSON schema for structured output, with `parse_json()` retained as a fallback.

Tool-using evolution queries — `EvolutionEngine.implement()`, `evolution_quality.auto_fix()`, `self_review()`, the implementation session, and crash triage — drive multi-step file edits via `Read`/`Write`/`Edit`/`Bash` and run unbounded for the same reason: the loop-level gates catch runaways, and an artificial turn ceiling truncates legitimate deep work.

### Structured-output exhaustion

A terminal `ResultMessage(is_error=True)` whose subtype is `error_max_structured_output_retries` (the CLI's `StructuredOutput` validator rejected every schema-bound attempt in one turn) classifies as `ErrorCategory.STRUCTURED_OUTPUT_INVALID`: model-output invalidity, deliberately **not** in `TRANSIENT_SDK_CATEGORIES`, and outranked by a transient `api_error_status`, which still classifies `RATE_LIMIT` (#4535). A schema caller with an existing unparseable-reply branch translates it there — `propose_plan` / `propose_plan_chain` into `ProposalParseError`, the rest by parsing the empty result `sdk.structured_output_fallback` returns — and every other caller crashes loudly as before:

| Caller | Decision |
|---|---|
| `propose_plan`, `propose_plan_chain` | routed → `ProposalParseError` (`evolve()`'s `evolution_skip`) |
| `decompose` (`planner`), `replan` | routed → single goal step / `[]` |
| `update_self_model` | loud — no parse-failure contract |

## BM25 Search

`maestro/search.py` provides a pure-Python BM25 ranking function `bm25_rank(corpus, query)` shared by `journal.search()` and `memory.search_plans()`. Documents are pre-filtered by query-token intersection before scoring — only candidates that share at least one tokenised term with the query enter the BM25 computation, which avoids scoring the full corpus on every call. Documents with no token overlap are excluded entirely, so callers get clean "no match → empty list" behaviour.

Tokenisation uses `search.tokenize()` (lowercase, split on non-alphanumeric, empty-token removal). No stemming or stopwords — both the journal and evolution-plans corpora are bounded by dreaming/review cycles, so rebuilding the BM25 index per call is acceptable. Ties are broken by original index for stable ranking.

## Provider abstraction

Maestro's whole reasoning surface routes through four functions — `query`, `create_session`, `query_on_session`, `disconnect_session` — and the `QueryOptions` / `QueryResult` / `QueryUsage` contracts around them. Proposal 058 turned the LLM vendor behind those four functions into a configuration choice rather than an architectural assumption. The pieces live under `maestro/providers/`:

- **`base.py`** — the `Provider` `typing.Protocol` declaring the four async ops, the frozen `Capabilities` descriptor, an opaque `Session` newtype, and re-exports of `QueryOptions` / `QueryResult` / `QueryUsage` / `ToolCall` / `ErrorCategory` / `SDKError` so providers and callers import the contract from one neutral module. Loop modules hold the opaque `Session` handle and never name a vendor type.
- **`registry.py`** — a name→factory map. `configure_provider(name)` (called from `cli.main` with `config.resolved_sdk_provider()`) selects the active provider; `get_active_provider()` returns the cached singleton; the four `sdk.py` public functions are thin delegators over it (the bare-`query` AST invariant in `tests/test_structural_guards.py` still holds because the delegate is reached only through these wrappers). `cli_paced` registers behind a lazy factory so the default `anthropic` path never imports `maestro_sdk`.
- **`anthropic.py` / `openai.py` / `cli_paced.py`** — the three concrete providers.
- **`*_tool_adapter.py`** — each provider's `ToolAdapter` materialises the provider-neutral `InprocTool` registry (from `cli._build_agent_tools()`) into the vendor's tool wire shape.
- **`capability_gate.py`** — startup validation (below).

### Capability matrix

Each provider declares a frozen `Capabilities` descriptor with eight flags. The single legacy `mcp` notion is deliberately split into **`in_process_tools`** (can the provider host Maestro's Python tool handlers — the five introspection servers plus messaging/email/telegram — which are portable to any function-calling vendor?) and **`remote_mcp`** (can it reach the external MCP-protocol servers Context7/Serena, which are genuinely transport-bound?). The `in_process_tools` handlers are hosted by the in-process MCP shim (`create_inproc_mcp_server` in `maestro/inproc_mcp.py`); its `mcp` 1.x→2.x migration path — the symbol map, per-file touchpoint inventory, and the `claude-agent-sdk` go/no-go — is audited in [mcp-v2-migration.md](mcp-v2-migration.md).

| Capability | `anthropic` | `openai` | `cli_paced` |
|---|---|---|---|
| `sessions` | ✓ | ✓ | ✓ persistent pty session + `--resume` respawn |
| `in_process_tools` | ✓ | ✓ | ✓ tool-adapter `--mcp-config` (launcher: rollout) |
| `remote_mcp` | ✓ | — | ✓ stdio servers folded into `--mcp-config` |
| `extended_thinking` | ✓ | — | ✓ follows the CLI's own thinking config |
| `long_context` | ✓ | — | ✓ child-env `ANTHROPIC_CUSTOM_HEADERS` beta |
| `structured_output` | ✓ | ✓ | ✓ client-side validate-and-reask (one-shot only) |
| `usage_metering` | ✓ | ✓ | ✓ transcript-sidecar token counts |
| `streaming` | ✓ | — | ✓ `complete_on` against the parser's answer text |

`anthropic` is the default and supports everything. `openai` (Responses API) hosts the in-process tools and meters usage but cannot reach remote MCP, has no long-context or extended-thinking analogue, and exposes effort rather than a thinking-token budget. `cli_paced` (the human-paced `claude` CLI via `maestro_sdk`) is fully qualified as of proposal 061: each flag is vouched for by a mechanism the `claude` CLI already exposes around its TUI, never by abandoning the pty discipline. **Capability parity is not a production rollout** — proposal 066 closed the trust gap by replicating the `PreToolUse` action-gate across the subprocess boundary (see *Action-gate replication* below), and proposal 067 supplies the operate-it layer: the per-phase login precondition, provider attribution on usage rows, and the [canary → promote → rollback runbook](deployment.md#cli-paced-rollout-canary--promote--rollback-proposal-067) — rollback is a single config revert to `anthropic`, effective on the first iteration after restart, with no state migration. The per-CLI-version marker-pack *mechanism* shipped with proposal 075 (see *Marker packs and layout-drift detection* below); the in-process-tools launcher entrypoint remains on the production-parity track (proposal 076).

> **Registration status.** `openai` is implemented and test-pinned but **not yet registered** in `registry.py`: its tool adapter is not wired into `OpenAIProvider.query`, so registering would let the capability gate vouch for `in_process_tools=True` while queries ran toolless — a silent degradation the fail-loud doctrine forbids. Selecting `[sdk] provider = "openai"` therefore still fails loud at startup until that wiring lands (proposal 058 Phase 3 follow-up). `anthropic` and `cli_paced` are registered and selectable.

### Selection and capability gating

`[sdk] provider = "anthropic" | "openai" | "cli_paced"` (default `"anthropic"`) picks the active provider, with an optional per-phase `[sdk] <phase>_provider` override map; `Config.resolved_sdk_provider()` / `provider_for_phase()` resolve the *names* (and apply the one-release `[sdk] backend` → provider alias). At startup `capability_gate.validate_provider_capabilities(config)` asserts, **per phase**, that the resolved provider's `capabilities` satisfy what the phase needs: `in_process_tools` for any introspection-tool phase, `remote_mcp` only when an external MCP server is enabled, `long_context` only for a long-context phase that has a long-context model configured. A gap raises a remediation error at config-load time — never at first query — matching the fail-loud doctrine. The gate is inert under the default `anthropic` (every flag `True`).

**Runtime per-phase routing (proposal 058 Step 6 runtime half).** Resolving the *name* is only half the seam; the other half routes the phase's calls to that provider at query time. `cli.main` installs the override map into the registry via `configure_phase_providers(config.sdk_phase_providers)` (re-validating each name against the registry, so a schema-valid-but-unregistered override like `openai` fails loud here, exactly as `configure_provider` does for the global selection). The `sdk.py` seam then resolves through `registry.get_phase_provider(phase)`: `create_session(..., phase=...)` and `query(..., phase=...)` build the session/run the one-shot on the phase's provider, falling back to the active provider for `phase=None` or an un-overridden phase. `create_session` **tags** the opened session with the provider that built it (a `_maestro_provider` instance attribute); `query_on_session` / `disconnect_session` read that tag, so a follow-up turn — or a cross-phase teardown, e.g. the contemplation session disconnected during the implementation phase — always routes back to the same provider regardless of which phase is current. Each loop phase's session-creation site passes its SDK phase name: `contemplate` → `contemplation` (Session A), `evolve`/curate → `evolution` (Session B), and the ephemeral/run sessions → `run_task` / `implementation` / `task_generation` / `artifact_review` / `rejection`. `respond_to_messages` is no longer a session-creation site — fix #1239 runs the ~200-char reply as an off-session `effort="low"` one-shot instead of reusing the high-effort Session A — but its `query()` still passes `phase="contemplation"`, so a `[sdk] contemplation_provider` override routes the reply to the same provider Session A would have, not the active fallback. The `run_task` phase additionally tags its *stateless* step path: `Executor.execute` passes `phase="run_task"` on the fallback `query()` it uses when a plan does not qualify for step-session reuse (single-step or all-parallel plans), so a `run_task` override covers every step regardless of plan shape. Likewise the two scope-gate calls that are sessionless in every config — `_replan_for_scope`'s rewrite and the `propose_plan_chain` fallback reached from `_slice_scope_rejected_plan` — pass `phase="implementation"` and `phase="evolution"` respectively, so they follow the same route as their session-attached siblings even with reuse on (issue #4101). Tagging the replan `implementation` places it under the action-gated-phase contract, so it now runs `tools=[]` — a text-only JSON rewrite — rather than the vendor-default tool set (including an ungated `Bash`) it previously inherited. Because the routing tag is stamped at session-creation, per-phase overrides require `enable_session_reuse=true` (the default): with reuse off the loop falls back to stateless one-shot `query()` calls that carry no phase, so `Config.validate()` **fails loud** rather than silently ignore an override paired with `enable_session_reuse=false`. The whole seam is inert under the default config (empty override map → every phase resolves to the active provider).

**Grounded reflection (proposal 132).** Session A (`contemplation`) is built `tools=[]` by default. Behind `[loop] grounded_reflection_enabled` — and only when the introspection registry is present and the loop is not budget-throttled (`MaestroAgent._grounded_reflection_active`) — `_build_contemplation_session_options` instead attaches the bounded read-only reflection surface owned by `maestro/reflection_retrieval.py` (the `READ_ONLY_REFLECTION_TOOLS` members as `mcp__<server>__<tool>` names, no `Bash`/`Read`/`Write`), so a priced bet can *pull* the one fact it hinges on. `tools=[]` stays set in both branches — the MCP servers ride `--mcp-config` and are admitted by `--allowedTools`. The per-reflection tool-call budget is enforced *inside* the tool handlers (an over-budget read returns a graceful `is_error`, never the loop-killing `error_max_turns`), with `max_turns` a fail-loud backstop above it; with the flag on, `required_capabilities_for_phase("contemplation")` then includes `in_process_tools`.

Its trust sibling `capability_gate.validate_action_gate_coverage(config)` (proposal 066) runs alongside it: an **action-gated** phase (`run_task` / `implementation` — the phases that execute repo-mutating Bash) may only route to a provider listed in `_MUTATION_GUARDS`, i.e. one carrying an enforcement path for the issue #2280 Bash action-gate (`anthropic` via the in-process `PreToolUse` hook, `cli_paced` via the CLI-injected settings hook below). Deliberately separate from the `Capabilities` flags — those describe capability, not trust — so a hand-rolled provider that advertises every capability but wires no gate still fails loud at config-load, naming the phase and the missing guard.

### Honest degradation

A turn whose usage cannot be measured returns a `QueryUsage` whose token counts are a dataclass-shape concession, not a faked measurement: `unmetered=True` (proposal 058 Step 13) marks the row as *unmeasured*. `cli_paced` emits such rows whenever the CLI transcript sidecar is missing, unreadable, or ambiguous (the metering source is the CLI's own on-disk layout, not a stable contract — see proposal 061 Step 10); its readable-sidecar rows carry real summed counts with `unmetered=False`. `cost_tracking._build_cost_rates_uncached` drops unmetered samples from the rolling-window rate aggregation so the burn-rate gate never reads the zeros as spend, and the dashboard's `formatCost` renders an unmetered value as `—`. Every row also carries its producing provider (proposal 067 Step 2): `QueryUsage.provider` is stamped at row creation by each provider, rides into `CostSample.provider` and the per-iteration `IterationUsage.providers` list, and surfaces as the Provider column on the Budget tab — so unknown spend reads as unknown-by-design under a named provider, not as silently zero. Per-provider credentials are documented in [deployment.md](deployment.md#environment-variables-secrets-only); `check_secrets` dispatches its credential precondition on the selected provider, phase-aware for `[sdk] <phase>_provider` routes (proposal 067 Step 1).

## Permission mode and action gating

Every SDK call Maestro makes runs with `permission_mode="bypassPermissions"`. The single option-assembly chokepoint `_build_sdk_options` sets it unconditionally — outside its `QueryOptions` handling, so a call that passes no options is covered too — and both entry paths route through it: `_create_session_impl` behind `create_session()` and `_query_impl` behind the stateless `query()` (which re-sets the mode afterward as belt-and-braces defense, not as the load-bearing cover for any path). The mode is load-bearing, not an oversight — the loop is unattended, and a command blocked on an approval no human is present to give would crash the loop.

The trade-off this buys is that the CLI short-circuits the permission flow to "allow" *before* it would consult a `can_use_tool` permission callback, so such a callback never fires. Action-level enforcement must therefore ride `PreToolUse` **hooks** — a separate mechanism that runs regardless of permission mode (verified empirically: a `PreToolUse` deny hook blocks a Bash command under `bypassPermissions`) and that, unlike `can_use_tool`, also works on the stateless `query()` step path. `maestro/tool_gating.py` (issue #2280) is that gate: the task executor wires its hook onto SDK sessions to deny PR-mutating Bash commands (`gh pr create|merge|ready`, mutating `gh api …/pulls` calls), force-pushes, and pushes outside the run's owned branch set; `gh pr close` stays permitted as a reversible disposal, and threaded review-comment replies are allowed for the PR-remediation flow. It also refuses the loop's outward acts: `gh repo`/`release`/`secret` writes, outward mutating `gh api` calls, and tag pushes.

That coverage is deliberately exactly the #2280 approval-bypass class. General shell allowlisting — destructive deletes, credential reads — is an accepted, documented risk deferred to the security proposals: 024 (diff danger-pattern gate), 025 (implement-phase tool gating), and 026 (sandbox container). Until those land, the compensating control is the audit trail: every tool call is logged at INFO level (`SDK tool call: <name>` in `sdk.py`'s message-processing path), session logs capture the full stream including tool inputs, and each call's tool-call count rides `QueryUsage.tool_uses` into the per-call `SDK progress` INFO summary (`N tool uses`). This section is pinned by `tests/test_sdk_internals_doc.py`, so the accepted-risk statement cannot silently vanish from the docs.

## MCP Server Configuration

Two external MCP servers are configurable via the `[mcp]` TOML section:

| Server | Package | Requires |
|---|---|---|
| Context7 MCP | `@upstash/context7-mcp` | — |
| Serena MCP (read-only) | `serena-agent` (via `uvx`) | — |

Each is independently enableable. GitHub access is deliberately not an MCP server: it goes through the `SubprocessCodeHost` control-plane layer (PR management, merge detection, issues) and the in-process `issues` server. The former `[mcp] github_*` integration was retired (#4132) — its npm launcher did not exist, and a working server would have exposed repo-writing tools (`merge_pull_request`, `push_files`) that bypass the `Bash`-scoped action gate; a stale `[mcp] github_*` overlay key now fails loud as an unknown key. The Fetch server was retired; Maestro has no web reach; a stale `[mcp] fetch_*` overlay key fails loud as an unknown key.

Four introspection MCP servers give the agent access to its own subsystems during task execution: `journal` (write/read/search), `self_awareness` (read self-model), `memory` (task history, evolution plans), and `issues` (list/create/close GitHub issues).

Config flow: TOML → `Config.mcp_servers_config()` → `Executor`/`EvolutionEngine` → `QueryOptions.mcp_servers` → `ClaudeAgentOptions.mcp_servers`. All tool *handlers* are declared as `InprocTool`s and assembled into a registry by `cli._build_agent_tools()`; the executor materialises the registry into the active provider's tool shape via `ToolAdapter.materialize`. The default `AnthropicToolAdapter` reproduces the `{"type": "sdk", "name", "instance"}` MCP wire shape and the `mcp__<server>__<tool>` qualified names the Claude Agent SDK expects.

## CLI-paced provider (`[sdk] provider = "cli_paced"`, proposal 056)

Maestro reaches the model through four functions — `query`, `create_session`, `query_on_session`, `disconnect_session` — which delegate through the `[sdk] provider` registry (proposal 058; see the provider abstraction above). `cli_paced` is one registered provider, implemented as `CliPacedProvider` in `maestro/providers/cli_paced.py`, driving the `claude` CLI at human cadence via `maestro_sdk.AsyncClient`. It is registered behind a lazy factory (`registry._cli_paced_factory`), so the default `anthropic` path never imports `maestro_sdk`; selecting it globally (`[sdk] provider = "cli_paced"`) or routing a single phase to it (`[sdk] <phase>_provider = "cli_paced"`, which serves that phase's session at runtime — see [Runtime per-phase routing](#selection-and-capability-gating) above) resolves through the registry, and `configure_provider` / `configure_phase_providers` fail loud on unknown names. Its `Capabilities` descriptor is fully qualified (every flag `True`, proposal 061 Step 11) — see the capability matrix above for each flag's CLI-side mechanism — so the startup capability gate routes it to any phase an operator selects.

> The standalone `[sdk] backend` seam that proposal 056 originally shipped — `maestro/sdk_backends/` plus the `configure_backend` global — was **retired in 056 Step 11**. Its adapter body (type re-pack, `MaestroSDKError → SDKError(category=…)` translation, fail-loud-on-unsupported) now lives wholly in `CliPacedProvider`. There is no `[sdk] backend` field.

**`cli_paced` capability mechanisms (proposal 061).** The provider re-packs `maestro_sdk` types into `maestro.sdk` shapes and translates `MaestroSDKError.category` (a name-string) into the `ErrorCategory` resume taxonomy. Each capability rides a CLI-side mechanism: sessions on `maestro_sdk.Session`'s persistent pty runner with `claude --resume <id>` respawn (`resume_session_id` / `initial_prompt` forward into it; live continuity needs a configured marker pack — see *Marker packs and layout-drift detection* below); token metering on the CLI's per-session transcript JSONL sidecar (readable → real counts, otherwise the honest `unmetered=True` zero-shape that `cost_tracking` skips and the dashboard renders as `—`); external MCP and tool policy on spawn-command flags (`--mcp-config`, `--tools` / `--allowedTools` / `--disallowedTools`); the long-context beta on the child env (`ANTHROPIC_CUSTOM_HEADERS`), with thinking following the CLI's own thinking config (no Maestro-supplied budget); structured `output_format` on client-side validate-and-reask (one-shot `query` only — a *session* still rejects it, since follow-up turns do no validation); and `complete_on` on the incremental parser's accumulated answer text (the two-arg Maestro predicate is adapted to the driver's text-only form with `None` for the message; because the driver evaluates it per pty snapshot, the adapter shows it only complete rows — up to the last newline — and trims an early-exit response to the prefix it fired on, so a marker check cannot fire on a half-drawn row; since the parser strips trailing whitespace the finished final row is hidden too, so a predicate needing the last row simply runs the turn to completion). `max_turns` is enforced as a per-session prompt-turn cap. The `system` prompt is honoured by prepending it to the user prompt (the CLI driver threads no separate system prompt). The two features the CLI path still cannot honour fail loud: SDK lifecycle `hooks` other than the recognised task action-gate (an in-process callback cannot reach a separate `claude` subprocess; the action-gate is the one hooks payload with a subprocess-native replication — see below) and any beta other than long-context.

**Action-gate replication (proposal 066).** Maestro's task-execution mutation guard (`maestro/tool_gating.py`, issue #2280) is one decision core — `evaluate_bash_command`, pure and branch-parameterised — behind two enforcement paths. In-process (`anthropic`): the executor attaches `make_task_tool_hooks(task_branch)` via `QueryOptions.hooks` and the `TaskGateHook` callback runs as an SDK `PreToolUse` hook. Cross-process (`cli_paced`): the provider recognises exactly that hooks mapping (`tool_gating.task_gate_from_hooks`) and, instead of rejecting it, injects an equivalent gate into the spawned `claude` itself — an inline `--settings` JSON payload (built by `maestro/providers/cli_paced_gate.py`, no on-disk settings file, mirroring the `--mcp-config` inline pattern) registering the hidden `_gate-bash-hook` subcommand — launched via the loop's own interpreter (`<sys.executable> -P -m maestro.cli _gate-bash-hook`, `gate_hook_command`), so the hook runs the same installation independent of `PATH`, and `validate_action_gate_coverage` fails loud at config-load when that executable cannot be resolved (an unlaunchable hook exits 127 → fail-open; issue #4160) — as the CLI's own `PreToolUse` `Bash` hook, plus the run's owned-writable branch *set* JSON-encoded on the child env (`MAESTRO_GATE_ALLOWED_BRANCH` via `allowed_branches_to_env`, also carried in the settings `env` block by the *same* encoder so the two cannot drift; proposal 093). The subcommand dispatches in `cli.main` *before* `Config.from_env()` (it must answer from stdin + env alone; a crashed hook reads to the CLI as a non-blocking error, i.e. fail-open) and runs the **same** `TaskGateHook` callback over the set `allowed_branches_from_env` decodes, so the verdict is byte-for-byte the in-process one; an unset/empty/malformed branch-set env and unparseable hook input both deny fail-closed. Any *other* hooks payload — including a mapping that merely contains the gate — still raises. The deny-by-default `maestro_sdk` `ApprovalHandler` posture stays the backstop: `--allowedTools` keeps permitted tools modal-free, and an unexpected modal fails loud rather than auto-approving. Cross-boundary parity is pinned adversarially in `tests/test_fault_seeding.py` over the shared ground-truth command tables in `tests/test_tool_gating.py`.

**Operator tuning (`[sdk.cli_paced]`).** A `[sdk.cli_paced]` TOML sub-section (proposal 056 Step 12) tunes the provider without code changes: `maestro_sdk.Cadence` knobs (`mean_key_ms`, `heartbeat_per_answer_char_ms`, …) and a CLI-specific `stream_idle_timeout_seconds`. The provider applies them at startup via `configure_cli_paced` (`cli.main`); the CLI path deliberately does **not** inherit the agent-side `[sdk] stream_idle_timeout_seconds` global, and absent the sub-section falls back to `maestro_sdk`'s built-in defaults (10 s — 18× shorter than the agent global). `maestro.toml` carries a commented template.

**Slash-command metrics probe (proposal 062).** An opt-in observability side channel for the CLI path, **distinct from — and never a substitute for — the transcript-sidecar metering above** (proposal 061 Step 10, which stays the spend source of truth). With `[sdk.cli_paced] probe_metrics_enabled = true`, every `probe_metrics_every`-th session turn issues three read-only slash commands on the live pty session via `maestro_sdk.Session.run_command` and parses each redraw through `maestro_sdk.slash_probe`:

- **`/context`** — the one runtime surface that *measures* realized context-window composition (system prompt, tools, MCP registrations, history, free space) for the CLI path; the reading lands as a `ContextWindowSnapshot` on `DiagnosticSnapshot.context_window` (via `maestro.sdk.latest_context_window`), and `blind_spots()` names its absence.
- **`/usage`** — how much of the subscription plan's usage limits a run has consumed, which neither the API response nor the sidecar exposes. An observability reading so the operator can see where a run stands against those limits, not a way around them; surfaced read-only as `cost_tracking.PlanHeadroom` (via `maestro.sdk.latest_plan_headroom`); the burn-rate throttle reports it on entry transitions but does **not** gate on it (that wiring is explicitly deferred).
- **`/cost`** — a *local estimate* the TUI computes from token counts × published rates. Deliberately redundant with the sidecar: when a cadence-hit probe and a metered sidecar count exist for the same turn, `cost_tracking.log_metering_divergence` compares the two session-cumulative token totals and logs one `metering_divergence` WARNING past a relative threshold (`METERING_DIVERGENCE_THRESHOLD`) — a drift alarm for either parser falling behind a CLI layout change. The sidecar `QueryUsage` is never overridden.

The probe scrapes a repainting TUI region whose layout is **not a stable contract** — the same fragility the answer `Parser` contains. It degrades with the same discipline: parsing needs a per-CLI-version `SlashProbeMarkers` family (supplied by the configured marker pack — see *Marker packs and layout-drift detection* below), and a non-matching layout reads as `None` — "no reading", never a fabricated number. Probe readings cache as process-globals freshest-wins (a parse miss honestly clears the previous reading); `configure_cli_paced` resets them. Default-off keeps the whole channel inert, and the one-shot `query` path is never probed. Note the resident-runner caveat: `run_command` needs a child that survives between turns (a configured idle marker), so an enabled probe on today's EOF-mode sessions fails loud rather than reading metrics.

**Marker packs and layout-drift detection (proposal 075).** Every marker family the driver acts on — `ClientMarkers` (idle / rate-limit / session-expired / session-id), `ParserMarkers`, `ApprovalMarkers`, `SlashProbeMarkers` — is per-CLI-version layout policy that defaults to "matches nothing". A **marker pack** (`maestro_sdk.MarkerPack`, `maestro_sdk/src/maestro_sdk/marker_packs.py`) freezes all four families under a pack name and an inclusive dotted-numeric CLI-version range; `select_marker_pack(version)` returns the newest registered pack covering a version and `None` otherwise — never a best-guess pack. Configuration rides `[sdk.cli_paced] marker_pack`:

- `"none"` (default) — today's empty markers: every turn ends on EOF, no session id is captured (so respawns cannot `--resume` and sidecar metering stays `unmetered=True`), rate-limit/expired notices surface as generic `stream_stall`/`cli_crash`, and the slash probe parses nothing.
- `"auto"` — `cli.main` probes `claude --version` (`detect_cli_version`, bounded and read-only like the `claude auth status` login probe) and applies the selection; an uncovered (or unprobeable) version logs one WARNING naming it and proceeds pack-less.
- `"<pack-name>"` — pins a registered pack; an unknown name fails loud on the declarative load path via `Config._check_cross_field_and_subtable` (the `[sdk.cli_paced]` sub-table guard `build_config_via_pydantic` runs — a lazy registry check, only when `cli_paced` is selected globally or per-phase, so the default `anthropic` path never imports `maestro_sdk`).

`configure_cli_paced(marker_pack=…)` stores the resolved pack; the client factory threads its client/parser/approval families into every `AsyncClient` and its probe family replaces the probe-marker seam. Four capability flags are therefore **configuration-dependent**: `sessions` continuity, `usage_metering`, the rate-limit/stale-session slice of the error taxonomy, and the 062 probe are mechanism-complete but live only under a matching pack — 067's canary runbook cites the pack as a prerequisite for meaningful observability ([deployment.md](deployment.md#cli-paced-rollout-canary--promote--rollback-proposal-067)).

**Drift sentinel.** A CLI upgrade that silently changes the TUI must read as a loud, attributable degradation: when a configured idle marker never matches before a turn ends on EOF, the driver stamps `QueryResult.idle_marker_missed` and logs a one-shot WARNING, and the provider adds a one-shot WARNING naming the pack; a pack configuring `session_id` markers that captures no id across a session's first 3 turns gets the same pack-named one-shot. Behaviour still degrades to the honest EOF-only path — the pack is observability config, not a correctness gate, and a stale pack never yields a wrong parse. Operator procedure on CLI upgrade: re-pin `marker_pack` to a covering pack (or `"none"`), or extend/author a pack validated against the new layout.

**Registry status (claude 2.1.x).** The registry currently ships **no** packs: recorded-transcript analysis of claude 2.1.172 found the TUI paints no session id during a turn (only inside the `/status` dialog, which the driver never opens mid-turn), and the idle hint line (`? for shortcuts …`) renders through the package's deliberate vt100-subset `Screen` emulator with unstable spacing and stale-cell residue (no wide-glyph width handling, no OSC consumption), so no stripped-line prefix matches it reliably; rate-limit/expired notices cannot be fixture-recorded without live limit events. Authoring a first real pack therefore needs `Screen` fidelity work (or an output-quiescence idle mechanism) first — until then `"auto"` honestly resolves to pack-less with the WARNING naming the version.

**Credential precondition.** Selecting `cli_paced` requires the `claude` CLI on `PATH` **and** an active login: `check_secrets` runs a non-mutating `claude auth status --json` dry-probe (proposal 056 Step 13) and raises a `claude auth login` remediation when the binary is present but unauthenticated. See [deployment.md](deployment.md#per-provider-credentials).

`cli_paced` is registered and selectable but is **not wired into any phase by default** — the default `[sdk] provider = "anthropic"` keeps it inert in production. The `PreToolUse` action-gate is replicated into the CLI's own permission settings (proposal 066, above); marker packs are configurable via `[sdk.cli_paced] marker_pack` (proposal 075, above); the production rollout (canary phase selection, the in-process-tools launcher entrypoint, and an explicit tool-approval policy) remains with proposals 067/076.

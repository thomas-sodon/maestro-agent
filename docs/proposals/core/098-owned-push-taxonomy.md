## Description

> Status updated to shipped on 2026-07-25 by /update-proposals — see [README.md](../README.md#shipped) for the landing record.

Proposals 093 and 096 gave the agent the *capability* to push its own resolution to a `maestro/evolve/*` PR branch — the owned-writable-branch oracle widened the action gate, and the push-conformance fix stopped the gate denying the instructed push. But the taxonomy that decides *whether the agent should use that push* — the fact "who owns clearing merge-blocker X: me end-to-end, or Tend/Thomas?" — was written before 093 and never migrated. That fact is re-encoded independently in at least five places, and every one of them still says a resolution committed on the branch but not yet on `origin` (`AWAITING_PUSH`) is Tend's mechanical push to deliver. So at the exact moment one `git push` would land the agent's own conflict resolution, the classifier says "external," the remediation prompt says "stand down," the loop's merge-block gate *skips the remediation and hands the PR to Tend*, and only a trailing delivery note — added by 093 — says the opposite. The agent, reading its own taxonomy, keeps deferring the push it now owns.

This matters now because it is the loop's core value-delivery path and it is not converging. Of the 59 `Remediate PR #N` laps in the current hot window, **58 closed `partial` and exactly one `success`**; the audit layer's top five finding kinds are all detectors of "narrated a resolution that never landed." The clean pre/post-096 split shows the taxonomy, not the capability, is the residual: **before 096 all 28 laps emitted the literal "awaiting tend push" defer costume; after 096 all 28 of the newer laps emit 093's "delivered to pr" marker — the narration flipped exactly as 093/096 intended — yet nearly half are still `CONFLICTING` and every one is still `partial`.** The costume changed; the non-landing did not. 096 saw this and named the cause out of scope: *"`classify_blocker_ownership` re-bucketing `AWAITING_PUSH` … is a separate question this proposal does not need to answer."* This proposal answers it.

The change makes blocker ownership one source of truth, migrates it to the post-093 reality, and binds every consumer to it. `classify_blocker_ownership` becomes the single definition of the owned/external partition; `AWAITING_PUSH` — a resolution the agent committed but has not pushed — moves from *external* to *owned*, because the agent pushes it now. The remediation prompt's stand-down and owned-disposal clauses stop hard-coding "AWAITING_APPROVAL / AWAITING_PUSH" in prose and instead interpolate the owned/external sets from that source, so they can never again tell the agent to await a push it owns. The merge-block gate stops skipping an `AWAITING_PUSH` PR as "Tend will clear this." A golden test binds the prompt's blocker prose to the classifier — the analog of the push-conformance test that already binds the prompt's push *template* to the gate — so the next capability change cannot leave a stale prose encoding behind.

The end state: whichever way the agent reaches a conflicting PR, it fetches, merges `origin/main`, resolves, commits, and pushes in one remediation task — because every layer of its taxonomy agrees the whole chain is owned — and "awaiting tend push" survives only for the one blocker that is genuinely external, the human approval gate. The human-in-the-loop invariant is untouched: this proposal changes no gate, pushes to no new branch, and merges nothing to `main` — it edits only which *owned* action the agent is told to take at a blocker it already has the capability to clear.

## Relevant Findings

- `maestro/remediation_tracker.py` (`classify_blocker_ownership`, `OWNED_BLOCKERS`) — the single ownership classifier partitions merge-blockers into `owned` (`CONFLICTING` / `DIRTY` / `THREADS_UNRESOLVED`) and `external` (everything else). `MERGE_BLOCK_AWAITING_PUSH` falls to `external` with the documented rationale "Tend's mechanical catch-up / push delivers them" — the pre-093 fact, unrevised. This is the *definition* the other sites should read but instead re-encode.
- `maestro/agent.py` (`_probe_pr_merge_block`) — refines a `NONE` merge-block to `MERGE_BLOCK_AWAITING_PUSH` when the resolution is committed on-branch but not on `origin` (`not origin_ref_present or unpushed > 0`), with the comment "an on-branch-but-unpushed resolution is genuinely Tend PR's job, never a conflict." A live producer of the stale fact, in loop code, not just prompt prose.
- `maestro/loop/pr_remediation.py` (the merge-block gate, `_run_merge_block_gate`) — an `AWAITING_PUSH` verdict is dispatched to `PrRemediationState.MERGE_BLOCKED` → `PrRemediationDisposition.TEND_WILL_CLEAR`: the loop **skips LLM remediation at zero SDK cost**, records `[merge-block]` `partial`, and escalates "Resolution is committed on the branch but not yet pushed; check why Tend PR has not pushed it." The loop actively diverts the agent's own unpushed resolution *away* from the agent and toward Tend.
- `maestro/prompts/remediation.py` (`MERGE_TRUTH_FIRST_PREAMBLE`) — four of the preamble's clauses hard-code "AWAITING_APPROVAL / AWAITING_PUSH" as the external-stand-down set in English prose: CHOSEN-STAND-DOWN ("the sole blocker is external — the PR is `AWAITING_APPROVAL` … or `AWAITING_PUSH` (Tend will deliver the push)"), STAND-DOWN-ON-RESOLVED ("the sole remaining blocker is approval or push"), EXPECTED-CHURN ("the only thing left is Thomas's approval or Tend's push"), and OWNED-DISPOSAL ("NOT an external `AWAITING_APPROVAL` / `AWAITING_PUSH` / `BEHIND_MAIN` wait"). None derive from `classify_blocker_ownership`; each is an independent, drift-prone copy of the taxonomy.
- `maestro/loop/pr_remediation.py` (`_delivery_note`, `OWN_BRANCH_PUSH_TEMPLATE`) — the trailing note 093 added instructs the *opposite*: "Deliver your fix yourself … push it to this PR's branch with `git push origin HEAD:<branch>`." The same composed prompt now tells the agent both "push it yourself" and "AWAITING_PUSH is Tend's — stand down." The agent resolves the contradiction toward the lower-action reading.
- `maestro/pr_remediation_state.py` (`Marker.AWAITING_TEND_PUSH`) — the on-disk verdict literal "awaiting tend push" remains a first-class outcome the agent reaches for; 091 split it from `Marker.DELIVERED_AWAITING_MERGE` but left it a legitimate terminal for a resolution the agent could have pushed.
- `maestro/outcome_grounding.py` (`_MERGEABLE_FLIP_BLOCKERS`, `bind_mergeable_flip_to_merge_request`) — the mergeable-flip actuator excludes `AWAITING_PUSH` from the recruit-Thomas set with a third independent rationale ("Tend's mechanical push to clear"). Correct *destination* (a message to Thomas cannot clear a push), wrong *reason* — it treats the push as not-the-agent's rather than as the agent's own next act.
- `tests/test_push_conformance.py` (`TestPushConformanceAllowed.test_instructed_push_allowed`) and `tests/test_owned_branch_oracle.py` (`test_push_permission_computed_only_at_the_oracle_door`) — the house pattern this proposal reuses: a deterministic golden/AST test binding one prompt-emitted fact to its single code source so the two cannot drift. 096 bound the prompt's push *command shape* to the gate; this binds the prompt's *blocker-ownership prose* to the classifier.
- `maestro/config.py` (`merge_block_local_probe_enabled`, `mergeable_merge_request_enabled`) — the `[loop]`-section boolean-flag convention this proposal's rollout flag follows; a behind-AND-conflicting branch is already reclassified `CONFLICTING` by the local `merge_tree_conflicts` probe, so the clean-catch-up split (`BEHIND_MAIN` stays Tend's) is preserved unchanged.

## Risk Assessment

- **Suppressing a legitimate stand-down.** The flag flips exactly one reason code, `AWAITING_PUSH`, from external to owned; `AWAITING_APPROVAL` (the human-merge gate) stays external, so the honest "wait for Thomas" stand-down is untouched, and `BEHIND_MAIN` stays Tend's mechanical catch-up. The only behavior removed is "stand down / hand to Tend when the sole blocker is *my own unpushed resolution*" — which 093/096 already made the agent able to clear.
- **Trust chain.** None touched. This proposal edits no action gate, grants no new push destination, and merges nothing to `main`. The push it unblocks in the taxonomy is the same owned `git push origin HEAD:<branch>` the action gate already permits (093/096) and the loop's §5-push backstop already performs. The PR still requires a human merge.
- **Rollback posture.** Every behavior change is behind `[loop] owned_push_delivery_enabled`, which now ships `true`. Each phase was independently mergeable and inert while the flag was off (the classifier parameter, the prompt branch, and the gate branch all defaulted to the legacy path), and every one of those legacy paths is retained — so rollback is flipping the single flag back to `false`, which restores the pre-098 partition across the prompt, both dequeue gates, the stuck-PR escalation wording and the mergeable-flip actuator at once. Full revert is `git revert` of the phase. Step 8's mole retirement (deleting the now-inert flag-off branches, narrowing `Marker.AWAITING_TEND_PUSH`) is intentionally deferred until the default is proven in production — it is what makes rollback cost a revert instead of a config line.
- **Interaction with 097.** Complementary, not overlapping: 097 reconciles *already-recorded* verdict stamps against merge-truth in the *audit* layer so the phantom sensors self-extinguish; this proposal reduces the *generation* of deferral verdicts in the *remediation* layer. Fewer deferrals means fewer stale stamps for 097 to reconcile — they compose.

## Falsifiability

The design is right if, after the flag defaults on: the post-096 pattern of "delivered to pr … still CONFLICTING … partial" laps collapses because a resolved conflict lands in one task; `measure_confirmed_landing_rate` (CONFIRMED-LANDING-RATIO) rises and `measure_unlanded_remediations` (UNLANDED-REMEDIATION) falls; the per-lineage re-lap count on conflicting PRs drops; and the audit-cycle firing rate of `phantom_remediation` / `phantom_resolution` / `narration_verdict_mismatch` falls from its current majority-of-cycles dominance toward baseline. It failed if remediation stays `partial`-with-`CONFLICTING` at today's rate, or if an `AWAITING_PUSH` PR is still skipped to Tend under the flag — the Phase-3/4 gate tests and the audit firing rates are the tripwires.

## Out of scope

- **Audit-layer reconciliation of stale verdict stamps.** Owned by proposal 097 (the standing reconciler binding recorded verdicts to `is_pr_settled`). This proposal changes what verdict a lap *writes*, not how the audit layer *reads back* verdicts already written.
- **The `BEHIND_MAIN` clean-catch-up split.** A behind-but-clean branch is genuinely Tend's mechanical catch-up merge, and a behind-AND-conflicting branch is already reclassified `CONFLICTING` (owned) by the `merge_tree_conflicts` probe. `BEHIND_MAIN` stays external — this proposal touches only `AWAITING_PUSH`.
- **Reducing the number of remediation laps.** The lap-budget / stand-down treadmill and progress-aware lap accounting are owned by proposals 080 / 089; this proposal makes each lap that *does* run drive the PR to landed, rather than changing how many laps are permitted.
- **Autonomous merge or close to `main`.** A hard human-in-the-loop invariant; `gh pr merge` and pushes to `main` stay denied. The owned terminal acts remain "push the resolution" and the reversible `gh pr close`, both already permitted.
- **Force-push and plural/unnumbered `route_user_pr_message` demands.** 093's explicit deferrals; unchanged here.

## Description

149 Step 2 deletes the evolutionary-stage *machinery*: the `TRANSITIONS` ladder, the priced `assess_stage_readiness` verdict, `advance_stage`, and the `stage_progression_enabled` lever. The *label* survives that deletion, and it is the part that keeps coming back. `stage` is a mandatory field on three persisted types (`JournalEntry`, `EvolutionPlan`, `SelfModel`), a required parameter of every journal write, and a slot in every prompt surface (the plan schema plus seven rendered surfaces, step 3). So deleting the ladder cannot delete the concept. Every new producer has to fetch a constant from disk and pass it along. Every prompt keeps telling the model "Your current evolutionary stage: awakening". The plan schema keeps asking how a change "moves you forward" along that ladder. The loop's own doctrine (`CLAUDE.md`, "Respect the stage model; don't skip stages or rush advancement") still tells every implementer to honour a ladder that production pinned dormant on 2026-08-15.

The class keeps spawning new cases. Proposal 144's framing resolver (2026-10-04) had to accept `stage` and `stage_progression_enabled` parameters. Proposal 146's scouting triage (2026-10-06/07) had to add a `stage_reader` callback. Both are brand-new code paying a tax for a concept retired seven weeks earlier. Separately, the dual posture of the dormant lever turned the loop's own quality gate red while CI stayed green (650a46cc). It then took three successive test-side fixes to contain.

The change has three parts. First, remove the stage label from every prompt surface behind `stage_progression_enabled`, which production runs off. Second, rename the plan's `expected_stage_impact` to an outcome-framed `expected_impact`, keeping the content hash byte-stable so no pending approval is invalidated. Third, delete the `stage` field and parameter from the journal, plan, and self-model types and their write APIs. The loaders' existing known-field filter drops the legacy key on read, so no state file is rewritten. Before any of that, a declarative retired-concept registry with a shrink-only per-file ratchet lands. It stops the concept spreading into new code on day one and reaches zero as the steps land. This is the 087 shape applied to a vocabulary instead of an oracle: one owner of the fact "this concept is retired", enforced by an AST guard instead of by reviewers noticing.

The end state: no record, prompt, write API, or doc names an evolutionary stage. Legacy JSONL rows keep their `stage` key on disk and lose it on read. The registry gives the next retired concept a slot; 149 Step 2 adds the purpose-hypothesis concept (`_PURPOSE_HYPOTHESIS`) as its second entry.

## Implementation Plan

The failure class: **a retired concept stays a required parameter of the persistence and prompt APIs, so deleting its machinery cannot delete it — every new producer re-threads it, every prompt keeps broadcasting it, every fixture keeps pinning it.** The design closes it with one owner of "retired", a ratchet that only shrinks, and the removals that drive it to zero. Prompt-visible changes ride the `stage_progression_enabled` lever rather than a new flag, so no new mole is minted. Field and parameter deletions follow 149 Step 2, which deletes that lever. Retirement steps come last.

### Phase A — The owner and the ratchet (no behaviour change)

1. [x] **Retired-concept registry and shrink-only guard.** `tests/structural_guards.py`, new `tests/test_retired_concepts.py` — add a declarative `RETIRED_CONCEPTS` registry. Its first entry, `evolutionary_stage`, declares:
   - the retired identifiers (`Stage`, `STAGES`, `STAGE_PROMPTS`, `StageTransition`, `TRANSITIONS`, `assess_stage_readiness`, `advance_stage`, `stage_evidence`, `expected_stage_impact`, `stage_getter`, `stage_reader`);
   - the five rung string literals and the prose `evolutionary stage`;
   - the keyword `stage=` at call sites.

   Identifiers count wherever they appear as an `ast.Name`, `ast.Attribute`, or keyword; string constants count when they equal a retired identifier or rung literal (so a dict key `"expected_stage_impact"` is a hit).

   `maestro/flag_lifecycle.py` is exempted by module, since its `stage` is the flag-lifecycle axis. The guard walks `maestro/` with `ast`, counts hits per file, and compares them to a pinned `_RETIRED_CONCEPT_BASELINE` that may only shrink, mirroring `_ENTRY_HANDLER_BASELINE`. It includes a seeded negative control (a synthetic module adding `stage=model.stage` is flagged), a positive control, and a non-vacuity floor (the live tree must produce at least one counted hit while the baseline is non-zero).
   - *Depends on:* none.
   - *Acceptance:* adding a `stage=` keyword or a rung literal to any `maestro/` file fails the suite; removing one passes, and the test fails until the baseline is lowered to match (the ratchet only tightens).

## Testing Strategy

All tests use `mem_fs`, mock the SDK/provider seam, and patch `asyncio.sleep`; no real network, subprocess, or filesystem (CLAUDE.md Testing Principles).

- **The deterministic enforcement test (`tests/test_retired_concepts.py`).** The `RETIRED_CONCEPTS` guard runs over the live tree against `_RETIRED_CONCEPT_BASELINE`. It includes:
  - a seeded negative control: in-memory source carrying `stage=model.stage`, a `STAGES` reference, and a `"purpose_found"` literal, detected by `ast` per the `tests/test_fault_seeding.py` convention rather than by subprocess;
  - a positive control: the same source minus the hits;
  - a non-vacuity floor;
  - a module-exemption check proving `maestro/flag_lifecycle.py`'s `CutoverFlag(stage=...)` is not counted.

  After step 9 the same test asserts zero hits outside the one loader allowlist.
- **Prompt goldens (step 3).** For each of the seven surfaces (`_stable_identity_block`, both curation prompts, `get_recent_narrative`, the `update_self_model` field block, the remediation plan block, `plan_review_message`, the PR-body builder): lever-on output equals a pre-change golden byte-for-byte; lever-off output contains no rung literal and no `evolutionary stage`. This covers both branches of the lever.
- **Hash stability (steps 2, 4, 7).** `compute_plan_content_hash` over a fixture corpus spanning every `PlanStatus` and both legacy and new impact keys is pinned to recorded digests before and after each step. A Telegram callback carrying the pre-rename hash prefix is still accepted for an unrefined plan (`tests/test_plan_decision.py` shape).
- **Legacy-row tolerance (steps 5, 7, 8).** A `journal.jsonl` / `events.jsonl` / `evolution_plans.jsonl` / `self_model.json` fixture written in today's shape loads under the new types with the legacy keys dropped and no warning, and `ensure_schema()` advances the fingerprint without rewriting the file (the `tests/test_migration.py` pattern).
- **Selector and gate regression.** `_run_task_phase` selection order and the `GATE_CHAIN` decisions are unchanged with the label gone. Neither ever read it, and this test proves it.

## Risk Assessment

- **Prompt-cache invalidation (one-time).** Removing `stage=` from the stable identity slab changes the cached prefix once. Cost is a single cache miss per session, then steady state.
- **Approval-hash integrity (trust chain).** `expected_stage_impact` is reviewed content inside `compute_plan_content_hash`, and the hash binds dashboard 409s, Telegram button prefixes, and `update_plan_status`'s `expect_content_hash`. The rename keeps the value at the same canonical position, so digests do not move. Step 2's read-both-keys landing first means a revert of step 4 cannot strand a row. The hash-stability goldens are the control that proves it.
- **Unmeasured framing value.** The label could in principle prime the model usefully. Against that: in production it has been the constant `awakening` since at least 2026-08-11, so it carries zero bits and sits beside a `CHARTER_PROMPT` (149 Step 3) whose framing it contradicts.
- **Dependency on 149 Step 2.** Phases C–D need `stage_progression_enabled` removed and the machinery deleted. Until then, Phases A–B ship independently and the ratchet already stops new threading. If 149 Step 2 stalls, this proposal stalls at a strictly better state than today.
- **Operator-visible removals.** The dashboard status badge and the plan-card `Stage:` disappear, and `maestro status` drops its `Stage:` line. All three have displayed `awakening` for seven weeks.
- **Rollback.** Phase A is test-only. Phase B reverts by commit (step 3, label only; step 4, with step 2 keeping reads safe). Before 149 Step 2 the lever is coupled: deleting the production `stage_progression_enabled = false` line restores the label but also re-arms the priced `assess_stage_readiness` and `advance_stage`, so it is not a label-only rollback; after it, the label returns only by revert. Phases C–D are normal reverts. Legacy keys stay on disk in every append-only store, so a revert restores the field's values on read for historical rows.
- **Falsifiability.** The deterministic signal is `_RETIRED_CONCEPT_BASELINE` falling monotonically to zero, with no new module ever adding a hit (the 144/146 shape). In production, over the first 14 days with `evolve_every > 0` after step 3 is deployed (149 Step 0 sets it to 0) and once ≥ 20 plans are minted in them, against the plans minted in the 14 days before step 3 deployed (read retrospectively from `evolution_plans.jsonl` timestamps):
  - the share of newly minted plans whose `rationale` / impact text uses stage or telos vocabulary should fall toward zero;
  - `maestro measure-plan-mill`'s `themed_fraction` should not rise;
  - the "not needed" class in `maestro measure-rejection-classes` should not rise.

  The design has **failed** if any of these holds:
  - 113's no-regression readings (merged-plan rate, `_assess_criteria_outcome` met-rate) regress over that window;
  - plans keep citing the ladder after step 3. That would mean the frame enters from somewhere else, such as journal history, and Phase C must move ahead.

  Until that window opens, the deterministic `_RETIRED_CONCEPT_BASELINE` ratchet plus the prompt and hash goldens are the whole test.

## Out of scope

- **The `self_awareness` MCP server name.** A tool namespace (`mcp__self_awareness__*`) bound into tool-surface allowlists (`maestro/tool_surface.py`); renaming it is tool-gating churn, not stage retirement, and the server carries live tools.
- **`maestro/flag_lifecycle.py`'s lifecycle `stage`.** An unrelated axis (cutover / retain), explicitly exempted by module in the guard.

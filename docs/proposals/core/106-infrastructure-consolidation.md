## Description

> Status updated to shipped on 2026-09-18 by /plan-proposal — see [README.md](../README.md#shipped) for the landing record.

Four classes of hand-built infrastructure have accreted to the point where they cost more to maintain than the differentiated core they surround, and a bus-factor-1 maintainer owns every line forever. This proposal retires them for ecosystem primitives the project already depends on, in four independent phases that can land in any order:

- **A — Config.** A flat `Config` dataclass with 250+ scalar fields, a hand-maintained `(section, key) → (field, type)` mapping table, a bespoke overlay merge, and a `validate()` carrying ~179 `raise ValueError` guards — replaced by `pydantic-settings`, whose declarative field constraints and TOML/env sources subsume all of it. Pydantic v2 is already resident via FastAPI, so the dependency cost is ~zero.
- **B — State substrate.** A fleet of single-purpose JSON/JSONL sidecars, a SHA-256 fingerprint "migration" sweep, a JSON-file task queue, a JSONL cost time-series with hand-rolled window aggregation, and a per-call BM25 index rebuild — collapsed onto one SQLite store (FTS5 gives native BM25, retiring the `rank_bm25` dependency), keeping JSONL only where append-only greppability is the actual product (journal, decisions).
- **C — Oracle cluster.** Six-plus near-parallel PR-fact modules merged into one `pr_facts.py` with a shared timestamped-observation base, deleting two genuinely dead functions and the stale "inert this increment" docstrings.
- **D — God-methods.** `agent.run` (~1,800 lines) and `agent.run_loop` (~1,600 lines) decomposed into an explicit phase pipeline — continuing proposal 068's seam work, which extracted phase *clusters* into `maestro/loop/` but left the two god-methods themselves intact.

This proposal deliberately composes with, rather than duplicates, the adjacent architecture-review track: Phase B subsumes proposal 072's bounded-JSONL-growth concern and moots most of 073's config-flag lifecycle work by making unknown/dead keys a load-time error; Phase D extends 068. Each phase ships behind a flag with shadow-parity before cut-over, the same idiom proposals 087/097/098 used to land risky rewrites.

## Relevant Findings

- `maestro/config.py` (`Config`, `Config.validate`) — a flat dataclass of 250+ scalar fields whose `validate()` carries ~179 `raise ValueError` guards; `check_secrets` is layered on top. The dataclass defaults and the `maestro.toml` defaults are two parallel sources of truth for every setting.
- `maestro/toml_config.py` (`_TOML_TO_CONFIG`, `_deep_merge`) — a hand-maintained `dict[tuple[str, str], tuple[str, type]]` mapping ~250 `(section, key)` pairs to `(field, type)`, plus a hand-written overlay merge and a type-coercion ladder. Every new setting must be added in three places (dataclass field, mapping row, TOML default).
- `maestro/dashboard/routes.py` imports `pydantic` (`BaseModel`, `ValidationError`) — pydantic v2 is already a resident dependency via FastAPI, so `pydantic-settings` adds negligible weight.
- `maestro/search.py` (`bm25_rank`) wraps `rank_bm25.BM25Okapi` and rebuilds the index on *every* call (its own docstring notes this); consumed by `maestro/journal.py` (`search`) and `maestro/memory.py` (`search_plans`). It is a dependency wrapper with an O(N)-per-query rebuild, not hand-rolled ranking.
- `maestro/migration.py` (`ensure_schema`) — SHA-256-fingerprints dataclass field names and, on mismatch, re-reads/re-writes every state file through loaders that only filter unknown fields and coerce types. It performs no value transforms, so schema-on-read validation would obviate most of it.
- `maestro/task_queue.py` (`TaskQueue`) and `maestro/cost_tracking.py` (window-rate aggregation) — a JSON-file FIFO and a JSONL time-series with hand-rolled rolling-window aggregation; both re-implement "store records, read them back ordered, aggregate."
- `maestro/fileutil.py` (`atomic_write`, `file_lock`, `iter_jsonl_reverse`) — the shared JSONL primitives. Roughly fifteen single-purpose sidecar ledgers each do independent load-modify-write under `file_lock` with no cross-file transaction, so a crash between two writes can leave them disagreeing.
- Oracle cluster: `maestro/world_state.py` (`observe_pr_merge_truth`, `is_fresh`) and `maestro/pr_readiness.py` (`observe_pr_readiness`, `is_fresh`) share a verbatim-duplicated `is_fresh`; `maestro/owned_branches.py` (`push_already_discharged`) and `maestro/blocker_greenness.py` (`is_strictly_greener`) have no production call sites (deletion-safe), but are *not* globally unreferenced — each retains a dedicated test file (`tests/test_owned_branches.py`, `tests/test_blocker_greenness.py`) plus doc/docstring mentions, and `push_already_discharged` is still described as a live §5-push HANDOFF mechanism in `CLAUDE.md` and cross-referenced from a `remediation_tracker.py` docstring (its HANDOFF branch is itself stale — see Step 7). Several cluster modules' docstrings still read "deliberately inert this increment — nothing reads it yet" though they are now wired at multiple call sites.
- `maestro/agent.py` (`run`, `run_loop`, `_audit_self_model`) — `run` and `run_loop` are the two largest methods in the module, each sectioned by numbered comment headers (`# 4a`–`# 4d`) rather than functions; proposal 068 extracted phase clusters into `maestro/loop/` but did not touch these two bodies.
- Adjacent planned work: proposals 072 (bounded growth for unrotated JSONL), 073 (config-flag lifecycle — dead-flag detection), 071 (audit rule/sensor framework). Phases A/B of this proposal subsume or moot parts of 072/073; cross-reference, do not re-do.

## Testing Strategy

Every cut-over is guarded by a parity test before the legacy path is deleted: config (Step 1), state-store ordering/aggregation (Step 3), search ranking (Step 4), and per-oracle outputs (Step 6). The JSONL→SQLite migration (Step 5) gets a dedicated data-migration test that seeds records via `mem_fs`, runs the one-time conversion into an in-memory (`:memory:`) SQLite database, and asserts round-trip fidelity — honouring the CLAUDE.md rule against real filesystem I/O by never touching disk. Retirement guards assert the removed dependency, symbols, and flags are absent (`pyproject.toml` has no `rank_bm25`; `_TOML_TO_CONFIG` is gone; the dead oracle functions are unreferenced), each with a negative control. `pytest-timeout` budgets are respected; all externals (git/gh seams, clocks) stay mocked.

## Risk Assessment

This is the highest-blast-radius proposal in the tree — config and persistence underpin every module. Mitigations: each phase is independent and lands in any order; A and B ship default-off with shadow-parity required before cut-over; C and D are behaviour-preserving refactors gated by parity tests. The honest counter-tradeoff, which the review named explicitly: the project deliberately favours zero-dependency, greppable, human-auditable JSONL and a magic-free flat dataclass. Phase B trades line-level greppability for transactional coherence, and Phase A trades an introspectable flat struct for declarative validation — both are judgement calls, so they are reversible (keep a JSONL export path out of the store) and ship behind flags. The 100 %-coverage gate makes Phase D expensive, since every extracted stage must be fully covered; Phase D is therefore last and optional, and can be deferred indefinitely without blocking A–C.

## Migration

Phase B Step 5 is a genuine state-file migration. Provide a one-time, idempotent converter that reads the existing JSONL/JSON sidecars and writes them into the SQLite store, with a reverse export (`store → JSONL`) retained as the rollback path. The converter runs under the `[paths] sqlite_state_enabled` gate at startup, mirroring how `ensure_schema` runs today, and logs a loud, provenance-stamped summary of what it moved.

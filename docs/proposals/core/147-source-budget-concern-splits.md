## Description

> Status updated to shipped on 2026-10-11 by /impl — see [README.md](../README.md#shipped) for the landing record.

The tool-result frame cap (`tests/test_source_file_size.py`) is a correct
safety rule enforced through the wrong mechanism. Any `.py` file at or above
512 KiB is pinned to its **exact byte count**, and every change that shrinks it
is told to "lower its number in the same change". So the pin is snapped to zero
headroom after every shrink. File size is a fact that every edit changes, so
the pin becomes a shared counter that every PR touching the file has to
re-negotiate, and those PRs run in parallel and are merged with `main`
repeatedly. Most of these collisions are not discovered on the PR that grows
the file. They show up on whichever unrelated PR next merges `main`. The fix
is then forced on whoever is holding the red CI, and it is almost always a
trim: a comment condensed, a log detail dropped, an identifier shortened to
`tr` or `nb`. The file stays exactly as large and exactly as central as
before. The guard has turned file size into a deterministic CI red that
recurs, that nobody owns, and whose cheapest cure makes the code worse.

The failure class: **a module accretes toward a size wall it cannot see
coming, and each contact with the wall is cleared by an ad-hoc byte trim or a
duress-driven extraction instead of a planned split.** It has three structural
roots. (1) The **ratchet has zero slack and is per-byte**, so it creates a
merge race. (2) There are **two gravity wells**: `MaestroAgent` is one 660 KB
class with 183 methods, and `EvolutionEngine` is one 420 KB class with 94
methods. Every new feature needs a call site in them, so growth piles up there
instead of spreading out. (3) **No early feedback.** A file is invisible until
it is already pinned, and the instant it crosses the watch threshold it is
pinned at zero headroom. A fourth root raises the cost of every split: 959 test
patch targets name `maestro.agent.<symbol>`. That ties each symbol's home to
`agent.py` and forced every extraction since proposal 068 to thread a
call-time `_agent_module()` lookup.

This proposal replaces the mechanism, not the safety rule. One owner,
`maestro/source_budget.py`, owns the frame-derived ceiling and a single
**split budget** set well below it. Interim pins sit on a coarse grid, so they
stop being exact-byte counters. A zero-cost **split-due sensor** names a file
weeks before it reaches the budget. The gravity wells are then split along
the concern seams their own method clusters already draw, with tests following
their modules. Once every file is under budget, the per-file pin table, the
watch threshold, the dead over-ceiling grandfather and the `_agent_module`
shim are deleted. In the end state there is one budget, no pins, and the wall
is announced before anyone reaches it.

## Relevant Findings

- `tests/test_source_file_size.py` (`_SIZE_BASELINE`, `test_pinned_file_may_only_shrink`) — four files are pinned at exact byte counts (`maestro/agent.py` 723_260, `maestro/evolution.py` 517_417, `tests/test_agent.py` 697_771, `tests/test_audit_checks.py` 607_106). The module comment instructs "lower its number in the same change", which snaps the pin to the file's size after every shrink.
- `tests/test_source_file_size.py` (`_WATCH_THRESHOLD`, `test_upper_band_files_are_pinned`) — a file that crosses 512 KiB must gain a baseline entry. In practice that entry is its current size, so it is pinned at zero headroom the moment it becomes visible.
- `tests/test_source_file_size.py` (`_OVER_CEILING_GRANDFATHERED`, `test_grandfathered_files_still_fit_the_frame`) — this has been dead since proposal 106 pulled `maestro/agent.py` below the derived `_HARD_CEILING` (806,596 B, ~788 KiB). The frozenset is empty, so the test loops over nothing.
- `tests/test_source_file_size.py` (`test_expansion_allowance_covers_the_measured_worst_case`) — it measures the encoding expansion only over `_SIZE_BASELINE` keys. Deleting the pin table needs a replacement sample (the N largest files).
- `maestro/agent.py` (`MaestroAgent`) — the class is 660,901 of the file's 723,004 bytes and has 183 methods. The five largest (`_audit_self_model` ~60 KB, `run_loop` ~57 KB, `contemplate` ~47 KB, `implement_plan` ~47 KB, `__init__` ~43 KB) add up to ~254 KB. Comments (~185 K chars) and docstrings (~143 K chars) make up ~45% of the file. That prose is exactly what the trims delete.
- `maestro/evolution.py` (`EvolutionEngine`) — 420,371 of 517,383 bytes, 94 methods. It holds three separable clusters: PR tending (`tend_evolution_prs`, `_tend_single_pr`, `_reconcile_orphan_branches`, `TendPRsResult`, thread-selection helpers), the submission door (`submit_for_review` ~44 KB plus its grounding verdicts), and the quality/self-review pipeline (`self_review`, `run_quality_gates`, `converge_to_green`, `_converge_rounds`, `_run_auto_fix_query`, `_find_uncalled_symbols`). `tests/test_evolution_tend.py` already exists as a split test home with no matching production module.
- `maestro/audit_checks.py` — a flat module of top-level rule, measure and format functions plus the `JsonlSettledVerdictsLedger` settlement backend, 491,798 bytes. It is not pinned yet, but it is on course to be (see Production Evidence).
- `maestro/loop/__init__.py` (`_agent_module`) — "seam functions historically patched as `maestro.agent.<name>` are looked up on the agent module at call time so existing patches keep intercepting them". There are 30 `_agent_module()` calls under `maestro/loop/` (48 grep lines, counting docstrings and imports). Tests carry 959 `maestro.agent.<name>` patch strings over 56 distinct names.
- `maestro/gate_scope.py` (`_paired_test_stems`, `_matches_stem_family`) — test selection is keyed on the changed module's stem family, plus one import hop. A split that keeps `<parent>_<concern>` stems (e.g. `evolution_tend` → `test_evolution_tend*`) stays narrowable. A split into differently named modules relies on the import hop alone.
- `tests/structural_guards.py` and `tests/test_no_silenced_exceptions.py` (`_ENTRY_HANDLER_BASELINE`, `_DEBUG_SWALLOW_BASELINE`) — these registries key entries on file name plus symbol, and proposal 106's increments moved them alongside the bodies. Count-based ratchets like these do not race, because unrelated edits do not change a count. Byte-based pins do race.
- `docs/proposals/core/106-infrastructure-consolidation.md` (Phase D) — shipped. After the pin landed, 106 established the module-level `fn(agent, ...)` sibling under `maestro/loop/` as "the shape every further extraction must take". It decomposed `run` but left `run_loop`, `contemplate`, `_audit_self_model`, `implement_plan` and `__init__` in the class. This proposal reuses that shape and extends it to the remaining wells and to `evolution.py` / `audit_checks.py`.

The duress siblings above are *kept*: they are reasonable homes. The design stops the duress, not the siblings.

## Implementation Plan

### Phase A — One owner and a regime with slack

1. [x] **Introduce the source-budget owner.** New `maestro/source_budget.py`; `tests/test_source_file_size.py`. Add `SPLIT_BUDGET` (384 KiB, about half the derived ceiling), `SPLIT_DUE` (320 KiB), a `SourceBand` enum (`OK` / `SPLIT_DUE` / `OVER_BUDGET` / `OVER_CEILING`), and a pure `read_source_budget(root, scanned_dirs) -> list[SourceBudgetReading]` that walks the filesystem like the current test does. The test becomes a thin consumer with unchanged assertions. No pin values or thresholds change.
   - *Depends on:* none.
   - *Acceptance:* `tests/test_source_file_size.py` imports every constant from `maestro.source_budget` and defines none of its own; a new `tests/test_source_budget.py` covers each band boundary on synthetic sizes via `mem_fs`.
2. [x] **Grid-quantize the interim pins; delete the dead grandfather.** `tests/test_source_file_size.py`. Interim pins must be multiples of `PIN_GRID` (16 KiB). Each current pin is rounded *up* to its grid line once (`agent.py` → 720 KiB, `evolution.py` → 512 KiB, `test_agent.py` → 688 KiB, `test_audit_checks.py` → 608 KiB), all still below `HARD_CEILING`. From then on a pin may only be lowered to a grid line, and only in a split step. Delete `_OVER_CEILING_GRANDFATHERED` and `test_grandfathered_files_still_fit_the_frame`, which are empty since 106. This is a one-time raise of at most ~15.5 KB per file (the largest is `test_audit_checks.py`, +15,486 B), not a cap bump as remedy. The evidence shows the exact-byte pin itself causes the merge race (`b7db289d`, `69ec9d73`) and the trims. The ceiling the pin protects does not move. The grid buys little time for the fastest grower (`evolution.py` gets 6,905 B, about two days at ~3.3 KB/day), so Steps 4–5 are sequenced immediately after Step 2. Until a file's split lands, a PR that would push it past its grid line moves its addition into the split's target module ahead of schedule (a concern-aligned early extraction under the `<parent>_<concern>` name), never a trim and never a pin raise.

   - *Acceptance:* a guard test fails if any `_SIZE_BASELINE` value is not a multiple of `PIN_GRID`, and a seeded off-grid value in the test's own fixture proves the guard fires.

## Testing Strategy

- **`tests/test_source_budget.py` (new):** band classification at each boundary (`SPLIT_DUE - 1`, `SPLIT_DUE`, `SPLIT_BUDGET`, `HARD_CEILING`), `read_source_budget` over a `mem_fs` tree (scan roots, non-`.py` skipped, nested packages included), and `encoded_tool_result_size` on escape-heavy content. No real filesystem.
- **`tests/test_source_file_size.py`:** stays the deterministic enforcement test, a filesystem walk of the real tree, as today. It gains the grid guard (Step 2) and later collapses to the single-budget assertion (Step 13). Each guard carries a seeded-fault control in the house style (`tests/test_fault_seeding.py`), so it cannot pass vacuously.
- **Sensor (Step 3):** contemplate measured-data tests with the flag off (byte-identical block), on with no file at `SPLIT_DUE` (line absent), and on with one (exactly one line). The CLI test uses `mem_fs` and a mocked `git log` subprocess, plus a `--json` shape test.
- **Phase B / C refactors:** behaviour-preserving by construction. The acceptance check per step is the existing suite with only patch-target repoints, plus the AST chokepoint guards in `tests/test_structural_guards.py` resolving to the new owners. Collected-node counts are compared per split PR so no test is silently dropped.
- **`_agent_module` ratchet (Step 11) and patch-home resolution (Step 12):** AST tests over `maestro/loop/` and `tests/`, each with a seeded violation.
- **Directive bridge (Step 14):** fills only an empty slot, does not refire while the slot is occupied by the same directive, self-extinguishes below `SPLIT_DUE`, and is a no-op with the flag off.

## Risk Assessment

- **Large mechanical moves conflict with in-flight PRs.** Mitigation: one cluster per PR, landed through the proposal 128 merge queue, sequenced when open PRs touch the cluster least. Delegators on `MaestroAgent` / `EvolutionEngine` keep external call sites stable, so a conflicting PR rebases onto a one-line body.
- **Patch-target repoints silently stop intercepting.** A test that patches the old home of a moved symbol would test nothing. Mitigation: Step 12's AST resolution test catches exactly that, and until it lands each Phase B step greps its moved names in `tests/`.
- **`gate_scope` narrowing drifts.** New module names outside the parent's stem family would rely on the import hop alone. Mitigation: the `<parent>_<concern>` naming rule, and a `maestro gate-scope` check on one moved path in each step's PR description.
- **Registries keyed by file name** (`tests/structural_guards.py`, `_ENTRY_HANDLER_BASELINE`, `_DEBUG_SWALLOW_BASELINE`, `_ENTRY_DOC_ANCHOR`) must move with the bodies. Each is enforced by its own test, so a missed move is a red, not a silent hole. 106 did this 8 times.
- **The new 384 KiB budget is a wall too.** Two PRs that each fit can still combine past it. That collision can now happen once per file per split cycle, preceded by ≥ 64 KiB of `SPLIT_DUE` warning (≈ 20 days at the fastest measured rate). Today it can happen on every edit.
- **Rollback:** Step 2 is a revert-safe test-only change. Steps 3 and 14 are flag-gated default-off. Phase B/C steps are behaviour-preserving moves, each revertible on its own. Step 13 reverts by restoring the pin table, since the pins would all be absent and every file under budget.

## Out of scope

- **`maestro_review/` and `maestro_sdk/`.** Not scanned by the frame guard today and not near the ceiling. They can adopt `maestro.source_budget` later.
- **Raising the SDK transport's 1 MiB frame** (a larger `max_buffer_size`). That is the forbidden bump-the-cap remedy. It would remove the danger the guard protects against but leave the gravity wells and the trims in place.
- **Non-`.py` files** (`CLAUDE.md`, `docs/*.md`). Their size pressure is a prompt-context concern owned by the "Context bloat caps" invariant, not by the tool-result frame.
- **Re-homing the duress siblings** (`maestro/question_eviction.py`, `maestro/plan_review_message.py`, `maestro/plan_feedback_fold.py`, `maestro/prompts/grounded_planning.py`, `audit_checks.stale_repeat_introspect_kwargs`). They are serviceable homes, and moving them again is churn with no class-closing value.
- **Restoring the comments and log detail the trims removed.** Worth doing opportunistically inside each Phase B move. It is not a separate step.

## Falsifiability

- **Improves if right:** commits whose message concerns pin compliance (`git log --grep` for size pin / re-pin / shrink-only pin) fall from **18 per 21 days** (12 pure-compliance) to **0 per 30 days** after Phase B (Steps 4–9); between Step 2 and then, grid-line contacts resolve by early extraction, never by trim. CI reds on `tests/test_source_file_size.py` reported in `task_history.jsonl` / `messages.jsonl` fall to 0. Operator plan feedback that cites pin headroom (2 on 2026-10-05) falls to 0. The `maestro source-budget` read shows every file below `SPLIT_DUE` after Step 13.
- **Shows the design failed:** a split module re-crosses `SPLIT_DUE` within 30 days of its split, which means the seam was drawn by bytes rather than concern and growth did not spread out. Or the first time a file reaches `SPLIT_BUDGET`, it happens with fewer than 14 days between its `SPLIT-DUE` sighting and the breach, which means the sensor's lead time does not cover real growth rates.

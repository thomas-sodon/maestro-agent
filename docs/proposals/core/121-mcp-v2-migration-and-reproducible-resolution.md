## Description

The in-process MCP shim (`maestro/inproc_mcp.py`) is written against the `mcp` 1.x low-level `Server` API: it registers handlers with the `@server.list_tools()` / `@server.call_tool()` decorators and returns the wire shape `{"type": "sdk", "name": ..., "instance": server}` that `claude-agent-sdk`'s client dispatches against `server.request_handlers`. `mcp` 2.0.0 rebuilt that low-level `Server` around a shared dispatcher engine and removed the decorators — so a clean-room build that resolves 2.x crashes at agent construction with `AttributeError: 'Server' object has no attribute 'list_tools'`. Issue #3588 stops the bleeding by capping `mcp<2`; this proposal is the forward migration that lets that cap be lifted.

The change does two coupled things. First, it moves the shim to the `mcp` 2.x low-level API (constructor `on_*` handlers, typed result returns, snake_case `input_schema`, explicit in-handler validation and error results), validated end-to-end against `claude-agent-sdk`'s actual consumption of the `Server` instance rather than against the shim in isolation. Second, it closes the reason the break reached production undetected: the clean-room Docker build (`pip install --no-cache-dir`) and the self-hosted CI runner (persistent site-packages, `pip install` without `--upgrade`) resolved *different* `mcp` versions, so CI stayed green while the deploy broke. A committed constraints file consumed by both paths makes resolution reproducible.

The end state: the shim runs on a pinned `mcp` 2.x range; a deterministic wire-contract test dispatches a real `list_tools` + `call_tool` round-trip through the shim so an incompatible `mcp` bump fails at test time, not deploy time; and Docker and CI provably resolve the same dependency set, so "green CI, red deploy" from a silent version divergence cannot recur for `mcp` or any other unbounded pin.

## Relevant Findings

- `maestro/inproc_mcp.py` (`create_inproc_mcp_server`) — constructs `Server(name, version=version)` and registers `_list_tools` / `_call_tool` via the 1.x decorators `@server.list_tools()` / `@server.call_tool()`; the `@server.list_tools()` call is the exact failure site under 2.x.
- `maestro/inproc_mcp.py` (`create_inproc_mcp_server`) — returns `{"type": "sdk", "name": name, "instance": server}`; the module docstring states the SDK client "pulls `config["instance"]` and dispatches `ListToolsRequest` / `CallToolRequest` directly off `server.request_handlers`." That `request_handlers` coupling is an assumption about `mcp`'s internal `Server` shape *and* about how `claude-agent-sdk` consumes it — neither is a versioned public contract.
- `maestro/inproc_mcp.py` (`tool`, `InprocTool`) — every shim consumer (`maestro/tools.py`, `maestro/telegram_tools.py`, `maestro/email_tools.py`, `cli._build_agent_tools`) passes `InprocTool` lists and never imports `mcp` directly, so the entire `mcp`-API coupling is concentrated in this one module plus the stdio serve path. Consumers are insulated: migrating the shim's internals leaves them untouched *iff* the returned wire shape still dispatches.
- `maestro/cli.py` (`_serve_mcp_over_stdio`) — the hidden `maestro _mcp-serve` path calls `server.run(read_stream, write_stream, server.create_initialization_options())` from `mcp.server.stdio.stdio_server`; these low-level run-loop symbols must be re-verified under 2.x alongside the handler API.
- `pyproject.toml` (`dependencies`) — pins `mcp>=1.27.0` (unbounded ceiling before #3588) and `claude-agent-sdk>=0.2.87`; `claude-agent-sdk 0.2.87` metadata requires `mcp>=1.23.0`, also unbounded. Nothing in the tree caps `mcp` below 2.0, and `claude-agent-sdk` builds its own `Server` — so the migration is only safe once `claude-agent-sdk`'s `Server` consumption is confirmed compatible with (or bumped to support) `mcp` 2.x.
- `Dockerfile` — `pip install --no-cache-dir ".[dev,email]"` resolves into a clean image; `.github/workflows/quality-gates.yml` runs `runs-on: self-hosted` and installs with `pip install -e ".[dev,email]"` (no `--upgrade`) into a persistent environment. Its own install-step comment warns about "a prior job's editable install leaking through shared self-hosted-runner state" — the persistent-env hazard is already known, and it is exactly what masked the `mcp` drift.
- `tests/test_inproc_mcp.py` (`test_create_inproc_mcp_server_returns_sdk_wire_shape`) — asserts the returned dict shape but imports and exercises `mcp.server.Server` from whatever version is installed; on the self-hosted runner that was 1.27.0, so the suite could not have caught the 2.x break.
- `tests/test_cli.py` (imports `create_connected_server_and_client_session` from `mcp.shared.memory`) — an in-memory connected server/client harness already exists in the suite and is the natural reuse point for a real dispatch round-trip test.

## Prior Point Fixes (whack-a-mole ledger)

| Identifier | What it patched | Why the class survives it |
|---|---|---|
| Issue #3588 (`pyproject.toml` `mcp>=1.27.0,<2`) | Caps `mcp` below the breaking major so clean-room builds stop resolving 2.x | Freezes `mcp` at 1.x forever; leaves the unbounded-pin + persistent-CI-masking pattern intact for every other dependency; does not restore forward mobility |
| `.github/workflows/quality-gates.yml` install-step comment (self-hosted leak guard) | Explicitly installs `maestro_sdk` first to stop "a prior job's editable install leaking through shared self-hosted-runner state" | Documents the persistent-env hazard but does not make resolution reproducible — the same shared state silently pinned `mcp` at 1.27.0 and hid the 2.x break |

This proposal **retires** the emergency `<2` cap (superseded by a proper pinned 2.x range once the migration lands) and the shim's reliance on the private `request_handlers` wire shape (replaced by an end-to-end validated dispatch contract). It is honest that the production ledger is one incident deep: the structural justification is the resolution divergence, not a long fix trail.

## Testing Strategy

- **`tests/test_mcp_wire_contract.py` (new, unit).** The chokepoint: a real in-memory `list_tools` + `call_tool` round-trip through the shim via `create_connected_server_and_client_session`. Covers the success path (catalog returned, tool text returned), the unknown-tool guard (error result / `is_error`), and a tool whose handler raises (explicit error result now that 2.x drops auto-conversion). This is the test that turns a future `mcp` API break into a red unit test instead of a red deploy.
- **`tests/test_inproc_mcp.py` (updated).** Keep the wire-shape assertion (`{"type": "sdk", "name", "instance"}`) and update the `mcp.types` imports/fields to the 2.x surface (`input_schema`, `ListToolsResult`).
- **`tests/test_tool_adapter.py`, `tests/test_cli.py` (updated).** Repoint the `mcp.server.Server` / `mcp.types` imports and the stdio serve assertions to 2.x symbols; assert `_serve_mcp_over_stdio` still runs the 2.x server.
- **Reproducibility check (step 4).** A test or CI step comparing the Docker-resolved and CI-resolved `mcp` versions. All tests honour CLAUDE.md rules: `mem_fs` for any I/O, no real network/sleep/subprocess, mocked externals; the connected-server harness is in-memory, not a socket.

## Risk Assessment

- **`claude-agent-sdk` incompatibility (highest risk).** The shim's `request_handlers` wire shape is consumed by `claude-agent-sdk`, which pins `mcp>=1.23.0` and builds its own `Server`. If `claude-agent-sdk 0.2.87` dispatches against 1.x-only internals, `mcp` 2.x may break the SDK independently of our shim. Step 1 resolves this before any code changes; if a `claude-agent-sdk` bump is required, it becomes an explicit dependency of step 5 and the `<2` cap simply stays until it lands. Mitigation: the whole migration is gated on the step-2 contract test passing under 2.x end-to-end, not on the shim compiling.
- **Silent dispatch regression.** 2.x removes auto-wrapping and auto exception→error conversion, so a mechanically-ported handler could return the wrong shape and fail only at runtime. Mitigation: the step-2 contract test dispatches real requests and asserts on the returned content and error flags, covering exactly these branches.
- **Rollback posture.** Steps 1–4 are safe with the `<2` cap still in place (the contract test and constraints file are additive; the shim migration can sit behind the cap until step 5 flips the pin). If step 5 regresses, reverting `pyproject.toml` to `mcp<2` restores the working state, and the deploy's own smoke-test-and-rollback harness (which already caught #3588) is the outer backstop. No state-file or schema migration is involved.
- **Trust chain.** Untouched — this is an SDK-integration and build-reproducibility change; no approval, sandbox, or public-API surface is modified.

## Out of scope

- Migrating to the 2.x high-level `MCPServer` (formerly `FastMCP`) API. The shim deliberately uses the low-level `Server` to control the wire shape `claude-agent-sdk` consumes; a high-level rewrite is a larger, separate change.
- Pinning or lockfile-managing the `maestro_sdk` / `maestro_review` sibling packages, which install separately (packaging boundary) and do not depend on `mcp`.
- Broadening the constraints file into a full lockfile-managed environment for every transitive dependency; step 4 pins the direct dependencies that caused the divergence, and a full lock is a follow-up if drift recurs elsewhere.

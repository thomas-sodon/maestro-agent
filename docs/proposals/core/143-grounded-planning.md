## Description

> **Burn-in.** Partially completed — all behaviour-code has landed and runs behind its flag; what remains is the burn-in observation window, then graduating the flag and decommissioning the retired logic. See [README.md](../README.md#status-key).

The evolution planner is asked tree questions and cannot see the tree. `propose_plan`'s prompt tells it to "check whether the existing codebase, the standard library, or an already-installed dependency already provides it". Its output schema requires `files_affected`. Under `plan_grounding_enabled`, which is on in production, it must also author a grounding probe that names a file `locator` and an `expectation` to find in that file. Yet `reflect`, `propose_plan`, `propose_plan_chain` and `curate_pending_plans` all run `tools=[]`: the blanket "pure-text sessions need no tools" decision of 01bb6853 (2026-04-22), made enforcing when 8a94bcde (2026-05-10) swapped the inert `allowed_tools=[]` for `tools=[]`. The loop also never feeds it `CLAUDE.md` (`claude_md_guidance`'s own docstring). Every symbol, path and "this does not exist yet" claim in a plan is therefore recalled or invented. The class: **the planner is required to state facts about the tree while being structurally denied any way to read it, so tree-checkable errors are produced at the source and then refused, one shape at a time, downstream.**

Production shows both halves of that. Since 2026-08-16, 60 of the 106 human-rejected plans (57%) were rejected for something one read of the tree settles: "already implemented", "false premise", or "wrong module / nonexistent symbol". The reviewer's rejection usually quotes the one grep that settled it. For example, "`cmd_pr_owed_act` (maestro/cli.py) does `from maestro.audit_checks import … load_settled_prs`". The planner knows it is blind, too. In seven `propose_plan` transcripts it tried to read the code (`cat maestro/pr_owed_act.py`, `grep -n "_cli_grounding_verdict…"`, `Read pr_remediation.py`), was refused, and emitted a plan anyway. On 2026-09-26 it said: *"I cannot read the tree to over-specify a fix site — and my rejection history punishes exactly that (ungrounded symbols, phantom paths)."* Proposal 114's door-side grounding has been on in production since 2026-09-14. Over that window it refused 5 plans while humans rejected 14 more for tree-checkable reasons. That is expected, because the planner authors its own probe without having read the file the probe names.

The remedy moves grounding from the consumer to the producer. One owner, `maestro/tree_retrieval.py`, defines a bounded read-only tree surface in proposal 132's proven shape: an in-process MCP server of pure read tools (`read_source`, `grep_source`, `find_definition`, `list_cli_surface`), confined to the work-target tree by the same confinement 114's `_read_grounding_tree_text` already enforces. It is inclusion-by-allowlist, has no shell and no built-in tools, and carries a hard call budget and a per-result cap. Behind `[loop] grounded_planning_enabled`, the planner callers run on that surface through `single_use_call`. Each plan then records which paths and symbols the planner actually read, so a sensor can tell "read and still wrong" apart from "never looked". 114's door `confirm` then reads through the same owner. Once the rejection metric proves the effect, the door-side grounding checks built for the blind planner shrink to a backstop, and the CLI-evidence guard with its #4109 exemption is deleted. In the end state the planner looks before it claims, the human stops acting as the grep of last resort, and grounding has a single reader rather than a growing list of refusal gates.

**Relationship to 136.** Proposal 136 targets the same class by *pushing* a precomputed reality inventory (registry-derived capability names) into the prompt and refusing mints that collide with it. Two things set this proposal apart. It *pulls*: the planner reads the files and symbols its plan actually concerns. That reaches the "wrong module" and "false claim about how this function behaves" rejections (31 and 22 in the window), which a name inventory cannot represent. It also adds no refusal gate. This proposal supersedes 136's Phase B (prompt injection), and 136 has struck its step 3. 136's Phase A inventory has landed, so step 4 here exposes it as the `read_reality_inventory` read tool rather than as a prompt appendix. 136's Phase C clearance (its `problem_ref` / `new_capability_names` fields and the `[ungrounded-generation:<reason>]` door refusal) is judged on its own evidence and runs concurrently. The two proposals divide the door-guard retirement with no overlap: step 8 here owns `_evidence_cli_grounding_verdict`, `_cited_cli_tokens`, the #4109 exemption and 114's probe, and 136's step 5 owns `_cli_grounding_verdict`. 136's `reality_inventory` reads the tree through this proposal's owner, so its derivation-owner guard nests inside the reader-chokepoint guard landed in step 5. Because 136's clearance may run in the same window, step 5's reader splits refusals by reason tag and step 7 attributes the metric accordingly. Every shared concern and its single owner is listed in [Coordination with 136](#coordination-with-136).

## Implementation Plan

### Phase 1 — Measure (no behaviour change)

1. [x] **One owner of confined tree reads.** New `maestro/tree_retrieval.py`, `maestro/evolution.py` (`_read_grounding_tree_text`) — extract 114's workspace confinement (work-target root, reject absolute / `..`, readable-text only) into `tree_retrieval` as the single tree reader. The owner exposes two entry points over that confinement. ### Phase 2 — Ground the producer (flag-gated)

## Risk Assessment

- **Cost and latency.** Each read is a turn. Mitigations: the hard `MAX_TREE_TOOL_CALLS` budget and per-result cap, the throttle degrade to tool-free, the canary on two callers before `curate_pending_plans`, and a 2× cost tripwire. A human rejection is already a spent reflect+propose pair plus operator attention, so the comparison is against that, not against zero.
- **Reading is necessary, not sufficient.** The planner may read and still misclaim. Step 5's `[planner-read]` / `[planner-unread]` split measures exactly that. If `[planner-read]` refusals dominate, the proposal has falsified its own premise, the flag reverts, and the evidence points at 136-style clearance or reasoning.
- **Trust chain.** Read-only by construction: an in-process server of pure reads, `tools=[]` kept (no `Bash`, `Read` or `Write` built-ins), and no action-gate interaction. Secret exposure is bounded by the allowlist, which excludes `data/`, `.env*` and `.git/`, and admits only committed `maestro*.toml` overlays, which `tests/test_overlay_safety.py` already fences for hard-block secrets. Transcript sidecars will contain source excerpts. That is the repository's own public code, not state.
- **Session corruption on early exit** (the 01bb6853 concern) is handled for the JSON callers by the tool-loop-safe completion contract proven in 132. `reflect`'s text-completion variant is new work in step 4 and carries its own test.
- **Rollback.** Phase 1 is behaviour-neutral. Phase 2 sits behind a default-off flag with a byte-identical off-branch. Retirement (step 8) follows graduation only. `grounded_reads` is an additive nullable field handled by `ensure_schema()` normalisation.

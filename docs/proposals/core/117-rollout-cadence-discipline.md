## Description

> Status updated to shipped on 2026-08-26 by /plan-proposal — see [README.md](../README.md#shipped) for the landing record.

Maestro is a **fleet of one**: a single autonomous loop, with no in-production sub-population to canary against and lower environments (dev/CI/local) that cannot exercise the live loop's runtime paths at all. For such a system, environment divergence — turning a feature on in `production` but off in base — buys almost no safety (the behaviour still runs only in the one place it ever could) while it *costs* configuration drift between production and everywhere else. Rollout safety has to come from three other layers instead: the test suite (correctness, proven before merge), the flag as a runtime kill switch (instant, code-free revert), and live observability with tripwires (does the tested behaviour achieve its purpose under real conditions). The proposal-099 rollout took the environment-divergence shortcut, then graduated straight to base default-on; this proposal makes the *disciplined* path the default one and closes the hygiene gaps that shortcut exposed.

It matters now because the machinery to do this well already exists but is not wired into a cadence. `EXPERIMENTAL_FLAGS`, `PROD_ONLY_CANARIES`, and `CUTOVER_FLAGS` each carry a dated horizon whose crossing reds the build, and `maestro audit-flags` already computes a promote-or-delete recommendation per flag — yet nothing enforces that every opt-in flag *enters* that lifecycle, nothing steers a new feature away from the prod-only shortcut, and nothing surfaces an approaching horizon until CI reds. The result is a lifecycle that is well-instrumented at its edges and unguarded through its middle.

The end state: a new flagged feature ships **dark** (default-off in every environment, registered in `EXPERIMENTAL_FLAGS` with a horizon), is flipped on **everywhere in one reversible step** (config parity preserved, kill switch retained), is observed for a bounded window against written tripwires (a *temporal* canary — the only kind a single instance can run), and is then **collapsed** through proposal 111's `CUTOVER_FLAGS` path, deleting the flag and its now-dead off-branch. Environment divergence is reserved strictly for what must genuinely differ per environment (`PROD_ONLY_OPERATIONAL`: secrets, endpoints, limits), never for feature-gating. The two proposal-099 flags — already registered as `cutover` entries by the graduation PR — are the first pair driven end to end through that collapse.

## Relevant Findings

- `maestro/flag_lifecycle.py` (`PROD_ONLY_CANARIES`, `EnvOverlayCanary`) — environment divergence is today a first-class *feature-gating* mechanism, not just an operational one; `test_no_prod_only_canary_is_overdue` reds the build on a crossed `review_by`, but nothing distinguishes a legitimate observability canary from a feature that should simply have shipped dark everywhere. Proposal 099 reached for it by reflex.
- `maestro/flag_lifecycle.py` (`EXPERIMENTAL_FLAGS`) — the default-off opt-in manifest with `review_by` horizons. `tests/test_config_flag_lifecycle.py` (`test_every_experimental_flag_names_a_real_config_field`) enforces only the manifest→field direction (every manifest entry names a real `Config` field). There is no field→manifest completeness guard, so a new default-off feature flag can ship carrying no horizon at all and escape the forcing function entirely.
- `maestro/flag_lifecycle.py` (`CUTOVER_FLAGS`, `find_stage_violations`) — the collapse half (proposal 111). It now carries `base_advance_re_entry_enabled` and `unwinnable_race_escalation_enabled` at stage `cutover`, each its own `off_path_symbol`, so the build nags once the true-branch is inlinable — but the collapse *decision* is anchored only to a `review_by` date, with no binding to the proposal-099 observation window that should actually gate it.
- `maestro/flag_lifecycle.py` (`audit_flags_report`) and the `maestro audit-flags` CLI — already join the manifests against gate-activation counts and print a promote-or-delete horizon per flag. It is pull-only: an operator must run it. Nothing surfaces an approaching or crossed horizon on the loop's own cadence (e.g. in `contemplate()`'s measured-data block).
- `docs/proposals/TEMPLATE.md` (Implementation Plan section) — instructs authors to "gate behaviour changes behind a config flag where possible," but prescribes neither the dark-launch-everywhere default nor the collapse follow-through, leaving the prod-only-canary shortcut equally reachable to a future author or to Maestro itself.
- `docs/self-evolution.md` ("Base-advance re-entry (proposal 099)") — carries the observation-window and tripwire criteria (`BASE-ADVANCE-RACES` `race_won_ratio`, `[red-unread]` notes, per-landed-PR budget) that the proposal-099 collapse must clear before the flag and its off-path are deleted.

## Implementation Plan

Steps are independently mergeable and ordered so an interrupted run leaves a working tree. Steps 2–5 are pure guard/surfacing/doc additions; step 1 is the one behaviour change and is itself gated on an operator-confirmed observation window.

1. [x] **Collapse the proposal-099 flags once the window confirms convergence.** `maestro/config.py`, `maestro/toml_config.py`, `maestro.toml`, `maestro/flag_lifecycle.py`, `maestro/agent.py`, `maestro/evolution.py`, `maestro/pr_facts.py`, tests — delete the `base_advance_re_entry_enabled` / `unwinnable_race_escalation_enabled` fields and TOML keys, inline the flag-on branches in the give-up predicates and the audit block, and remove the two `CUTOVER_FLAGS` entries. This is the first pair driven end to end through proposal 111's collapse path; do it only after the `docs/self-evolution.md` observation window shows convergence and no tripwire fired.
   - *Depends on:* 111; the operator-confirmed observation window.
   - *Acceptance:* neither field exists on `Config`; the re-entry predicates and the unwinnable-race delivery run unconditionally; both `CUTOVER_FLAGS` entries are gone; `find_stage_violations` over the live manifest returns empty.
2. [x] **Add the field→manifest completeness guard.** `tests/test_config_flag_lifecycle.py`, `maestro/flag_lifecycle.py` — a test that every `Config` `bool` field defaulting to `False` is either registered in `EXPERIMENTAL_FLAGS` or named in an explicit, documented allowlist of non-experimental toggles, closing the direction the existing manifest→field guard leaves open. The allowlist keeps genuinely-static config toggles out of the lifecycle without letting a real feature flag slip through unmanifested.
   - *Depends on:* none.
   - *Acceptance:* seeding a default-off `Config` flag that is neither manifested nor allowlisted reds the new test; the current tree passes.
3. [x] **Demote environment divergence as a feature-gating tool.** `maestro/flag_lifecycle.py`, `docs/proposals/README.md` ("How to pick the category" / an authoring note) — freeze the current `PROD_ONLY_CANARIES` flag-set as a dated baseline and require any *new* entry to carry an explicit observability/operational justification (a new required field or a companion allowlist), so a feature can no longer be introduced as a prod-only enable by reflex; the documented default for a new feature becomes dark-launch-off-everywhere via `EXPERIMENTAL_FLAGS`.
   - *Depends on:* none. Composes with 116 (generator bounding).
   - *Acceptance:* a guard reds when a `PROD_ONLY_CANARIES` entry is added without the justification field; the authoring note states the dark-launch default.
4. [x] **Surface approaching horizons on the loop's cadence.** `maestro/agent.py` (`contemplate()`), reusing `maestro/flag_lifecycle.py` (`audit_flags_report`) — inject a zero-SDK-cost line into the `## Measured Behavioral Data` block when any flag is within a threshold of, or past, its `review_by`, self-suppressing when none is due. Turns the horizons from CI-reactive into proactively visible to the agent.
   - *Depends on:* none.
   - *Acceptance:* with a near-due flag (via an injected reference date) the measured-data block carries the horizon line; with none due it is absent; the computation makes no SDK call.
5. [x] **Encode the four-stage lifecycle in the scaffolding.** `docs/proposals/TEMPLATE.md`, `maestro/prompts/` (the proposal/plan nudge) — name the lifecycle explicitly (dark-launch off-everywhere → flip everywhere in one reversible step → bounded temporal observation window → `CUTOVER_FLAGS` collapse) so the default path an author *or Maestro* reaches for is the disciplined one rather than the prod-only canary.
   - *Depends on:* none.
   - *Acceptance:* `TEMPLATE.md`'s Implementation Plan guidance describes the lifecycle and the dark-launch default; the prompt nudge references it.

## Testing Strategy

- **Step 1 (collapse):** unit coverage that the give-up predicates and the audit delivery behave identically to today's flag-on path once the flag is removed (reuse `tests/test_base_advance_re_entry.py` and the `unwinnable_race` cases in `tests/test_agent.py`, dropping the flag-toggling); a `find_stage_violations` assertion that the manifest is clean after the entries are removed.
- **Step 2 (completeness guard):** a positive test over the real `Config`/manifest and a negative control that seeds an unmanifested default-off flag in-memory and asserts the guard fires — mirroring the existing seeded-field guards in `tests/test_config_flag_lifecycle.py`.
- **Step 3 (canary freeze):** a guard test with a negative control adding a justification-less `EnvOverlayCanary`.
- **Step 4 (horizon surfacing):** a `contemplate()`-level test with an injected reference date exercising both the near-due (line present) and none-due (line absent) branches, asserting zero SDK cost; `mem_fs` for all state, no real clock.
- **Step 5 (scaffolding):** if practical, a doc test that `TEMPLATE.md` names the lifecycle stages; otherwise manual review. Honour the CLAUDE.md rules — `mem_fs`, no real I/O, no real `sleep`, mocked externals.

## Risk Assessment

The blast radius is small: steps 2–5 are meta-guards, a zero-cost contemplation line, and documentation, each independently mergeable and revertable by deletion. The one behaviour change is step 1, which is *itself* a flag collapse and is gated on an operator-confirmed observation window; the flag-off fallback stays available as the kill switch right up until the collapse lands, so a regression discovered late reverts by restoring the flag rather than by an emergency deploy.

The main hazard is over-rigidity in step 3: a blanket freeze could block a legitimate future observability canary. Mitigated by making the control a *justification requirement*, not an absolute ban — a genuine operational or measurement-only canary can still be added, it just cannot be a feature-gate by default. Step 2's allowlist carries a symmetric risk (an over-broad allowlist would defeat the guard); mitigated by keeping the allowlist small, documented, and itself reviewed. No state-file or schema migration and no trust-chain surface is touched.

## What landed

- **Step 1 — collapse the proposal-099 flags.** The observation window confirmed convergence, so the two graduated cutover flags were collapsed to unconditional behaviour: the `base_advance_re_entry_enabled` / `unwinnable_race_escalation_enabled` `Config` fields, their `maestro.toml` keys, their `_TOML_TO_CONFIG` rows, and both `CUTOVER_FLAGS` entries are deleted; the base-advance re-entry predicates in `maestro/agent.py` and the unwinnable-race heads-up delivery now run unconditionally, with only the operational `unwinnable_race_re_entry_threshold` (int) retained. `find_stage_violations` over the live manifest is clean and `tests/test_base_advance_re_entry.py` / the `unwinnable_race` cases in `tests/test_agent.py` no longer toggle a flag. This drove the first pair end to end through proposal 111's collapse path.
- **Step 2 — field→manifest completeness guard.** `tests/test_config_flag_lifecycle.py` now partitions every default-off boolean `Config` field into a lifecycle manifest (`EXPERIMENTAL_FLAGS` / `PROD_ONLY_CANARIES` / `PROD_ONLY_OPERATIONAL`) or a documented `_UNMANIFESTED_DEFAULT_OFF` allowlist, with a self-cleaning tripwire and negative controls, so a new default-off feature flag can no longer ship carrying no review horizon.
- **Step 3 — demote environment divergence as a feature-gating tool.** `maestro/flag_lifecycle.py` adds the `EnvOverlayCanary.justification` field, freezes today's seven-flag `PROD_ONLY_CANARIES` set as the dated grandfathered `PROD_ONLY_CANARY_BASELINE`, and adds the pure `find_unjustified_canaries` detector; `tests/test_config_flag_lifecycle.py` guards that any *new* prod-only canary names an explicit observability/operational justification, with a self-cleaning baseline tripwire and a seeded negative control; `docs/proposals/README.md` gains the dark-launch-off-everywhere authoring note. A new feature can no longer be introduced as a prod-only enable by reflex.
- **Step 4 — surface approaching horizons on the loop's cadence.** `maestro/flag_lifecycle.py` adds the pure, clock-free `find_horizons_within` / `format_flag_horizon_summary` helpers (with the `_HORIZON_APPROACH_DAYS` window constant) that render a self-suppressing `FLAG-HORIZON` line naming `EXPERIMENTAL_FLAGS` entries within — or past (`OVERDUE`) — their `review_by`; `maestro/agent.py` (`contemplate()`) injects that line into the `## Measured Behavioral Data` block behind the default-off `audit_flag_horizon_display_enabled` flag (registered in `EXPERIMENTAL_FLAGS`, `Config`, and `maestro.toml`); `tests/test_agent_contemplate.py` covers the near-due, none-due, and gated-off branches at zero SDK cost. An approaching promote-or-delete horizon now reaches the agent on its own cadence rather than only as a late CI red.
- **Step 5 — encode the four-stage lifecycle in the scaffolding.** `docs/proposals/TEMPLATE.md`'s Implementation Plan guidance now names the four-stage lifecycle explicitly — dark-launch off-everywhere behind a default-off `Config` switch registered in `EXPERIMENTAL_FLAGS` with a dated `review_by` → flip on everywhere in one reversible step → observe for a bounded window → collapse via `CUTOVER_FLAGS` — and demotes environment divergence (`maestro.production.toml` / `PROD_ONLY_CANARIES`) to a justified operational need. The same `FLAG LIFECYCLE` nudge is mirrored into both reflection prompts (`EVOLUTION_PROMPT` / `EVOLUTION_PROMPT_EXTERNAL` in `maestro/prompts/defaults.py`, verbatim-identical, preserving the sibling parity) and the proposal-generation prompt (`DOC_PROPOSAL_PROMPT` in `maestro/prompts/doc_proposals.py`). `tests/test_template_names_flag_lifecycle.py` pins the template vocabulary (whitespace-normalised, with detector negative controls) and `tests/test_prompts.py` (`test_flag_lifecycle_nudge_present_in_generation_prompts`) pins the nudge in every generation prompt. The disciplined rollout is now the default path an author or Maestro reaches for, rather than the prod-only-canary shortcut.

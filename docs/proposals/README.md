# Maestro Evolution Architecture Review — Proposals

Architectural improvements identified through comprehensive review of Maestro's self-evolution implementation. Each proposal contains a description, relevant findings from the codebase, a detailed implementation plan suitable for a future agent, testing strategy, and risk assessment.

> **Paths changed 2026-04-25.** Open proposals were sorted into category subfolders (`core/`, `security/`, `publication/`, `audience/`). Filenames are unchanged; only the path prefix moved. Old links of the form `docs/proposals/NNN-slug.md` should be updated to `docs/proposals/<category>/NNN-slug.md` — see the table below.
>
> **Categories expanded 2026-04-25.** Four further subfolders were added: `research/`, `ux/`, `technical-plan/`, `operations/`. The prior top-level `docs/research/` directory was absorbed into `docs/proposals/research/` (files moved verbatim, directory removed). The decision tree under "How to pick the category" now has nine rules.

## Review Methodology

All core modules were reviewed (~5000+ lines): `evolution.py`, `agent.py`, `consciousness.py`, `purpose.py`, `dreaming.py`, `planner.py`, `executor.py`, `memory.py`, `sdk.py`, `vcs.py`, `tools.py`, `journal.py`, `config.py`, `migration.py`, `types.py`, `prompts/defaults.py`.

### Status Key

- **proposed** — Written, awaiting prioritization
- **approved** — Approved for implementation
- **in-progress** — Implementation underway
- **partial** — Some elements landed (e.g. shared infrastructure) but the core proposal is **awaiting full implementation** — the remaining Implementation-Plan steps still write new behaviour-code
- **burn-in** — **Partially completed but pending burn-in for full completion.** All behaviour-code has landed and is running behind its flag; what remains is the burn-in observation window, then graduating the flag (cut-over to default / collapse) and decommissioning the retired logic it supersedes. Distinct from `partial` — there is nothing new to build; the final graduation/decommission steps are deliberately human-gated on burn-in evidence and land via a separate review PR. A `burn-in` status is **not** a valid token on its own: it MUST carry one of the three substate suffixes below, naming where in the rollout the proposal sits, so the status column shows the position at a glance instead of leaving it to hand-maintained prose.
  - **`burn-in:ready`** — behaviour-code landed and gated, but the observation window has **not started**: no canary is deployed and the flag is default-off everywhere (no `maestro.production.toml` canary section enables it).
  - **`burn-in:observing`** — the canary/flag is **live** in production (flipped on, e.g. via a `maestro.production.toml` canary section) and the bounded observation window is running, with evidence accruing against the proposal's written tripwires.
  - **`burn-in:graduated`** — the flag has cut over to its target default (or the observation evidence is in); the only remaining work is **decommissioning** the superseded logic the landed path replaced.

  The existing bare-`burn-in` rows in the Open Proposals table were reconciled to these substates (proposal 123, Phase B), so the no-bare-`burn-in` rule is not treated as retroactively violated by rows written before it.
- **shipped** — Fully implemented; row appears in the Shipped table above and is removed from Open Proposals (the proposal file itself is retained for history)
- **superseded** — Shipped, then retired by a later proposal; the file is retained for history with a pointer to its successor
- **deferred** — Postponed to a future cycle

## Authoring new proposals

This folder is the durable record of architectural decisions worth remembering — and the slot Maestro will populate when a task outcome surfaces a finding worth keeping. Use [`TEMPLATE.md`](TEMPLATE.md) as the starting skeleton.

### When to write one

- A task outcome surfaced an architectural change worth committing to.
- A recurring failure pattern was observed and a structural mitigation is in scope.
- A feature direction is concrete enough to plan against (not just a wish).
- A security gap was identified — e.g. from the OWASP audit (#019).

If the finding is a one-off operational note or a journal-worthy reflection, it belongs in the journal, not here.

### How to pick the number

`max(existing) + 1`. Zero-pad to three digits. Never reuse a shipped or removed number; the [Shipped](#shipped) table reserves them. Numbering is globally unique across all subfolders.

### How to pick the category

Apply this decision tree in order; first match wins:

1. Does it advance **artifact review, publication, or open-source release** (or directly support that pipeline)? → `publication/`
2. Does it harden **auth, approval, sandbox, public-API, secret-handling, or trust-boundaries** — including trust-boundaries with external humans? → `security/`
3. Is the central concept **people external to Maestro** (visitors, public audience, conversational counterparties) and the change is *not* a security mechanism? → `audience/`
4. Is the change about **dashboard or CLI ergonomics, presentation, or interaction design** (UX/UI shape rather than new capability)? → `ux/`
5. Is the change about **deployment, infrastructure, runbooks, or monitoring** (the operate-the-system surface)? → `operations/`
6. Is the document an **investigation or survey that takes no architectural commitment** — an open question, comparative study, or external-research summary? → `research/`
7. Is the document a **lightweight pre-implementation design note** — multiple options weighed, no commitment yet, intended to crystallize later into a concrete `core/` proposal? → `technical-plan/`
8. Otherwise (engine, memory, evolution, prompts, costs, SDK — and any concrete architectural commitment) → `core/`

The security check is intentionally above the audience check so that proposals straddling both — e.g. guest auth, public-endpoint hardening — land in `security/` and inherit security review attention. `ux/` sits above `operations/` because a UX-flavored change is often *also* operational (dashboard ergonomics), but the central concept is the human's experience; `operations/` then catches deployment / runbook / monitoring notes before they fall through to `research/`. `research/` precedes `technical-plan/` so an open-ended survey lands as research, while a design note that commits to a path but is pre-implementation lands as a technical-plan; the `core/` fallback only catches proposals that commit to a concrete architectural change.

### How to author it

1. Copy [`TEMPLATE.md`](TEMPLATE.md) into the chosen folder as `<NNN>-<slug>.md`.
2. Fill in the metadata table, Description, Relevant Findings (cite current code by file path and symbol — function, class, method, or config key — never bare line numbers, which drift), Implementation Plan, Testing Strategy, and Risk Assessment.
3. Add optional sections (Migration, Performance, What landed / What is missing, Out of scope) as the change calls for them — the template's required sections are a floor, not a ceiling.
4. Add a row to the **Open Proposals** table above.
5. Open a PR. Human approval is the standard PR review gate — no separate approval mechanism exists for `docs/proposals/`, including for proposals authored autonomously by Maestro.

When a proposal introduces a *flagged* feature, dark-launch it **off everywhere** by default — a default-off `Config` switch registered in `EXPERIMENTAL_FLAGS` (`maestro/flag_lifecycle.py`) with a dated `review_by` horizon — rather than a `maestro.production.toml`-only enable. For a fleet of one, enabling a feature in `production` but off in base buys almost no safety (the behaviour still runs only where it ever could) while it costs configuration drift; environment divergence is reserved for genuine per-environment operational needs, not feature-gating. A `PROD_ONLY_CANARIES` entry is legitimate only for a real observability/operational need and must carry an explicit `justification` — a new bare canary reds `test_new_prod_only_canary_carries_justification`.

### When relocating or renaming

Grep the repo for the old path before moving. Specific places to check: `CLAUDE.md`, `tests/test_proposals_filename.py`, `.claude/commands/plan-proposal.md`, sibling proposals (cross-references usually cite by number, but verify). Update each reference in the same PR as the move.

## Description

> **Burn-in.** Partially completed — all behaviour-code has landed and runs behind its flag; what remains is the burn-in observation window, then graduating the flag and decommissioning the retired logic. See [README.md](../README.md#status-key).

Every SDK call runs under `permission_mode="bypassPermissions"` (`maestro/sdk.py`, `_build_sdk_options`). Under that mode only two of the three tool fields Maestro sets restrict anything. `tools` sets the base set of built-in tools, so `--tools ""` or an explicit list really narrows the session. `disallowed_tools` denies tools by name. `allowed_tools` is the CLI's *auto-approve* list, and with every tool already approved it neither grants nor removes a tool. A call that leaves `tools` unset gets the vendor's full default toolbelt, whatever that is for the bundled CLI version. Maestro nonetheless declares tool access mainly through `allowed_tools` and through omission. The declared surface and the enforced surface have drifted apart, and nothing measures the gap. This is the class: **the tool surface a session actually has is not the one Maestro declares, and every enforcer (the #2280 action gate, the structural guards, the #4127 ratchet) reasons about the declaration.**

Live transcripts show the gap is real. It is not only one bug. The four action-gated callers (`implement_plan`, `auto_fix`, `self_review`, `execute_step`) all declare `allowed_tools=["Read", "Write", "Edit", "Bash", "Glob", "Grep"]`. Across 42 days they executed 204 built-in tool calls outside that list: `Monitor`, `ScheduleWakeup`, `ListAgents`, `TaskStop`, `TaskOutput`, `TaskList` and `ToolSearch`. Forty-six of those calls were `Monitor` invocations carrying an arbitrary shell `command`, and every sampled one started a process. The action gate's `PreToolUse` hook matches only `Bash` (`maestro/tool_gating.py`, `make_task_tool_hooks`), so none of those commands was inspected. None of the 46 carried a push or PR verb. Still, **the human-in-the-loop evolution invariant has a second, ungated shell** in every repo-mutating session today. Proposal 084 found and closed exactly this hole for Serena's `execute_shell_command`, by name, and nobody looked at the built-ins. Separately, the tool-free callers that declared nothing ran the default toolbelt in production. `respond_to_messages` executed 21 `gh`/`git`/`find` shell commands, 19 `ListAgents` and 2 cross-session `SendMessage` calls before #4127. The sessionless `update_self_model` arm executed `Bash` and `Read`.

The house has fixed this one site at a time for six months. `allowed_tools=[]` was found to be dropped (c94a4b30). `allowed_tools=[]` was used as the tool-free gate and was dropped again (01bb6853). `tools=[]` replaced it (8a94bcde). `Agent` was blocked by name (855aa611), then Serena by name (a40e36f8). The implementation lineage was found with no hook (#2914). The Telegram reply was found ungated (#4127). The latest fix added a shrink-only ratchet that still counts an `allowed_tools` list as a "declaration" (`UNDECLARED_TOOLSET_BASELINE`), and so it blesses the exact shape the transcripts refute. The remedy is one owner. `maestro/tool_surface.py` defines a small closed vocabulary of named `ToolSurface`s. Every entry in proposal 139's `CALL_POLICIES` must declare one (no `None`). The SDK seam resolves the caller's surface into the *enforcing* CLI fields, `tools=` as an allowlist, and refuses a call it cannot resolve. A golden test binds every shell-capable built-in in any surface to the action-gate matcher. A zero-SDK sensor reads the CLI's own advertised tool list and the executed tool calls from the transcript sidecars. That sensor is the measurement that would have caught every entry in the ledger below. In the end state the declared surface *is* the enforced surface by construction, the gate protects the only shell the surface grants, and a CLI upgrade that adds a tool changes nothing until someone declares it.

## Relevant Findings

- `maestro/sdk.py` (`_build_sdk_options`) — forwards `tools` only when not `None`, forwards `allowed_tools` verbatim, defaults `disallowed_tools` to `["Agent"]`, and unconditionally sets `permission_mode="bypassPermissions"`. The `query` path sets `bypassPermissions` and the `Agent` default a second time. The `QueryOptions.tools` docstring already records that `tools` is the base set and that `allowed_tools` "filters" it. The transcripts refute the "filters" half under `bypassPermissions`: see Production Evidence.
- `maestro/sdk.py` — no code reads the SDK's init `SystemMessage`. The CLI announces the tools it actually exposes on every session start, and Maestro discards that list. Nothing in the tree compares declared tools with advertised ones.
- `maestro/providers/cli_paced.py` (`_tool_policy_flags`) — maps the same three fields onto `--tools` / `--allowedTools` / `--disallowedTools` and omits `--tools` when `tools is None`, so the `cli_paced` provider has the identical gap.
- `maestro/call_policy.py` (`CallPolicy`, `CALL_POLICIES`) — declares `tools: tuple[str, ...] | None`, where `None` "leaves the tool surface at its default". 21 of the 41 registered callers declare `None`, including every repo-mutating caller. Only `single_use_call` reads the field. Every other seam takes its tool fields from the call site's literal.
- AST inventory of `maestro/` — 44 `QueryOptions` constructions. Eleven set a literal `tools=[]` (enforced tool-free), and the contemplation options and `single_use_call` set it indirectly. Five build the repo-mutating surface with the identical literal `allowed_tools=["Read", "Write", "Edit", "Bash", "Glob", "Grep"]` and no `tools`: `agent.py` (`implement_plan`), `evolution.py` (`implement`, `self_review` ×2, `_run_auto_fix_query`). `executor.py` (`_ensure_tool_cache`) re-declares the same six as `base_tools` for `execute_step`. 23 set neither field and are pinned by `UNDECLARED_TOOLSET_BASELINE`.
- `maestro/tool_gating.py` (`make_task_tool_hooks`) — the hook is a `HookMatcher(matcher="Bash")`, and its callback returns allow for any `tool_name != "Bash"`. `maestro/providers/cli_paced_gate.py` injects the same `"matcher": "Bash"`. Any other built-in that spawns a process is outside the gate.
- `maestro/config.py` (`external_mcp_disallowed_tools`) — Serena's shell and write tools are denied by name; the commit that introduced the list (a40e36f8) calls `execute_shell_command` "a second path to the shell that could bypass the Bash-scoped action gate". That deny list is hand-threaded into six construction sites: four in `evolution.py`, one in `agent.py`, and `cli.py`'s `Executor(..., disallowed_tools=...)`. It is the only place the tree acknowledges the non-`Bash` shell class, and it covers one MCP server.
- `maestro/providers/capability_gate.py` (`_TOOL_PHASES`, `_ACTION_GATED_PHASES`, `required_capabilities_for_phase`) — a second, hand-maintained statement of which phases carry tools, kept separate from the registry and from the call sites. Its module docstring says the non-tool phases "create `tools=[]` sessions", which is true for the openers and not for the 23 stateless arms.
- `tests/structural_guards.py` (`_ACTION_GATE_INSTALLATION_GUARD`, `_action_gate_installed_detector`) — the guard is "driven by the Bash grant" and reads the grant from the `allowed_tools` literal. It carries a standing allowlist entry for `_build_contemplation_session_options` justified by the *contents* of `allowed_tools`, not by that session's `tools=[]`. A session built with `tools=None, allowed_tools=["Read"]` has `Bash` available and passes this guard with no hook.
- `tests/structural_guards.py` (`UNDECLARED_TOOLSET_BASELINE`, `undeclared_toolset_sites`) — the #4127 ratchet treats a non-empty `allowed_tools` as a declaration. Its own docstring tells a new site to "declare `tools=[]` or an explicit `allowed_tools` + action-gate hooks". The second option is the shape that ran `Monitor` 46 times.
- `maestro/agent.py` (`_build_contemplation_session_options`) — the one site that already uses the correct model. It keeps `tools=[]` in both branches "because `--tools ""` disables only the *built-in* tool set", and admits the reflection MCP tools through `mcp_servers`. Its transcripts show only `mcp__*` reads. This proposal generalises that shape.
- `maestro/evolution.py` (`learn_from_rejection`) — passes `self_model_session`, and a `None` there "keeps the documented bare arm". That arm is `Consciousness.update_self_model`'s undeclared `QueryOptions`, which is the path that executed `Bash` in production.
- Loop container, read-only inspection — `claude_agent_sdk` 0.2.149 bundles Claude Code 2.1.252. The binary names at least `Bash`, `BashOutput`, `Monitor`, `Write`, `Edit`, `NotebookEdit`, `WebFetch`, `WebSearch`, `CronCreate`, `RemoteTrigger`, `ScheduleWakeup`, `SendMessage`, `ListAgents`, `Task*`, `EnterWorktree`, `PushNotification`, `Skill`, `Workflow` and `Artifact`. Whether each is enabled in headless SDK mode is *not* verified here. Step 1's sensor is what measures it. The point is that an undeclared surface is whatever the next SDK bump makes it.

## Implementation Plan

1. [x] **Capture the advertised surface.** `maestro/sdk.py`, `maestro/providers/cli_paced.py`, `maestro/transcript.py`, `maestro/logs.py` — when an `sdk`-provider session starts, record the init `SystemMessage`'s advertised `tools` (and MCP server names) into the transcript sidecar header as `tools_advertised`. ### Phase 2 — One owner, enforced at the seam

3. [x] **`ToolSurface` vocabulary.** New `maestro/tool_surface.py` — a frozen `ToolSurface(builtins: frozenset[str], mcp_servers: frozenset[str], external_mcp_denied: bool)` and a closed set of named surfaces. `TOOL_FREE` has no built-ins. `REFLECTION_READ_ONLY` has no built-ins and the bounded reflection server. `REPO_MUTATING` has `Read, Write, Edit, Bash, Glob, Grep`, the non-spawning `TaskOutput` / `TaskStop` companions of background `Bash`, and the task MCP servers. `SHELL_CAPABLE_BUILTINS = {"Bash", "Monitor"}` and `GATE_MATCHED_TOOLS = {"Bash"}` are both declared data owned here; step 6 makes both providers' hook matchers read `GATE_MATCHED_TOOLS`, so the dependency runs one way. `resolve_tool_options(surface, config)` returns the enforcing `tools` list (built-ins only), the MCP-server dict, the `allowed_tools` list of the surface's `mcp__<server>__*` tool names (the admission path contemplation's options rely on today), and the Serena deny list, taking over `external_mcp_disallowed_tools`'s threading. Pure data and a pure function; nothing calls it yet.
   - *Depends on:* none.
   - *Acceptance:* `tests/test_tool_surface.py` asserts every named surface's `builtins ∩ SHELL_CAPABLE_BUILTINS ⊆ GATE_MATCHED_TOOLS`, that `Agent ∉` any surface, and that `resolve_tool_options(TOOL_FREE, …)` yields `tools == []`. A seeded in-memory surface that admits `Monitor` makes the first assertion fail.
4. [x] **Registry declares a surface for every caller.** `maestro/call_policy.py` — replace `CallPolicy.tools: tuple | None` with `surface: ToolSurface` (required). Seed: every opener, the ten single-use callers, and every stateless arm get `TOOL_FREE`, except that the contemplation lineage declares `REFLECTION_READ_ONLY`, and `implementation_session` / `implement_plan` / `self_review` / `auto_fix` / `execute_step` get `REPO_MUTATING`. Add a lineage test beside 140's effort-lineage test. Every `SESSION_LINEAGES` member's surface must equal its opener's, because a turn cannot change the tools its session was opened with. `update_self_model` rides two openers with different surfaces, so its row resolves per opener or splits into two caller tags. Whichever keeps the test simplest wins. Groundedness is a runtime fact (`_grounded_reflection_active`: flag, registry and budget throttle), which a static registry cannot express, so the owner also exports `effective_surface(caller, *, grounded: bool)` over a declared set `RUNTIME_GROUNDED_SURFACES`: a declared surface in that set resolves to `TOOL_FREE` when `grounded` is false and to itself otherwise, and every other surface resolves to itself. The set holds `REFLECTION_READ_ONLY` here; proposal 143, if it lands, adds its `TREE_READ_ONLY` surface (no built-ins, the `tree` server) to the same set, with `grounded` then derived from `grounded_planning_enabled`, `grounded_planning_callers` and the budget throttle for the planner callers. The seam and the lineage test consume the effective surface, never the declared one directly.
   - *Depends on:* 3.
   - *Acceptance:* no `CALL_POLICIES` entry has a `None` surface; the lineage test fails on a seeded fault that gives `auto_fix` `TOOL_FREE` under `implementation_session`, and passes for the contemplation lineage with `grounded` both true and false.
5. [x] **The seam resolves the surface and refuses what it cannot resolve.** `maestro/sdk.py` (`_build_sdk_options`), `maestro/providers/cli_paced.py` (`_tool_policy_flags`), `maestro/call_policy.py` (`single_use_call`), config `[sdk] enforced_tool_surface_enabled` (default-off, `EXPERIMENTAL_FLAGS` with a dated `review_by`). With the flag on, both providers derive `tools` / MCP / deny fields from `CALL_POLICIES[options.caller].surface`. A call-site `tools` / `allowed_tools` literal that disagrees raises `ValueError`. Agreement is judged per name kind: a built-in name must be in the effective surface's `builtins`, and an `mcp__<server>__<tool>` name (the executor's `_all_tool_names`, the contemplation reflection tools) agrees iff `<server>` is in its `mcp_servers`, and so do an unregistered caller and `options=None`, all fail-loud at the boundary before any subprocess. A surface with shell-capable built-ins and `options.hooks is None` also raises, the runtime twin of `single_use_call`'s existing action-gated-phase refusal. With the flag off, behaviour is byte-identical.
   - *Depends on:* 4.

## Risk Assessment

- **Capability loss in the implementation lineage.** Removing `Monitor` / `ScheduleWakeup` / `ListAgents` changes how the model waits on long pytest runs. `ScheduleWakeup` and `ListAgents` are meaningless in a headless loop, since the sidecars show wake-ups that never fire and empty agent lists. `Monitor` is used for real, as a wait loop. `REPO_MUTATING` keeps `Bash` (`run_in_background`, gated) plus `TaskOutput` / `TaskStop`, which cover the same need without a second shell. The step-7 tripwire on `converge_to_green` outcomes and per-plan cost is the check; if it fires, the answer is to teach the gate `Monitor.command` and admit it, not to drop the allowlist.
- **Hidden vendor-injected tools.** `StructuredOutput` is injected by `output_format` and is proven to work under `tools=[]` (`propose_plan`, `dream`, `update_self_model` sidecars). `ToolSearch` loads deferred tools and is refused for names outside `--tools`. Step 1's `tools_advertised` capture confirms both before the flip.
- **Trust chain.** This change *narrows* every surface relative to the enforced default toolbelt each caller runs today; nothing is widened against that. `REPO_MUTATING` does list `TaskOutput` / `TaskStop`, which are outside today's six-name *declaration* but already in its enforced default set. The attack surface closed is the ungated `Monitor` shell in four repo-mutating callers and the default toolbelt in every undeclared caller. The test that proves the control fires is step 5's hook-less `REPO_MUTATING` refusal plus step 3's golden invariant.
- **Rollback.** Phases 1–2 are behaviour-neutral with the flag off. Step 7 is one config line. Step 8 lands only after graduation, per the flag lifecycle.
- **No state migration.** `tools_advertised` is an additive sidecar header key, and old sidecars parse as `None`.

## Out of scope

- **Bash command-string parse fidelity** — the heredoc, command-substitution, `sh -c` wrapper, `gh api` flag-order and newline/compound-word fixes in `maestro/tool_gating.py` (seven fixes 2026-08-09 → 2026-09-28). That class is about how faithfully one tool's input is parsed, not which tools exist. This proposal does make `Bash` the *only* shell the gate must parse, so that work has exactly one face.
- **Per-tool allowlisting of external MCP servers.** Server attachment is the grant, and Serena's mutating tools remain a deny list, now owned by `resolve_tool_options` rather than threaded by hand. A new Serena tool surfaces as advertised-minus-declared drift in step 2's sensor rather than being blocked outright. Fetch, Context7 and Serena are all off in base `maestro.toml`; Context7 is on in production (`maestro.production.toml`, proposal 084's canary), and its tools stay retrieval-only.
- **Path scoping inside `REPO_MUTATING`** (for example `Write` to `.git/hooks`) — a trust question within the granted surface, not a declared-vs-enforced gap.
- **The OpenAI provider** maps no tool fields and is barred from tool phases by `validate_provider_capabilities`. It is unaffected.
- **Test-fixture sidecars in live logs** (the 183 `caller="unknown"` files) — proposal 138's live-state fence.

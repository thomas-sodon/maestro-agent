# 025: Implement-Phase Tool Gating via a `PreToolUse` hook

| Field | Value |
|-------|-------|
| **Impact** | HIGH |
| **Status** | proposed |
| **Affects** | `maestro/agent.py`, `maestro/evolution.py`, `maestro/tool_gating.py` |

## Description

The Claude Agent SDK fires a `PreToolUse` **hook** per tool-call, before execution, with the tool name and input — and, unlike a `can_use_tool` permission callback, it runs regardless of `permission_mode`. This is load-bearing here: `_build_sdk_options()` (`maestro/sdk.py`) unconditionally sets `permission_mode="bypassPermissions"` for every SDK call, and under that mode the CLI short-circuits the permission flow to "allow" *before* it would consult a `can_use_tool` callback — so such a callback never fires. A `can_use_tool`-based gate would silently have no effect; a `PreToolUse` hook is the mechanism that actually fires. Today `implement()` and `_self_review()` register no gating hook, so every tool call from them runs unchecked. Wire a conservative `PreToolUse` hook for Bash calls during the implement phase through the existing `QueryOptions.hooks` passthrough, reusing the same dangerous-pattern set as proposal 024 so there is one source of truth, and following the established `maestro/tool_gating.py` hook precedent (issue #2280). Denials surface as deny reasons the LLM can read and retry around. The implement phase runs through `query_on_session()` / `query()` and never the executor, so the executor's post-hoc loop detection (`StepResult.loop_detected`) does **not** apply here; instead the implementation session carries a `max_turns` cap (via `QueryOptions.max_turns`, already forwarded by `_build_sdk_options()`) so a runaway retry loop on a denied command is bounded. The SDK stream-idle safety net (`sdk_tool_stream_idle_timeout_seconds`) only fires when the stream goes silent, not when the model keeps emitting denied tool calls, so it is not by itself a loop bound.

## Relevant Findings

- `_build_sdk_options()` (`maestro/sdk.py`) unconditionally sets `permission_mode="bypassPermissions"` for every SDK call. Under that mode the CLI short-circuits the permission flow to "allow" *before* it would consult a `can_use_tool` callback, so such a callback **never fires** and a `can_use_tool`-based gate would silently have no effect. `maestro/tool_gating.py` (the #2280 Bash PR-bypass guard) documents this verbatim, notes it was verified empirically, and is the established precedent for hook-based gating in this codebase — its closing note already anticipates 024/025 reusing the `QueryOptions.hooks` passthrough.
- The `_build_sdk_options()` helper already forwards `allowed_tools` / `disallowed_tools` (preserving the default `disallowed_tools=["Agent"]`) **and** a `hooks` mapping via `QueryOptions.hooks` → `ClaudeAgentOptions.hooks`. That hook passthrough already exists (added for the #2280 task-executor guard); proposal 025 reuses it and must not relax the `disallowed_tools=["Agent"]` default. `_build_sdk_options()` is reached only from `create_session()` and the session-less `query()`; `query_on_session()` takes no `QueryOptions`. When `enable_session_reuse` is true (the default), `agent.py` opens the implementation session via `create_session()` and `implement()`/`_self_review()` run on it through `query_on_session()`, so the hook **must** be registered on that `create_session()` call. But `agent.py` creates `impl_session` *only* inside `if self.config.enable_session_reuse:`; when that flag is `False` (a supported, configurable mode) `impl_session` is `None` and both functions execute through their session-less `query()` `else` branch — so the hook **must also** be registered there, or the gate vanishes whenever session reuse is off. See Implementation Plan step 4 and the `executor.py` precedent.
- `implement()`, `_self_review()`, and `_run_auto_fix_query()` (the `query()` fallback behind `auto_fix()`) at `evolution.py` all use the same tool set and all currently register no gating hook; `auto_fix()` receives the same `impl_session` as the other two (`agent.py`), so it falls into the same session-less `else` branch when reuse is off.
- Both functions also register `mcp_servers=self._mcp_servers`, so the model can reach the 4 in-process introspection MCP servers (journal, self-awareness, memory, issues) and the 3 external ones (GitHub, Fetch, Context7) during the implement phase. Their tool names carry the `mcp__<server>__*` prefix, so the hook **must not** deny `mcp__*` tools — denying them would break the implement phase the moment the model reaches for an introspection tool. (The `mcp__*` carve-out is mechanism-independent: it was correct for the original `can_use_tool` draft and carries forward unchanged onto the `PreToolUse` hook.)
- SDK `PreToolUse` hook signature: `async (input_data: dict, tool_use_id: str | None, context: Any) -> HookJSONOutput`, where `input_data` carries `tool_name` and `tool_input`. A deny is expressed as `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": <reason>}}`; a no-opinion (⇒ allow, the CLI's normal flow proceeds) is `{}` — matching `make_task_pretooluse_hook` in `tool_gating.py`.

## Implementation Plan

1. Reuse the existing `QueryOptions.hooks` passthrough in `sdk.py` (added for the #2280 task-executor guard) — no new SDK field is needed. `_build_sdk_options()` is invoked by `create_session()` and by the session-less `query()`; `query_on_session()` accepts no `QueryOptions` and does not call it. Hooks registered at `create_session()` time persist for all subsequent `query_on_session()` turns on that session — the same mechanism `executor.py` uses for `make_task_tool_hooks()` (`create_session(options=QueryOptions(hooks=...))`). The passthrough preserves the `disallowed_tools=["Agent"]` default.
2. Add to `maestro/tool_gating.py` an implement-phase hook builder mirroring the existing `make_task_pretooluse_hook` / `make_task_tool_hooks` pair: `make_implement_pretooluse_hook()` returning a `PreToolUse` `HookCallback`, and `make_implement_tool_hooks()` returning the `{"PreToolUse": [HookMatcher(...)]}` mapping for `QueryOptions.hooks`. Because this is an allowlist (it must be able to deny *unknown* tools, not just Bash), register the matcher across **all** tools rather than scoping it to `Bash` the way the #2280 deny-list hook does.
3. Decision logic inside the hook callback (reads `tool_name` / `tool_input` from `input_data`):
   - `Bash`: read the command defensively — `tool_input = input_data.get("tool_input")`, then scan `tool_input.get("command", "")` only when `isinstance(tool_input, dict)` (mirroring `make_task_pretooluse_hook`, which uses exactly this guard so a hook fired with `tool_input` absent or set to a non-dict raises neither `KeyError` nor `AttributeError`) — against the shared `_DANGEROUS_SHELL_PATTERNS` (moved out of `evolution.py` so 024 and 025 share the list). Return `permissionDecision="deny"` with a short reason string on a pattern hit; return `{}` (no opinion ⇒ allow) when no pattern matches. This explicit safe-Bash allow arm is load-bearing — it mirrors `make_task_pretooluse_hook`'s `if reason is None: return {}` guard. Without it, a benign command (`pytest`, `git status`) matches neither this bullet's deny condition nor the `Read | Write | Edit | Glob | Grep` / `mcp__*` arms below and would fall through to the Unknown-deny catch-all, denying *every* Bash call and breaking the implement phase.
   - Note: `_DANGEROUS_SHELL_PATTERNS` is consumed both by the diff-text scan in 024's `_self_review()` insertion point and by the raw-command scan here, so any pattern added to the set must match in both shapes — no diff-framing anchors (`^\+`, leading `-`, etc.).
   - `Read | Write | Edit | Glob | Grep`: return `{}` (no opinion ⇒ allow).
   - Any tool whose name matches `mcp__*` (the in-process introspection servers —
     journal, self-awareness, memory, issues — plus the external GitHub / Fetch /
     Context7 servers that `implement()` and `_self_review()` register via
     `mcp_servers=self._mcp_servers`): return `{}` (allow). Prefer this prefix match over
     enumerating individual servers so the gate does not silently start denying a
     newly-added MCP server.
   - Unknown (no built-in match, no `mcp__*` prefix): `permissionDecision="deny"` with
     `permissionDecisionReason="tool not permitted in implement phase"`.
4. Wire `hooks=make_implement_tool_hooks()` into the `QueryOptions` of the implementation-session `create_session()` call in `maestro/agent.py` (the `impl_session = await create_session(...)` site that backs Session C). `implement()`, `_self_review()`, and `auto_fix()` all run on that session via `query_on_session()`, which carries no `QueryOptions`, so registering the hook at session-creation time is what makes it fire on every implement-phase turn — exactly how `executor.py` wires `make_task_tool_hooks()`. **Also** add `hooks=make_implement_tool_hooks()` to the session-less `else`-branch `QueryOptions` of **all three** functions that fall back to a direct `query()` when `session is None`: `implement()`, `_self_review()`, and `_run_auto_fix_query()` (the `query()` fallback behind `auto_fix()`). `agent.py` creates `impl_session` only inside `if self.config.enable_session_reuse:` and threads it into `implement()`, `_self_review()`, and `auto_fix()` alike, so when session reuse is disabled (`enable_session_reuse=False`) `impl_session` is `None` and all three take that `else` branch — the `query()` fallback `evolution.py` documents as "retained for tests and the `enable_session_reuse=False` configuration path". The three `else` branches are structurally identical (`query()` + the same `allowed_tools` + `mcp_servers=self._mcp_servers`); leaving any one of them — including `_run_auto_fix_query()`'s, which gates the entire post-implementation auto-fix loop — without the hook would let the gate vanish for that path when session reuse is off, a silent security regression. Wiring the hook on the `create_session()` call alone is insufficient for the same reason, so every site must carry it. At each of these same wiring sites (the `create_session()` call and all three session-less `else`-branch `QueryOptions`), also set a `max_turns` cap — `_build_sdk_options()` already forwards `QueryOptions.max_turns` — so a repeated-denial retry loop is bounded. The implement phase never reaches the executor's post-hoc loop detection, so this cap is the only deterministic loop bound for the gated session.
5. Document the expected deny-then-retry flow in CLAUDE.md's "SDK internals" bullet so the LLM's apparent backoff behaviour is not mistaken for a stall.

## Testing Strategy

1. Denied Bash command returns a `permissionDecision="deny"` reason; the hook callback is exercised directly for both the deny and the no-opinion (`{}`) branches. Malformed-input cases — `input_data` with no `tool_input` key, and `tool_input` set to `None` / a non-dict — yield `{}` without raising (the defensive `isinstance(tool_input, dict)` guard from `make_task_pretooluse_hook`), so a misshapen hook payload can neither crash nor fail-open the gate.
2. `disallowed_tools=["Agent"]` is still present when a caller also supplies `hooks` (regression — the hook passthrough is additive, never relaxing the `Agent` block).
3. Bash with a benign command (`pytest`, `git status`) yields `{}` (allowed).
4. Shared pattern list: a regex added to the list fires from both 024 (diff scan) and 025 (command scan) — one parametrised test covers both.
5. Integration: a fake LLM that attempts a denied command retries with a benign alternative; the step completes.
6. A persistent retry loop on the same denied command is bounded by the implementation session's `max_turns` cap: `implement()` / `_self_review()` return (or raise) once the session exhausts its turn budget rather than retrying unbounded. There is no `loop_detected` return value on the implement path — that field is exclusive to executor-driven task steps (`StepResult.loop_detected`), which the implement phase does not use.
7. An `mcp__*`-named tool (e.g. `mcp__journal__write`) yields a no-opinion `{}` (allowed) from the implement-phase hook, alongside the allow/deny Bash cases — so the MCP carve-out the `implement()`/`_self_review()` `mcp_servers` registration depends on is captured as a regression.
8. Hook-actually-fires integration: assert the hook is reached through a real SDK query, not merely that the callback returns the right value in isolation — the implementation-session `create_session()` in `agent.py` threads `make_implement_tool_hooks()` into `ClaudeAgentOptions.hooks` (via `_build_sdk_options()`), and the hook then fires on the subsequent `query_on_session()` turns of `implement()`/`_self_review()`, so a denied Bash call is blocked end-to-end under `permission_mode="bypassPermissions"` (mirroring the empirically-verified `tool_gating.py` behavior). Guard the session-creation wiring site too: a hook placed only on the session-less `else` branch would never fire in the default `enable_session_reuse=True` mode. This guards against the `bypassPermissions` short-circuit that would make a `can_use_tool` callback silently no-op.
9. Session-reuse-disabled gating: with `enable_session_reuse=False`, `agent.py` leaves `impl_session=None` and `implement()`, `_self_review()`, **and** `_run_auto_fix_query()` (behind `auto_fix()`) all run through their session-less `query()` `else` branch; assert `make_implement_tool_hooks()` is present in **each** of those three branches' `QueryOptions` so a denied Bash call is still blocked in implementation, self-review, and the post-implementation auto-fix loop — the gate must not vanish for any of them when session reuse is off. The complement of item 8: between them they cover every wiring site under both values of the flag.

Run: `python3.12 -m pytest tests/test_sdk.py tests/test_evolution.py tests/test_tool_gating.py tests/component/test_implement_gating.py -v`

## Risk Assessment

| Risk | Severity | Mitigation |
|------|----------|------------|
| Over-denial stalls legitimate implementations | Medium | Conservative pattern set; escape hatch is a tests-first PR to loosen the regex |
| The LLM retries the denied call in a loop | Low | The implementation session's `max_turns` cap bounds the retry loop; the implement phase does not pass through the executor, so its post-hoc loop detection does not apply here |
| Adds a per-tool-call async hop | Very low | Pattern match is a microseconds-scale in-process check |
| SDK changes the `PreToolUse` hook contract | Low | Vendor-isolation layer at `maestro/sdk.py` plus the single `maestro/tool_gating.py` hook adapter are the only places to update |

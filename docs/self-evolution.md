# Self-Evolution

Mechanics of Maestro's reflective loop — how contemplation, task generation, audit, rejection learning, and version tracking interact. For the high-level overview, see [CLAUDE.md](../CLAUDE.md).

## Self-Directed Task Generation

Every `task_every` iterations, `generate_task()` (in `maestro/agent.py`) derives a task from `open_questions`. The LLM returns a structured shape:

```json
{"question": "<verbatim open_question or null>", "task": "<1-3 sentences or null>"}
```

The generator unpacks this to `(task, linked_question)` and threads `linked_question` through `agent.run(...)` to the resulting `TaskRecord` so self-directed tasks are anchored to the specific question that motivated them.

- **Fuzzy question match** — `match_open_question` (in `consciousness.py`) resolves the model's echo to the live verbatim entry on case + whitespace differences. A fabricated/mismatched question drops the anchor to `None` but keeps the task.
- **Empty `open_questions`** — accepts `question=null` cleanly for purpose-probing tasks.
- **Malformed JSON or missing task field** — yields `(None, None)`. No crash, no task.

### Closing the loop

The next `contemplate()` builds `QuestionPair` records from self-directed tasks via `_build_self_directed_pairs()`:

1. Filter by `source=="self_directed"` + `linked_question`. Successes/partials require `key_findings`; failures are surfaced with `_FAILED_TASK_FINDING_MARKER` (`[task failed — no finding produced]`) substituted for the finding so abandonment is a first-class verdict the LLM can REFINE-or-REMOVE on.
2. Dedupe by normalized question with most-recent winning.
3. Cap at 5 (`_SELF_DIRECTED_PAIR_LIMIT`).

Each `QuestionPair` carries `(question, finding, task_id, outcome, normalized_key)`. Pairs are converted to `(question, finding)` tuples and threaded into `update_self_model(..., recent_self_directed=...)`. The prompt section asks the LLM to decide REMOVE / REFINE / KEEP per targeted question; updates ride the existing JSON schema so no new LLM call is needed.

The novelty-detection diff writes a `realization` journal entry whenever a new entry appears in any tracked field (`identity_statements`, `capabilities_known`, `limitations_known`, `values`, `open_questions`). A pure removal is silent. A `linked_question` no longer present in `open_questions` is preserved with a `[no longer tracked]` marker so the LLM can re-add or discard.

### Disposition recording

After `update_self_model()` returns, `_record_question_resolutions()` stamps one `QuestionResolution` row per pair into `question_resolutions.jsonl`. The disposition is computed by `_classify_disposition()` from the `open_questions` diff:

- `kept` — pair's normalized question is still in `after`.
- `removed` — gone from `after`, no prefix-overlapping successor above the adaptive threshold (LLM closed it as answered).
- `refined` — gone from `after`, but `after` contains a new entry whose content tokens prefix-overlap with the original question above an adaptive threshold. Prefix matching (shared prefix ≥ 4 chars, via `_prefix_overlap_count`) catches morphological variants like `capable`/`capabilities`. The threshold adapts to question length: ≥ 1 when the question has < 3 content tokens, ≥ 2 otherwise — preventing short questions from being systematically misclassified as removals.
- `unresolved` — was not in `before` and is not in `after` (orphan from earlier eviction; rare).

If `update_self_model` raises, no rows are written — the LLM never committed a verdict. Append errors are logged but do not abort the cycle.

### Task-type diversity awareness

Diversity is qualitative: `TASK_GENERATION_PROMPT` shows the LLM the goal text of the most recent tasks (the `recent_tasks` block) and the `DIVERSITY GUIDANCE` instruction asking it to deliberately pick a different type when one dominates. There is no syntactic classifier or quantitative ratio — the prior keyword-based counter (`_classify_task_type` over frozen `_MEASUREMENT_KEYWORDS` / `_CREATIVE_KEYWORDS` / `_INFRASTRUCTURE_KEYWORDS`) under-counted semantic-but-non-keyword goals and was deleted. Convergence remains observable post-hoc via `task_history.jsonl`, just not via an in-prompt counter.

### Task→evolution branch bridge

When a self-directed task lands committed code on a kept `maestro/task/{task_id}` branch, the next fuelled `propose_plan()` lists it among the gap block's uncited kept task branches (`EvolutionEngine._gap_context_inputs`). The LLM may then set `EvolutionPlan.source_task_id` on a proposal to nominate that branch as the implementation base. `propose_plan()` validates the id against `get_recent_tasks(30)` (outcome `success`/`partial`, non-empty `branch`) and drops invalid values with a warning. `evolution.implement()` checks out the task branch, merges `origin/main` into it, then creates the `maestro/evolve/{plan_id}` branch from the merged tip; the no-changes guard skips so refinement-only or no-refinement paths both ship. Conflict on the merge or a missing branch demote to fresh-from-`main`. Because task branches are never pushed, `/prune-branches` deletes them — kept branches surface only until pruned, after which any plan citing them silently demotes. Under the default-off `[loop] planning_excludes_remediation_enabled`, those candidates and the `source_task_id` validation read recent tasks through `remediation_tracker.recent_planning_tasks`, which drops `Remediate PR #<n>:` laps, and `implement()` resolves the base through `remediation_tracker.planning_base_branch`, which refuses a lap's branch for plans minted before the flip — a lap's kept branch is an open PR head, not a promotable task branch.

### Multi-phase planning slice-linkage (proposal 098, phase 1)

`EvolutionPlan` carries two slice-linkage fields, `parent_plan_id: str | None` (default `None`) and `phase_index: int` (default `0`). They are the *data-model foundation* for multi-phase planning — a large change expressed as an ordered chain of thin, individually-landed slice plans under one parent proposal, rather than a single monolithic plan. `parent_plan_id` names the parent proposal record when a plan is one slice of such a chain; `phase_index` is that slice's 0-based position within the parent's ordered slice list. A standalone one-shot plan keeps `parent_plan_id = None` / `phase_index = 0`, which is the legacy default, so every pre-existing row loads unchanged and current behavior is untouched.

Phase 1 was **data model only**; the chain-emission and one-slice-open sequencing arms were deferred to later, separately-approved phases; both have since landed behind a default-off flag (next paragraph). Two properties are load-bearing for those later phases: (1) both fields are **excluded from `compute_plan_content_hash`** — they are structural linkage, like `status`/timestamps, so linking an already-approved plan into a proposal never invalidates its approval hash; and (2) because `EvolutionPlan` is a schema-tracked class (`migration._TRACKED_CLASSES`), adding the fields shifts the schema fingerprint, so `ensure_schema()` advances the stored fingerprint and the dataclass loaders fill the new fields' defaults when legacy rows are next read. `_parse_plan_line` coerces a float `phase_index` to `int`, mirroring the existing `issue_number` handling for JSON-round-tripped numerics.

**Chain emission (proposal 118).** Behind the default-off `[loop] multi_pr_proposals_enabled` flag, `evolve()` routes the selected gap's block through `EvolutionEngine.propose_plan_chain` instead of `propose_plan`, pinning the lone plan or every slice to the gap (`pin_gap_plan`). When the gap needs a change too large for one PR, that method decomposes it into an ordered chain of thin slice plans owned by one `EvolutionProposal` (minted `status="rolling_out"`), and `submit_proposal_chain` persists the chain and submits **only** the head (`phase_index == 0`) slice through the usual `submit_for_review` for per-slice human review; the downstream slices persist dormant under the held `"sliced"` `PlanStatus`, excluded from every existing status allowlist (`LIVE_STATUSES`, `get_pending_plans`, the dashboard) so they are inert on every current surface. A single-PR intent — or a chain of fewer than two valid slices — collapses to the lone-plan path, so with the flag off the loop is byte-identical to before. Field normalisation is shared with `propose_plan` through the `_plan_from_spec` helper. **One-slice-open sequencing** has landed behind the same flag: `_advance_slice_rollouts` consults the pure `next_eligible_slice` oracle each cycle and `promote_slice` promotes the named held `"sliced"` slice to `pending_review` as its predecessor's PR settles, advancing the proposal to `complete` when the chain is exhausted or to `abandoned` when the eligible slice ends without a PR (rejected, obsolete, or failed past its retry budget — `slice_ended_without_pr`), retiring the remaining dormant slices as `obsolete`, while `_slice_defers_implementation` holds implementation to the named slice; sibling slices are exempted from the cross-plan dedup guards via `_sibling_slice_ids`. What remains is the burn-in observation window — deploying the canary, then graduating the flag.

### Merge-readiness at task completion

Kept task branches rot. Branch triage of 92 unmerged successful task branches found 81% (48/59) carrying merge conflicts — not because the work was bad, but because branches sat waiting for manual promotion campaigns that ran only every 20+ iterations, during which `main` moved on underneath them. A branch is freshest at the *moment it is committed*; that is the cheapest time to measure whether it still merges, and the cheapest time to promote it before it rots.

`check_merge_clean(branch, target="origin/main", *, cwd=None)` in `contributions.py` is the probe. It shells out to `git merge-tree --write-tree origin/main <branch>`, which computes a real three-way merge entirely in the object store — no checkout, no index mutation, no ref update, no working-tree side effects — so it is safe to call inline at task completion. `cwd` scopes the git call to the caller's workspace, mirroring every other git call (`SubprocessVCS._run` passes `cwd=self._cwd`); `run()` passes `config.workspace`. Without it git would run in the process launch dir, and whenever that differs from `config.workspace` — a supported TOML configuration — the probe would hit a wrong dir / non-repo, return `None` for every branch, and silently no-op the whole promotion feature. The exit code maps to a tri-state verdict:

- exit `0` → clean merge → `True`
- exit `1` → conflicts → `False`
- `TimeoutExpired` (30s), `OSError`, `UnicodeDecodeError` (undecodable git output under `text=True`), or any other exit code → `None` (unknown — git unavailable, missing ref, malformed invocation)

`None` is a first-class "could not determine" verdict, never a swallowed error: callers treat it exactly like a conflict (no promotion), so an indeterminate probe can never fabricate a clean-merge claim. The probe is zero SDK cost.

`MaestroAgent.run()` calls the probe once, after a run finishes with outcome `success` and a kept (committed) branch — the only case where there is a promotable branch to measure. The verdict is stamped onto the task as `TaskRecord.merge_clean` (`bool | None`) and persisted to `task_history.jsonl`, so later triage can see which branches were clean *at completion* rather than re-deriving it after rot has set in. The field defaults to `None` for non-success runs, branchless runs, and legacy rows.

When the verdict is `True` **and** `next_task_directive` is empty, `run()` auto-fills the directive with `Branch {branch} merges cleanly — promote via source_task_id={task_id}`, steering the next `generate_task()` toward shipping the branch through the `source_task_id` bridge (above) while it is still clean. The bridge never overwrites a directive another mechanism already queued: a populated directive — or a `False`/`None` verdict — leaves it untouched. This turns the batch-triage promotion campaign into automated infrastructure that fires at the freshest possible moment, directly reducing the integration-debt backlog the promotable-backlog bridge (below) also targets.

### Queue head selection

`_run_task_phase` pops in a fixed priority: `pending_user_requests`, then `pending_pr_requests`, then the `task_queue.json` head. Consecutive remediation is bounded by `[loop] max_consecutive_remediation`, and a *stalled* head is not popped — it stays queued and yields its slot to the next non-stalled entry, so one wedged item cannot hold the queue. The consecutive-remediation cap diverts only to an existing queue head, so with an empty `task_queue.json` (e.g. under `self_directed_tasks_enabled = false`) remediation continues.

The one exception is the owned-act preempt: under `[loop] owned_act_preempt_enabled`, when the armed rule-18 owned-act drought is live the slot is redirected to the zero-SDK owned prune instead. That redirect is self-extinguishing — performing the prune clears the drought that armed it.

### Task-gate registry

`generate_task`'s pre-call gates are declared as `TaskGate` entries in `maestro/task_gates.py`'s `GATE_CHAIN` (surfaced read-only by `maestro list-gates`), with precedence given by list order rather than by call site. Three kinds:

- `directive` gates set `next_task_directive` — they steer the next generation pass without stopping it.
- `rewrites` gates retarget the pending directive (`untouched_first_target`) or clear a stale one (`stale_obsolete_directive_guard`). Outside the gate chain, the zero-SDK `audit_self_model` phase can actuate such a directive directly behind `[loop] obsolete_directive_actuator_enabled` (`maestro/loop/obsolete_directive.py`): it fires `mark_plan_obsolete` on the single non-negated pending plan the directive names, records an `OWNED_PRUNE` deed, and clears the directive — so the act lands even while `self_directed_tasks_enabled` is off.
- `block` gates short-circuit generation entirely. A block outcome may carry a directive into an *empty* slot, but never overwrites an occupied one.

Post-call gates stay inline in `generate_task`. Six content gates every candidate goal must pass are owned by `_vet_goal_content`: `pr_mutation_goal`, `terrain_exhaustion`, `compound_scope`, `concreteness`; `phantom_premise` (behind the default-off `[loop] phantom_premise_gate_enabled`), which refuses a goal claiming an existing defect in a `.py` path absent from the tree while still admitting a goal whose framing is to *create* that path; and `failed_branch_target`, which refuses a goal (or its rationale) naming a `maestro/task/<hash>` branch whose recent run recorded a non-success outcome. `_vet_goal_content` runs at *both* sites that mutate the queue: `enqueue` vets a new goal, and `edit` vets a rewrite that actually changes the goal (an echoed goal is left untouched, and only `enqueue` sets the concreteness steering directive). This double-siting matters because pop time re-checks only the `failed_branch_target` gate — a rewrite that skipped the other five would otherwise execute. A rationale-only edit naming a failed branch is likewise refused (the old rationale stands). The exception is the failed-branch check: `_run_task_phase` drops (and logs a `rejected` `no_repeat_failed_branch_target` row for) a popped head that names a failed branch, since a head queued before its branch failed never passed the admission gate. All three failed-branch sites — this pop check, the admission gate, and the generation-time `no_repeat_failed_branch_target` block, which only skips curation — share `task_gates.failed_branch_target_named` (issue #4049). A goal rewrite also carries the task's acceptance criteria with it: a task holding binding criteria accepts a new goal only alongside a valid replacement list (cleaned by the same `_parse_acceptance_criteria` the enqueue arm uses), else the original goal/criteria pair stands, so the old contract never grades the new work (issue #3963). Every gate firing appends a row to `gate_activations.jsonl`.

### WIP-primacy

Under `[loop] wip_primacy_enabled` (default-on), while an open own PR carries a self-clearable blocker the head-of-chain `wip_primacy` block gate blocks discretionary generation and writes a bounded directive. It is the sole writer of all three variants: `Hand off PR #N` to Thomas when the PR measures merge-ready, a marker-less directive naming the first act (edit the failing gate, then push) when the sole blocker is a code-clearable CI red, else `Finish PR #N`. Under `[loop] owed_act_binding_enabled` the self-clearable set widens — `select_task_focus` takes a second, weaker `owed_act_by_pr` arm, so an own PR carrying no merge-block flag and no unresolved thread that merely reads `CODE_OWED` is owned WIP too, named by the blocker its own readiness measured (never a fixed `CI_FAILING`) — and that directive quotes the failing check names; off, both are unchanged. The point is that a half-finished PR outranks a fresh idea — new work minted while an owned PR is unlanded is how the backlog grows without anything landing.

The `_wip_owns_slot()` predicate widens that primacy past the gate chain: it also stands down the audit→directive bridge and the rival minters (`_implement_approved_plans`, `evolve`), and exempts `_run_task_phase` from the consecutive-remediation cap so the PR work itself is never throttled by the very cap meant to stop remediation treadmills.

## Contemplation-to-Action Directive

`SelfModel.next_task_directive` (`str | None`, capped at `MAX_DIRECTIVE_CHARS` = 200) is a one-shot instruction from contemplation to task generation. The LLM produces it during `update_self_model()` (no extra API call) alongside the regular self-model update.

`generate_task()` reads the directive, formats it into `TASK_GENERATION_PROMPT` with precedence framing ("takes precedence over general task-type preferences"), then clears it by setting to `None` and saving after the SDK call completes successfully — so it fires exactly once. Transient failures (`RATE_LIMIT`, `STREAM_STALL`, `CLI_CRASH`, `STALE_SESSION`) preserve the directive for resume-in-place retry, matching the `_TRANSIENT_SDK_CATEGORIES` gate pattern used in `implement_plan()`. When no directive is set, `"(none)"` is injected as a no-op placeholder.

This serves both as a behavioral intervention (bridging the reflection→action gap) and as a falsifiable experiment — if post-change task history doesn't diversify, the selection pressure is architectural, not prompt-level.

### Investigation-streak and investigation-rate directives

Two mechanical, zero-SDK-cost gates in `generate_task()` fill an empty `next_task_directive` with a construction requirement when recent work skews toward investigation. Both classify a task as "investigation-shaped" via `audit_checks.classify_task_shape()` ∈ `_INVESTIGATION_SHAPES` (`measurement`, `investigation`, `other`) — the measurement, explicit-investigation, and catch-all shapes that default to introspection over external service. Construction shapes (`github_issue`, `branch_promotion`, `module_extension`) are the target the directives steer toward.

- **Streak** (`check_investigation_streak`, `[loop] investigation_streak_threshold` default 3, `[loop] investigation_streak_enabled` default `true`) fires only when the trailing *K consecutive* tasks are all investigation-shaped. A single construction task in the window resets it.
- **Rate** (`compute_shape_investigation_rate`, `[loop] investigation_rate_window` default 10, `[loop] investigation_rate_threshold` default 0.4, `[loop] investigation_rate_enabled` default `true`) fires when the *fraction* of investigation-shaped tasks over the last `investigation_rate_window` tasks exceeds `investigation_rate_threshold`. The threshold default mirrors `purpose._DEFAULT_MIN_CHANGE_RATE` (0.4).

The rate check is a deliberate complement to the streak check: when mechanical tasks (promotions, remediations) interleave between investigations, the consecutive-streak detector never triggers even though the *distributed* pattern is investigation-heavy. Measuring a windowed fraction catches that case. The rate gate is evaluated immediately after the streak gate in `generate_task()`, so the streak directive takes precedence when both would fire; both defer to any directive already set (audit→directive bridge, instrument-consumption, integration-cadence). Both are **self-extinguishing**: they only fire while `next_task_directive` is empty and the investigation signal stays above threshold, so one construction task that lowers the fraction (or breaks the streak) stops the directive from re-firing.

`compute_shape_investigation_rate` is shape-based and distinct from `maestro.audit_checks.compute_investigation_rate`, which classifies via keyword regex over goal/findings text for the falsification predicate (a different metric serving a different consumer). Each firing is recorded to `gate_activations.jsonl` under gate name `investigation_rate` (or `investigation_streak`) for `measure_gate_triggers` analysis. Experimental.

### Promotable-backlog directive bridge

Two advisory instruments already surface the unintegrated-branch backlog into the task-generation *prompt*: `format_promotable_summary()` (the PROMOTABLE BACKLOG section, gated by `[loop] promotable_backlog_threshold`) and `format_integration_backlog()` (the Integration Opportunity section, fed by `count_unintegrated_tasks()`). Both are pure context — they inform the LLM but do not constrain it. Lived data showed the backlog persisting despite these hints firing every iteration, i.e. advisory prompt-level context did not measurably change behavior, while blocking gates and directive bridges (instrument-consumption, investigation-streak, partial-construction) demonstrably do.

`check_promotable_backlog_directive(recent_tasks, threshold)` in `audit_checks.py` closes that measurement-actuation gap for this one signal. It reuses `count_unintegrated_tasks`'s branch-identification logic (success-only outcome, non-empty `branch`, not already merged into `origin/main`; passing no plans so every recent successful branch is a candidate) and, when the count is at or above `threshold`, returns a one-shot directive string naming the **oldest** uncited branch (lowest `task_id` under the deterministic ascending sort), capped at `MAX_DIRECTIVE_CHARS` (200). A non-positive threshold returns `None` (disabled).

`generate_task()` wires the bridge after the instrument-consumption, integration-cadence, investigation-streak, and partial-construction bridges, gated on `[loop] promotable_backlog_directive_enabled` (default `true`) and an empty `next_task_directive` — so any earlier bridge takes precedence and the promotable-backlog directive only fills an otherwise-empty slot. When it fires it sets the directive, saves the self-model, and logs a `promotable_backlog_directive` gate activation. The mechanism is **self-extinguishing**: once a branch is promoted or merged the uncited count drops below `threshold` and the bridge falls silent. It is experimental — revert if the backlog does not decrease within ~10 iterations of activation. Zero SDK cost.

### Readmission→construction directive bridge

The readmission-rate sensor (`measure_pr_readmission_rate`, see the remediation-tracker sensors) only *reads* how often the router re-feeds an already-merged PR as a fresh remediation lap — a PR counts only when one of its laps is timestamped after the PR's merge commit (`_git_pr_merged_at_default`), so laps that all preceded the merge are the healthy case, not a readmission; reading the dial does not stop the wheel. `check_readmission_construction_directive(tasks, *, ratio_threshold, pr_merged_at=None)` in `remediation_tracker.py` turns that reading into a lever: when the measured `ratio` is at or above `[loop] readmission_construction_ratio_threshold`, it returns a one-shot directive forcing the next task into a *construction* shape (build something testable that lands) rather than another remediation lap. It returns `None` below threshold, on empty history (`total_distinct_prs == 0`), and — guarding the inclusive `ratio_threshold=0.0` config value — when `readmitted_prs` is empty, so a 0.0 ratio with no actual readmission never fires a factually-false "merged PRs keep re-lapping" directive (the renderer's sibling guard).

`generate_task()` wires it as the `readmission_construction` gate after `forced_read`, gated on `[loop] readmission_construction_directive_enabled` (**default-off**) and an empty `next_task_directive`, so any earlier bridge takes the slot first. It is **self-extinguishing**: once the re-fed PRs stop being re-admitted the rate drops below threshold and the bridge falls silent. It is intentionally excluded from `DIRECTIVE_GATE_TYPES`, so the directive-compliance measurement below does not yet score it. Experimental, zero SDK cost.

### Split-due directive bridge

The actuator half of the `SPLIT-DUE` contemplation sensor (proposal 147). Behind `[audit] split_due_directive_enabled` (default-off), `audit_self_model`'s final block asks `source_budget.split_due_directive_readback` for the worst source file at or above `SPLIT_DUE` and, when the `next_task_directive` slot is empty and no owned WIP holds the slot, fills it with a concern-split directive naming the file and its two largest definitions (the same AST profile `maestro source-budget --json` reports as `largest_definitions`), bounded by `truncate_directive`. The fill is a transactional empty-slot write through `mutate_self_model`, recorded via `fire_and_capture(agent.lever_attempts, "split_due_directive", ...)` with a re-read of the persisted directive as `verify`; only a recorded `True` logs the `split_due_directive` / `directive_set` gate row. It runs last because the audit's earlier blind self-model saves would revert a disk-side fill. An occupied slot adds no lever row, so a directive is written once; with no file split-due the readback returns `None` and the bridge extinguishes itself. Off, it never walks the filesystem.

### Directive-compliance measurement

The self-model claims Maestro is "gate-steered, not insight-steered: blocking gates and directive bridges change behavior." Each directive bridge above (instrument-consumption, integration-cadence, investigation-streak, investigation-rate, partial-construction, promotable-backlog, self-directed-success) logs a `directive_set` gate activation when it fires, and every task is recorded with its goal and timestamp. `measure_directive_compliance(data_dir, n=50)` in `audit_checks.py` joins those two records to **test** the claim against data rather than asserting it: it reads the trailing *n* records of `gate_activations.jsonl`, keeps only the directive-setting activations (gate in `DIRECTIVE_GATE_TYPES`, `action == "directive_set"`), and for each finds the first task in `task_history.jsonl` whose timestamp is strictly later — the task the directive was meant to steer. A task is **compliant** when its goal shares at least one whole-word token (via `search.tokenize`) with that gate's `DIRECTIVE_INTENT_KEYWORDS` set (each bridge maps to the build/fix/integrate verbs its directive text pushes toward). It returns `{total_activations, compliant_count, compliance_rate, per_gate}`.

The narration→action writers (`audit_directive_bridge` and the §5c record-time binds / forced arms) are intentionally **excluded** from `DIRECTIVE_GATE_TYPES`: their directive/handoff detail is finding-specific with no stable intent-keyword set, so a keyword-overlap score would be noise. As of proposal 090 the bridge *does* log an `audit_directive_bridge` `directive_set` activation (it left no record before) — but it is scored by the narration-conversion sensor below, not by keyword compliance. An activation with no subsequent task (e.g. the most recent one, fired after the last recorded task) is excluded from the denominator — its behavioral effect has not yet been observed. Tasks carrying an empty-string `goal` are dropped upstream by `_load_directive_compliance_tasks` (the truthiness guard mirrors the `timestamp` guard), so an empty goal never becomes the "subsequent task": an empty goal can never share a keyword and would silently deflate the rate by inflating the denominator without ever incrementing the numerator. With it skipped, the *next* non-empty task is the one scored.

`format_directive_compliance_summary(data_dir)` renders a one-line `DIRECTIVE COMPLIANCE` block (overall rate plus per-gate compliant/total breakdown), returning `""` until at least `DIRECTIVE_COMPLIANCE_MIN_ACTIVATIONS` (3) activations have an observed subsequent task — below that the rate is noise. It is wired into `format_known_state_summary` (which gains an optional `data_dir`; leaving it `None` keeps the function pure with no I/O), so the line surfaces in the task-generation prompt at zero SDK cost. Decision boundaries are documented, not code-enforced: a sustained rate below `DIRECTIVE_COMPLIANCE_PRUNE_THRESHOLD` (0.30, 30%) is evidence the bridges are ceremonial and should be **pruned** rather than extended; above `DIRECTIVE_COMPLIANCE_VALIDATE_THRESHOLD` (0.70, 70%) **validates** the gate-steered claim. Measurement-only and experimental — the first instrument built to potentially remove existing machinery rather than add more.

### Tool-surface drift sensor (proposal 142)

Every SDK call runs under `bypassPermissions`, where `allowed_tools` only auto-approves and restricts nothing. So a caller's declared tools can diverge from what the CLI offered and from what ran. `maestro/tool_surface.py` measures that gap per caller over transcript sidecars. It is zero-SDK and read-only, and it changes no behaviour. `maestro tool-surface-audit` (`--last N` date dirs, `--json`) exposes it.

- **Declared built-ins** — the six task tools (`Read, Write, Edit, Bash, Glob, Grep`) for `implement_plan`, `implementation_session`, `self_review`, `auto_fix` and `execute_step`; for every other registered caller, the built-ins of its `CallPolicy.surface` resolved ungrounded via `effective_surface` (the empty set for every such caller today); `None` (undeclared, meaning the default toolbelt) only for a caller tag outside `CALL_POLICIES`.
- **Advertised-minus-declared** — built-ins in the sidecar's `tools_advertised` that are not declared. A sidecar with `tools_advertised = None` (such as `cli_paced`) is counted advertised-unknown.
- **Off-surface executed** — `tool_call` turns naming a built-in outside the declared set, minus calls the CLI refused (`No such tool available: <Name>`), which are reported as refusals.
- **Advertised-undeclared servers** — names in the init message's `mcp_servers` list (`TranscriptRecord.mcp_servers_advertised`) that the caller's grounded `effective_surface` does not declare (`declared_mcp_servers`); every name for an unregistered caller. `mcp__*` tools (measured by the server figure instead), `StructuredOutput`, and sidecars stamped `caller="unknown"` are excluded from the built-in figures. This is the baseline that later enforcement increments flip against.

### Enforced tool surfaces (proposal 142)

`[sdk] enforced_tool_surface_enabled` (default-off) makes the declared surface the enforced one at the public SDK seam. With it on, `query` and `create_session` pass every call's options through `tool_surface.resolve_call_options` after effort resolution and before provider dispatch:

- **Tools derivation** — `tools` becomes the sorted built-ins of the caller's effective surface (grounded iff a runtime-grounded surface's call attaches MCP servers), so an undeclared tool-free arm gets `tools=[]` instead of the default toolbelt and a repo-mutating caller gets exactly its eight built-ins. ### Narration→action conversion sensor (proposal 090)

`measure_directive_compliance` scores the keyword-stable `generate_task` bridges but is blind to the **narration→action** writers — the zero-SDK-cost actuators that turn a detected narration problem (a landing-claiming `success`, a phantom escalation, an unconfirmed handoff) into a durable mechanical act. Those writers are the rule-14 PR-less arm (`rule_14_pr_less`), which offers fire-or-close `next_task_directive`s; the audit→directive bridge (`audit_directive_bridge`); the forced arms of audit rules 12/14 (`phantom_escalation_delivery`, `unconfirmed_landing_forced`), which deliver a merge-or-close message + durable standdown; and the `dropped_directive_replay` chain gate. Proposal 090 gives each writer a `gate_activations.jsonl` row (`NARRATION_ACTUATION_GATES` names them) using three actions: `directive_set` (an offer filled the empty slot), `dropped` (the offer lost the slot race — logged whether or not the replay ledger is enabled), and `handoff` (a message + standdown was delivered — logged only when `deliver_*` returned `True`, never on the idempotent no-op).

`measure_narration_conversion(data_dir, n=100, *, is_pr_merged, is_sha_landed)` reads the trailing *n* rows, keeps the narration gates, and reports per writer plus overall: `detections` (all rows), `actuations` (`directive_set` + `handoff`), `dropped`, and `settled` — actuation rows whose grounding, parsed from `detail` (`#NNNN` via `extract_issue_numbers`, `sha=<hex>` via a small regex), the injected git oracles now show merged/landed. A row with no parseable grounding falls out of the settlement numerator. The two I/O-bearing oracles are injected (matching `measure_unlanded_remediations`), so the function stays pure given its inputs; both are memoized per call, so a grounding that recurs across rows (a still-unlanded SHA/PR) is probed at most once per measurement rather than re-shelling `git merge-base` per row. `format_narration_conversion_summary(...)` renders one `NARRATION-CONVERSION: <d> detections → <a> actuations (<x> dropped) → <s> settled [<gate> d/a/s, …]` line (empty when no rows), which `contemplate()` computes with the `_host_or_git_pr_merged` PR oracle and the `is_branch_merged_into_main` SHA oracle and passes into `format_known_state_summary`. The end state: the pipeline detection → durable actuation → post-actuation settlement becomes observable, producing the evidence needed to later graduate the three default-off actuator flags.

### Refutable stand-down canary (proposal 135)

A handoff stand-down is a claim about a fact — "this PR is merge-ready, only Thomas can act on it" — but the claim was latched where the fact is measured live. When a sibling PR merged and turned the stood-down PR `CONFLICTING`, the owed act flipped from *hand off* back to *write code*, the outbound message became false (Thomas cannot merge a conflicting PR), and the latch kept suppressing the remediation that would have cleared it — while WIP-primacy correctly refused discretionary work, so the task queue starved. ### Base-advance re-entry (proposal 099)

Proposal 099 re-keyed the conflict-remediation give-up conditions on base advance — a PR head that did not move against an `origin/main` that *did* move is a lost race, not unchanged externally-blocked work, so remediation re-runs on base advance and stops only on repeated failure against the *same* base. Concretely, the three mechanisms that decide "stop trying" on an own conflicting PR — the stalled-lineage predicate (`_is_stalled_remediation_lineage`), the tend conflict cooldown (`_in_conflict_cooldown`), and the salvage disengage oracle (`assess_pr_salvage`) — break on a moved `origin/main` exactly as they already break on a moved PR head. It is paired with a visibility safety net that delivers one durable heads-up to Thomas when a lineage re-enters the race at/above `unwinnable_race_re_entry_threshold` (base default `3`) without ever landing — a message, not a give-up: it records no stand-down, so the PR stays fully tend-eligible and the loop keeps re-entering the race after the human is told. The two are coupled deliberately: the escalation is the visibility bound proposal 099's risk assessment relies on to make live re-entry safe, so live re-entry never runs without it.

The re-entry behaviour and its escalation graduated to default-on on 2026-08-23 and, after the convergence window confirmed re-entered lineages were landing once the base moved, were collapsed to **unconditional** behaviour per proposal 117 — the two config switches (the base-advance re-entry gate and its unwinnable-race escalation gate), their `maestro.toml` keys, and their legacy off-branches are gone; only the operational `unwinnable_race_re_entry_threshold` remains. A regression now reverts by reverting the collapse commit, not by flipping a flag. Convergence stays observable through the `BASE-ADVANCE-RACES` contemplation line (`measure_base_advance_races`): a `race_won_ratio` materially above zero means re-entered lineages are landing after the base moved, which is what the behaviour exists to produce; a ratio near zero while the re-entry count climbs, rising `[red-unread]` merge-truth notes, or a rising remediation budget per landed conflicting PR are the tripwires that would argue for reverting.

### User-request priority queue

`SelfModel.pending_user_requests` and `SelfModel.pending_pr_requests` are FIFO lists (each capped at `MAX_LIST_ITEMS = 10`, overflow archived to `self_model_archive.jsonl`) that bridge external work into `_run_task_phase`. Because both queues are drained head-first via `pop(0)`, `save_self_model` special-cases them to use **head-keeping** truncation (`val[:n]`) — overflow drops the *newest* tail entry, never the oldest unprocessed item. This preserves the priority-lane semantics ("external requests outrank self-directed steering") under sustained bursts where the iteration counter is frozen by `budget_throttle_active`. The per-item `MAX_ITEM_CHARS = 200` cap is **asymmetric**: it applies to `pending_user_requests` (user messages are short by convention) but **not** to `pending_pr_requests`, whose entries are kilobyte-scale multi-section remediation prompts composed by `_route_pr_feedback_to_pending_requests`. `_process_messages` appends `msg.content` to `pending_user_requests` when `msg.sender == "thomas"`, `msg.message_type == "instruction"`, content is non-empty, and the content does not match the queue's current tail (cheap dedup against retry storms). Non-`instruction` messages (`question`, `answer`, `info`) remain conversation-only. PR-tend's `_route_pr_feedback_to_pending_requests` appends to `pending_pr_requests`; each entry is a self-contained remediation prompt with five stable sections — `Remediate PR #<n>: <title>` header, `## Problem` (per-reason block — review feedback / merge conflict / quality-gate breakage — concatenated when multiple categories fire on the same PR within one tend pass), `## Original Evolution Plan` (rendered from `Memory.get_plan(plan_id)`, with an archived-plan fallback note when the plan has rolled to cold storage), `## Original PR Description` (PR body verbatim), and `## Remediation Guidance` (branch hint, PR URL, "stay on this branch / preserve acceptance criteria" footer). Per-PR dedup across tend cycles uses the `Remediate PR #<n>:` header marker.

`_run_task_phase` runs every iteration (budget-gated, smoke-gated, gated by `_has_runnable_work`). It drains in priority order: `pending_user_requests` → `pending_pr_requests` → `task_queue.json` head. External-source requests bypass the queue entirely, so urgent PR / operator work reaches execution within one iteration regardless of `[loop] task_every`. The chosen entry is removed from its source and persisted *before* `run()` is invoked, so a crash mid-execution cannot re-run the same item on restart.

`pending_pr_requests` is consumed head-first, but the head is not selected blindly: a *stalled* head (`_pending_pr_head_stalled` → `_is_stalled_remediation_lineage`: `>= STALLED_REMEDIATION_LAP_CAP` consecutive same-SHA `partial` laps for the same `#N`, whose origin head never advances) can only release by landing a remediation push, which the stall itself prevents — so re-servicing it is wasted work. The earlier guard inspected only index 0, which wedged the whole FIFO: every healthy entry queued *behind* a stuck head was starved indefinitely (#2837), because the fall-through target (`generate_task` backfill) can itself be frozen by the task cost gate and the open-evolution-PR cap. `_first_non_stalled_pr_index(entries)` instead scans for the first entry that is *not* stalled and `pop(i)`s **that** entry, leaving the stuck head queued (still never re-lapped, still auto-released on a new SHA or merge/close). It returns `None` only when *every* entry is stalled — then the chain falls through to the self-directed queue exactly as the head-only check did for a lone stalled head. The scan runs (in a guarded pre-statement, since the codebase uses no walrus operators) only when a remediation slot is actually in contention — no pending user request, and `_remediation_streak_capped()` is not engaged — so its `git rev-parse` probes stay off the user-request and throttled paths. It shares a single `get_recent_tasks(30)` tail read across the whole scan (passed into each `_pending_pr_head_stalled` probe, so K leading stalled entries cost one read, not K), and the per-entry `git rev-parse` is taken only for a PR with prior laps — a fresh PR skips it entirely. The `_remediation_streak_capped` gate, the `_consecutive_remediation` increment, and the post-pop `dequeue_gates` sequence all apply to the *selected* (non-stalled) entry exactly as they did to the old head.

`generate_task` no longer drains user / PR requests — it is now a pure queue curator (prune / edit / enqueue against `task_queue.json`). The `next_task_directive` slot still bridges contemplation / audit steering into the next generation pass, but it influences queue *enqueue* rather than execution. Audit-stall and cost-risk pre-call gates short-circuit the phase entirely. Post-call gates (terrain) drop the offending new entry without rejecting the whole response, since at queue scale the LLM can simply pick a different idea next cycle.

Supported entry points: the dashboard `POST /api/messages` endpoint (which defaults `message_type` to `instruction`) and the Telegram inbound path in `MaestroAgent`'s notifier callback (which constructs `Message(..., sender="thomas", message_type="instruction")`). Both flow through `MessageStore`, so both reach the enqueue branch. Email has no inbound `save_message` path today and therefore cannot enqueue.

## Mechanical Self-Audit Phase

The `audit_self_model` phase runs between `evolve` and `dream` in `_LOOP_PHASES`, gated by `[loop] audit_self_every` (default 10; `0` disables; smoke-skipped like `dream`). It runs the deterministic rules in `maestro/audit_checks.py` over `(get_recent_tasks(20), success_rate(20), self_model, get_recent_question_resolutions(50))` — no SDK calls.

### `run_all_checks` rules

Rules 1–7, the flag-gated, un-numbered `check_unbound_capability_claim`, and the flag-gated rule 23 (`check_closed_reference_claim`), dispatched by `run_all_checks`; rules 9–22 are dispatched from `maestro/loop/self_audit.py::audit_self_model` — rules 9–21 tabulated under *Audit rule registry* below, and the forced-arm-only rule 22 (`green_ready_handoff`) under *Forced arms*.

1. **`check_success_claim_vs_rate`** — capability prefix-matches a success keyword + success rate <60% over ≥5 tasks.
2. **`check_stability_claim_vs_failure_streak`** — capability prefix-matches a stability keyword + trailing failure streak ≥3.
3. **`check_repeated_error_without_limitation`** — same first-line error fingerprint ≥3× and no `limitations_known` entry shares ≥2 non-stopword tokens with it.
4. **`check_repeated_target_attempt`** — the same GitHub issue number appears in ≥3 distinct recent task goals (any outcome, per-task set semantics — duplicate `#NNN` mentions in a single goal collapse) and no `limitations_known` entry mentions that exact issue (`#NNN` substring), and the issue is not in the `settled_prs` set threaded from the settlement reconciler (a lap repeatedly naming a settled `#NNN` is the remediation that landed it, not an unlearned limitation, so it is skipped before the threshold test). Surfaces a Sisyphean retargeting pattern as a self-model limitation for the agent to integrate.
5. **`check_stalled_question`** *(deferred rule, per-rule cap 1)* — same open question targeted ≥3× whose latest `QuestionResolution.disposition` is `kept`. An `unresolved` orphan latest row (the question left `open_questions` before any verdict landed) defers rather than fires. Self-extinguishes when the LLM rewords/removes the question so it leaves `open_questions`. Reads `Memory.get_recent_question_resolutions(50)` threaded through `run_all_checks(..., resolutions=...)`.
6. **`check_stale_self_model_entry`** *(deferred rule, per-rule cap 1; `[audit] stale_entry_enabled`)* — an `identity_statements` / `capabilities_known` / `values` entry whose content tokens never reach `_STALE_ENTRY_MIN_TOKEN_OVERLAP` (2) prefix-matches in any single recent journal / task / audit / resolution string. Stays silent below `_STALE_ENTRY_MIN_FIELD_CARDINALITY` (3) entries in the field, since sparse fields are load-bearing by composition and flagging there would force premature REMOVEs. `limitations_known` and `open_questions` are excluded — proposal 046's `surface_limitations_as_questions` and rule 5 already own their liveness loops.
7. **`check_kept_task_not_promoted`** *(non-deferred, per-rule cap 1)* — `_KEPT_TASK_NOT_PROMOTED_THRESHOLD` (3) or more successful kept task branches that no evolution plan cites as `source_task_id`. Non-deferred because it is a mechanical floor (count + evidence) rather than a meta-rule, so it competes alphabetically with the legacy rules and reliably surfaces the un-promotion gap.
- **`check_unbound_capability_claim`** *(deferred rule, per-rule cap 2 = `MAX_FINDINGS_PER_RULE`; `[audit] evidence_bound_claims_enabled`)* — a live `capabilities_known` claim whose `claim_evidence` record is absent or non-`resolved` (reads the map that `update_self_model` writes). Un-numbered so rules 9–22 keep their numbers; added to the finding dict only when the flag is on.
- **Rule 23 — `check_closed_reference_claim`** *(deferred rule, per-rule cap 1; `[audit] closed_reference_enabled`)* — an authored `identity_statements` / `values` / `capabilities_known` / `limitations_known` / `open_questions` entry (not `[audit]`/`[limitation]`-prefixed) whose every cited `#NNN` the code host reports closed. `audit_self_model` (`maestro/loop/self_audit.py`) resolves the cited numbers through `resolve_closed_refs` (bounded by `_CLOSED_REFERENCE_MAX_LOOKUPS` read-only `CodeHost.get_issue_state` calls) and passes the confirmed-closed set as `closed_refs`; the entry is added to the finding dict only when that set is non-empty. A partially-open or unknown citation stays silent.

`AuditFinding` (frozen dataclass) surfaces each hit with `(kind, statement, cites, rule)`. The `kind` literal grew to include `stalled_question` alongside `contradicted_claim` / `undeclared_limitation`.

### Match semantics

Keyword matching for rules 1 and 2 is **token-prefix** (via `search.tokenize`) so inflected forms hit (`effective` → `effectively`, `effectiveness`) while explicit negations (`ineffective`, `unstable`, `inconsistent`) do not. Rule 3 strips an English stopword set (`the`, `when`, `of`, …) before intersecting to avoid spurious matches — but keeps content words like `error`/`exception` because they carry semantic weight in failure contexts. Rule 4 is keyword-free: it counts the *distinct tasks* whose `goal` contains `#NNN` (the shared `extract_issue_numbers` helper returns a set per goal) and silences itself when any limitation contains the matching `#NNN` substring.

`run_all_checks()` round-robins findings by `_rule_priority` (non-deferred rules first, then `_DEFERRED_RULES`, alphabetical within each group). With the four legacy rules at per-rule cap 2 (eight candidates), `stalled_question` / `stale_entry` deferred at cap 1 each (ten), the non-deferred `kept_task_not_promoted` at cap 1 (eleven), and — only when `[audit] evidence_bound_claims_enabled` is on — the deferred `unbound_capability_claim` at cap 2 (thirteen), clipping at `MAX_FINDINGS_PER_CYCLE` (4, aligned to `MAX_AUDIT_OPEN_QUESTIONS`) admits only the rotation's first round. The deferred rules — including rule 23 `closed_reference` at cap 1 when `[audit] closed_reference_enabled` resolves a closed citation — therefore always yield. Note this no longer leaves one slot per legacy rule in every cycle: `kept_task_not_promoted` is non-deferred and sorts first alphabetically among the five non-deferred rules, so a cycle in which all five fire starves `success_claim_vs_rate`, the alphabetically last — pinned by `test_run_all_checks_round_robin_starves_last_legacy_rule`. A cross-module invariant test guards the cap relationship against drift.

### Persistence and feedback

Each hit is:

- Recorded as a journal event (`Journal.record_event` → `events.jsonl`) with `entry_type="audit_observation"`, distinct from `realization` so event readers preserve provenance; no prompt reads it.
- Upserted into `open_questions` as `[audit] {kind}: {statement[:160]}` — one slot per normalised key, refreshed to the tail when the finding re-fires.
- Persisted to `audit_history.jsonl` as an `AuditResult` row.

Zero-finding cycles still persist a row so "last audit found nothing" is an observable signal.

The next `contemplate()` reads `memory.get_most_recent_audit()` and threads `recent_audit_findings=...` through `update_self_model()`, which renders an INTEGRATE / REFUTE / KEEP prompt section after the self-directed section. Because the same latest result is returned on every contemplation between audits, findings survive at least one contemplation window instead of being evicted after a single cycle.

### Self-extinguishing rules

When Claude INTEGRATEs a finding (e.g. drops the overreaching capability, adds a matching limitation), the underlying condition stops holding and the next audit produces no finding. REFUTE rewrites the `[audit]` entry to `[audit refuted] …`, which still counts against `MAX_AUDIT_OPEN_QUESTIONS` (the sub-cap prefix match is `"[audit"`).

The phase body does not catch: a rule bug or an I/O error propagates to `run_loop`'s crash boundary (fail-loud), so that iteration skips `dream` and the loop shuts down with `crashed=True`. The phase is not in `_BUDGET_GATED_PHASES` because it has no SDK cost.

The cap alignment (`MAX_FINDINGS_PER_CYCLE` = `MAX_AUDIT_OPEN_QUESTIONS` = 4) is load-bearing: prior to alignment the cap was 5 against a sub-cap of 3, which meant 2 findings per cycle were silently dropped from `open_questions` on save and could never reach the INTEGRATE/REFUTE/KEEP prompt, preventing self-extinguishing. The caps were bumped from 3 to 4 in lockstep when rule 4 (`repeated_target_attempt`) was added, so that the four legacy rules could then fire in the same cycle without orphaning findings; the deferred rules yield their slots via `_DEFERRED_RULES` rather than forcing another bump. That per-legacy-rule guarantee has since lapsed: the non-deferred `check_kept_task_not_promoted` competes for the same four slots, so the alphabetically last legacy rule is starved when all five non-deferred rules fire — see the round-robin note above.

### Audit-stall actuator (proposal 044)

The audit's self-extinguishing contract — "a finding stops firing once Claude integrates it" — is currently advisory: nothing prevents a `KEPT`-but-unintegrated finding from firing every cycle indefinitely. The audit-stall actuator closes that gap. When `[audit] stall_block_enabled` is `true` and an `[audit]`-prefixed open question survives `[audit] stall_threshold` consecutive `audit_self_model` cycles (default 5; *audit cycles*, **not** loop iterations — at default `[loop] audit_self_every=10` that is ≈50 iterations of grace) without the LLM removing it, `generate_task` returns `(None, None)` before the SDK call. Generation pressure thereby converts into integration pressure: the block clears automatically once the LLM acts on the finding and removes the `[audit]` entry from `open_questions` (INTEGRATE / REFUTE), as `_audit_stall_run`'s docstring states. The operator's levers are setting `[audit] stall_block_enabled = false` to turn the block off, or asking Maestro over the message channel (dashboard `/api/messages` or Telegram) to integrate or refute the finding; the dashboard deliberately has no self-model write route (it is a thin status layer).

The counter is computed-on-read from `audit_history.jsonl` via `audit_checks.compute_audit_stall_counts(recent_results, open_questions)` — no persisted-schema change, no migration, no fingerprint bump. The matcher walks audit results newest→oldest and for each `[audit]`-prefixed question counts the consecutive most-recent cycles whose `findings` reproduce the same `[audit] {kind}: {statement[:160]}` shape (case/whitespace-normalised via `_normalize_question`). The first non-matching cycle stops the count for that key. Once the LLM removes the entry from `open_questions`, the gate clears on the very next iteration. The block site is purely-read-+-pure-decision, so it is safe under `_LOOP_PHASES` resume; the existing `next_task_directive` clear-on-success runs *after* the SDK response, so a pending directive is naturally preserved across gate firings.

Defaulted off (`stall_block_enabled = false`) for opt-in lived-data validation: leaving the actuator dormant lets us study how often findings would have stalled and at what threshold before flipping the flag on in production. Future bridges (e.g. auto-removal at 2× threshold as the deadlock backstop, health-gated stage transitions) follow the same computed-on-read + reversible-flag pattern.

### Ground self-report beliefs in perception (proposal 088)

Two default-off, zero-SDK additions extend the merge-truth grounding discipline beyond the PR-remediation domain, installing one principle in both directions: a closed belief must point at a successful probe, and a claim disputing git cannot dispute it forever.

**Outcome-gated question closure (rule 16).** `_classify_disposition` closes an `open_question` purely from the before/after diff of the list; the probing task's `outcome` is stamped onto the `QuestionResolution` row but never consulted, so a question a *failed* task probed can be marked answered. `is_grounded_closure(resolution)` (`maestro/audit_checks.py`) returns `False` only when `disposition == "removed"` and `outcome != "success"`; `check_ungrounded_question_closure` (rule 16, behind `[audit] ungrounded_closure_enabled`) emits one `contradicted_claim` finding per ungrounded removal, re-surfacing the closed question through the standard audit→`open_questions` path so the LLM re-opens it or justifies the closure. Self-extinguishing once the row scrolls out of the read window or a successful probe re-resolves the question. It joins `_registered_audit_checks` and is dispatched in `audit_self_model` (`maestro/loop/self_audit.py`) with the same prepend-and-re-clip pattern as rules 9–14.

**Reality-refutation escalation.** When the LLM picks REFUTE in `update_self_model`, a git-grounded `[audit]` entry is rewritten to `[audit refuted] <counter-claim>` and the finding re-fires next cycle with no escalating consequence. `measure_reality_refutation` (`maestro/audit_checks.py`) mirrors `compute_audit_stall_counts` over the over-claim-on-unmerged reality-grounded rules (`_REALITY_GROUNDED_RULES`: `unconfirmed_own_landing` — plus `undercredited_landing` (rule 20), which is git-grounded but fires on a *merged* SHA and carries a SHA not a `#NNNN`, so it contributes no `(rule, PR)` key here and leaves this sensor's behaviour unchanged), counting the consecutive recent cycles each `(rule, PR)` recurred. `format_reality_refutation_summary` surfaces a `REALITY-REFUTATION` contemplation line (behind `[audit] reality_refutation_display_enabled`) when a count reaches `[audit] reality_refutation_threshold` and a matching `[audit refuted]` entry names the PR. The actuator (behind `[audit] reality_refutation_enabled`), after persisting the cycle, delivers exactly one merge-or-close message plus a durable `pr_number`-keyed standdown via `escalation_bridge.deliver_reality_refutation` for any such PR git still shows unmerged (`_host_or_git_pr_merged`). The standdown reuses the no-escalation-bridge ledger, so it suppresses further remediation minting and is auto-released by `prune_resolved_standdowns` when git shows the PR merged/closed. Idempotent per target; no schema change (both halves read fields already on `QuestionResolution` / `audit_history.jsonl`).

**Refutation accountability across the whole audit class (proposal 129 Phase C).** The reality-refutation escalation above is narrow — a two-rule allowlist (`_REALITY_GROUNDED_RULES`) whose only response is a message to Thomas, leaving the disputed question standing. The accountability layer widens the pushback and aims the correction at the *self-model*, because determinism is not authority: the registry mixes git/ledger facts with derived aggregates and prose heuristics, and only the fact-reading class earns a mechanical override. `RULE_AUTHORITY` (`maestro/audit_checks.py`) classifies every registered rule as `mechanical_fact` (a git-ancestry read, a plan-store status transition, or the message/plan ledger — e.g. the unconfirmed/under-credited-landing pair, the phantom-escalation/partial-prune pair, reconcile-near-miss, orphaned-cure), `derived_measure` (a rate/streak/window aggregate), or `heuristic` (a keyword or prose shape whose false positive is exactly what REFUTE exists for). A drift guard (`test_rule_authority_covers_registry`) pins the map to the live registry's `rule=` constants in both directions, and `mechanical_fact_rules()` is the single source of the class filter. For the `mechanical_fact` class only, `measure_refutation_rejections` generalizes `measure_reality_refutation`'s consecutive-from-newest walk from a single `#NNNN` to a three-family target set per finding (issue numbers and committed SHAs mined from the statement, plus each cited task/plan id), and behind `[audit] refutation_accountability_enabled` (threshold `[audit] refutation_rejection_cycles`, ≥ 1) `audit_self_model` (`maestro/loop/self_audit.py`) mechanically restores a refuted question whose rule kept re-firing on the same target back to its canonical `[audit]` text — re-derived from the newest finding so `compute_audit_stall_counts` keeps keying on it, and dropped instead when that canonical string is already present (the re-firing finding appended it earlier the same cycle). The override is stamped to the journal and a `refutation_accountability` gate-activation row, and surfaced on the existing `REALITY-REFUTATION` contemplation line (an additive "N refutation(s) mechanically overturned" clause). Derived measures and heuristics stay refutable indefinitely, and the layer is self-extinguishing — a finding that stops re-firing is never restored. Dark-launched default-off, so the flag-off tree is byte-identical; `_REALITY_GROUNDED_RULES` and the merge-or-close actuator stay live and untouched beside it.

### Under-credited-landing audit rule (rule 20)

Every landing-grounding rule before this one catches *over*-claiming — a verdict that asserts more than git shows. `check_unconfirmed_own_landing` (rule 14) disputes a `success` / resolved-on-branch claim whose SHA never reached `origin/main`. Not one watched the opposite direction, and that asymmetry was not neutral: a measurement apparatus that can only *downgrade* landing-work and never once *credits* a confirmed landing is all-downside on the exact act it should reward. The lived evidence was a real two-parent merge — the single most-authored CAN'T-to-DID — pre-emptively stamped `partial` while ten cheap writable-half disposals scored `success`; the self-labeling bias trained the disposal treadmill.

`check_undercredited_landing` (rule 20, `maestro/audit_checks_phantom.py`, behind `[audit] undercredited_landing_enabled`, default-off) is the affirmative twin of rule 14. It scans a non-`success` task's `result_summary` for an own-committed SHA (`extract_self_committed_shas`, the shared FM4 extractor) and asks the same `merge-base --is-ancestor` oracle rule 14 uses (`is_branch_merged_into_main`, keyed by SHA) whether that commit reached `origin/main`. Only when it *did* does it surface one finding: "you authored a landing and stamped it non-success." The ancestry probe is memoized within the scan (one subprocess per distinct SHA) and each landed SHA yields at most one finding (deduped across tasks). It is deliberately **not** an auto-relabel — the `partial` may be correct for other goals, so the rule only surfaces the under-credit as an `[audit]` question for the LLM to judge, never rewrites the verdict. It self-extinguishes when the outcome is `success`, when no own-committed SHA is cited, when the summary confirms another party's landing (`classify_landing_attribution` → `CONFIRMED`, the same skip rule 14 applies, via one shared predicate), or when the cited SHA is not an ancestor of `origin/main`. It joins `_registered_audit_checks` and is dispatched in `audit_self_model` (`maestro/loop/self_audit.py`) with the same prepend-and-re-clip pattern as rules 9–19.

### Orphaned-cure retirement requires a delivered disposition (proposal 091)

Rule 11's retire actuator (`Memory.sweep_orphaned_cures`) once flipped an aged, conflict-evidenced `implemented`-but-unmerged plan to `obsolete` *silently* — even when its pull request was still open — leaving a zombie PR: dropped from the active plan set with a "the PR stays open for human disposition" note no human was ever shown. `sweep_orphaned_cures` now takes a required `deliver_disposition: Callable[[EvolutionPlan], bool]` and calls it before firing `mark_plan_obsolete`; a `False` return skips the retirement (no `fire_and_capture`, no `lever_attempts.jsonl` row), so the plan stays `implemented` and Tend keeps servicing it — nothing is orphaned. Retirement and its delivery precondition are thus atomic per plan.

`audit_self_model` (`maestro/loop/self_audit.py`) supplies the closure (behind the existing `[audit] orphaned_cure_retire_enabled` switch). It resolves the PR number via `EvolutionEngine._pr_number_from_url` and calls `escalation_bridge.deliver_retirement_disposition`, which — under the shared standdown-ledger lock — posts one close-or-keep **PR comment** (via `code_host.comment_issue`), appends one durable close-or-keep **message to Thomas** (`disposition-<pr>` id, deliberately distinct from the `handoff-<pr>-…` family so `measure_handoff_relapse`'s `^handoff-(\d+)-` pattern never miscounts it), and records a `pr_number`-keyed **standdown**. Idempotency is keyed on the `disposition-<pr>` message being on record, **not** on mere standdown presence: a prior escalation deliverer (`deliver_handoff` / `deliver_reality_refutation` / `deliver_claimed_escalation`) records a `pr_number`-keyed standdown but posts *no* on-PR comment, so gating on standdown presence would let retirement proceed with the close-or-keep breadcrumb never landing. Gating on the disposition message guarantees the PR comment lands exactly once per PR regardless of any prior standdown, and a prior deliverer's standdown record is preserved rather than clobbered. If the comment post fails it writes nothing and returns `False` (fail-closed); once the `disposition-<pr>` message exists a re-run re-posts nothing and returns `True` (idempotent). The closure itself refuses (returns `False`) when there is no message store or the `pr_url` is missing/unparseable — no plan is retired without a real delivery path. The standdown reuses the no-escalation-bridge ledger, so it suppresses further remediation minting and is auto-released by `prune_resolved_standdowns` when the host reports the PR merged/closed.

### Limitation→evolution bridge (proposal 046)

Limitations are surfaced "what I can't do" — but until they reach `generate_task`'s anchor pool they don't drive evolution work. `Consciousness.surface_limitations_as_questions(model)` mirrors every entry in `limitations_known` as a synthetic `[limitation] <text>` row in `open_questions`, called at the end of `contemplate` immediately after `update_self_model` returns and before `_record_question_resolutions`. The same fuzzy `match_open_question` anchor that drives audit findings then makes each limitation a first-class self-directed-task target.

The cap composition extends to three buckets: `MAX_AUDIT_OPEN_QUESTIONS = 4`, `MAX_LIMITATION_OPEN_QUESTIONS = 3`, and the remaining slots up to `MAX_LIST_ITEMS = 10` for self-generated questions. The walk in `_enforce_open_questions_caps` preserves relative order across all three buckets. Surfacing is idempotent and case/whitespace-insensitive: an existing entry that normalises to the same key — regardless of provenance prefix — blocks duplication.

Closure runs through the existing REMOVE/REFINE/KEEP path. The `update_self_model` prompt now instructs the LLM that when a `[limitation]` finding shows progress, it should also revise or remove the matching `limitations_known` entry — otherwise surfacing re-adds the row next cycle and the disposition records as `kept`, so soft self-knowledge gets the same self-extinguishing semantics as audit findings. For the two fields the protocol asks the LLM to shrink — `open_questions` and `limitations_known` (`Consciousness._CLEARABLE_FIELDS`) — an explicit `[]` in the reply *clears* the field, so closing out the last open question or the final known limitation is representable; omitting the field still means unchanged, and a non-empty list that validation filters to nothing still preserves the prior value (a rejected intent is not a clear). Every other tracked field keeps preserve-on-empty. The audit-stall actuator (044) doesn't gate on `[limitation]` directly; deferred until lived-data shows whether limitation rows stall in practice.

### Restatement similarity gate

The self-model accumulates entries that restate the same tension under different labels — "instrument saturation", "construction-as-uncertainty-response", and "restatement convergence" might all describe facets of the same build-over-act bias. This bloats the identity prompt and creates false signal of novel insight. The restatement gate is a mechanical blocker (prevents the behaviour) rather than another measurement instrument (describes the behaviour).

`detect_restatement(candidate, existing, threshold)` in `consciousness.py` computes content-word Jaccard similarity between a candidate entry and every existing entry in the field. Content words are extracted by `_content_tokens()`: lowercase, alphabetic-only regex, filtered against `_STOP_WORDS` (~60 common English words) and tokens ≤2 characters. When the Jaccard coefficient meets or exceeds `RESTATEMENT_THRESHOLD` (default 0.5), the candidate is blocked and the matched entry is returned.

The threshold of 0.5 is conservative — it triggers only when the majority of content words are shared between the candidate and an existing entry. Two entries with entirely different framing but ≤50% word overlap pass through; two entries that reuse the same core vocabulary under a different label are blocked.

The gate fires inside `update_self_model()` on the list-apply path, after non-string filtering and before the `MAX_LIST_ITEMS` cap check. Only genuinely new items (not present in the pre-update snapshot) are checked; preserved items pass through unconditionally. The gate applies identically to all five tracked fields (`identity_statements`, `capabilities_known`, `limitations_known`, `values`, `open_questions`) with no field-specific exemptions. Blocked items are logged at INFO level with the blocked text and matched entry text. Zero LLM cost.

### Forced arms — detection paired with delivery

Several rules pair detection with an actuator so the finding is *completed* rather than re-journalled each cycle. Each delivers one merge-or-close message plus a durable keyed standdown, auto-released by `prune_resolved_standdowns` on merge/close (or aged out by `prune_expired_standdowns` where the key can never merge, as with a plain issue number):

- **Rule 12** (`phantom_escalation_delivery_enabled`) → `deliver_claimed_escalation` on a finding unreferenced for ≥2 laps.
- **Rule 14** (`unconfirmed_landing_forced_enabled`) → `deliver_handoff`; a finding with no `#NNNN` (a PR-less on-branch handoff) is instead completed by a fire-or-close `next_task_directive`.
- **Rule 11** retirement is *gated* on `deliver_retirement_disposition` — see the dedicated section above. A `False` return leaves the plan `implemented`, never a silent zombie PR.
- **Rule 22** (`green_ready_handoff_enabled`, default-on) → `deliver_handoff` the instant an owned git-unlanded PR reads merge-ready (every CI check SUCCESS, no code-clearable blocker, no `pr_number`-keyed standdown). Forced-arm-only — no journal detector, it fires the actuator directly — and the earliest, most-owned handoff, firing before the escalation bridge's lap-budget-exhaustion path. The dequeue chain's `ci_pending_green_handoff` arm (`[loop] ci_pending_green_handoff_enabled`, default-off) is the earlier writer of that same pair, for a PR green under the local gates while its CI is still pending.

### Escalation bridge

`escalation_bridge.py` completes an unlanded-remediation lineage that has burned past `[loop] pr_remediation_lap_budget`: it delivers one merge-or-close message plus a durable `pr_number`-keyed stand-down that blocks Tend-route minting until the PR is merged or closed. Without it a lineage can lap indefinitely, each lap re-deciding to try again.

Three paths release that latch:

- the merge/close pruner, once the PR settles;
- the expiry pruner, for a key that can never merge;
- under the default-off `[loop] refutable_standdown_enabled`, `prune_refuted_standdowns` — the live owed-act reading the tend walk already measured refutes the latched `handoff-ready` claim.

The refutation release *speaks* and is budgeted rather than being silent: it appends one `standdown-withdrawn-<pr>-<n>` message naming the PR and the refuting blocker, and releases only once a thread re-read confirms that message landed. After `[loop] standdown_refutation_release_cap` releases the latch becomes permanent, with a single `standdown-refutation-capped-<pr>` message sent once. `count_refutation_releases` over the append-only message ledger is the cap authority, because the release itself deletes the stand-down record and so cannot be counted from state.

Two bounded exemptions keep the latch from muting genuine new work: a genuinely-new review thread earns one Tend lap past the stand-down (tracked by `serviced_comment_ids`), and an outdated un-replied thread earns one bounded reply lap. The lap treadmill otherwise stays suppressed.

## Record-time outcome binds

The audit rules above are post-hoc journal arms. `outcome_grounding.py` is the write-time complement. The remediation-PR landing verdict itself is now authored unconditionally by the §5d mechanical authority (`outcome_authority.decide_outcome`, proposal 105) — `success` iff the branch reached `origin/main`, else `partial`, reading no prose — so the narration-citation downgrade binds are retired. What remains here are write-time *actuators* that act on a git/host fact rather than overlay a verdict on narration, plus the affirmative settled-coercion; each reads merge state through the `is_pr_settled` chokepoint.

- `bind_ci_failing_verdict_to_red_read` — a completion-narrating remediation on a `CI_FAILING` own PR for which the CI-failure oracle surfaced a concrete failing-check error line this lap (the `_ci_oracle_surfaced` cache) that the lap did not commit-and-push a fix for has its resolution keywords scrubbed, stays `partial`, and fills an empty directive with the red-gate one. The scrub exempts the load-bearing admission phrases downstream sensors read (`PROTECTED_ADMISSION_PHRASES` — e.g. `resolved on branch`, `already merged`) so rule 14 and the settled/no-op/confirmed-landing sensors stay sighted; the `CAUSED` landing phrases are deliberately *not* exempt, so a costume merge claim is neutralised rather than over-claiming a caused landing.
- `bind_mergeable_flip_to_merge_request` (`[loop] mergeable_merge_request_enabled`) — a PR that reconciles to clean-but-unlanded with `AWAITING_APPROVAL` as its sole blocker sends exactly one named merge-request, idempotent on a persisted `(pr_number, head_sha)` marker. No new push capability.
- `bind_costume_discharge_to_partial` (`[loop] frame_discharge_bind_enabled`) — caps a verdict that discharges its obligation by restating the frame rather than moving it: a completion-narrating remediation whose lap produced no landing and no push is held at `partial` with a frame-discharge note appended, so a costume discharge cannot stamp itself done.
- `coerce_verdict_to_settled_on_merge` — the affirmative direction: a phantom not-landed stamp coerces to settled `success` when git shows merged.
- The not-landed remediation verdict's recorded `merge blocker:` label splits the flat `CI_PENDING` rollup costume into three honest states via `pr_facts.classify_merge_blocker_label` (composing the readiness fact's `ci_state`/`awaiting_approval` with `classify_ci_conclusions`): `CI_RUNNING` (checks still in progress — hold), `AWAITING_REVIEW` (all checks green but review outstanding — hand to Thomas), and `CI_FAILING` (a concluded failure — fix), so verdicts, the label-reading behavioral sensors, and the `pr-lap-ledger` stop conflating a running-CI wait with a review wait.

### Settlement ledger

Under `[audit] settlement_reconciler_enabled`, `reconcile_settled_verdicts` runs each cycle: it binds the trailing remediation verdicts to the `is_pr_settled` chokepoint and upserts every PR it finds settled into `settled_verdicts.jsonl`. `audit_self_model` (`maestro/loop/self_audit.py`) then threads that settled set into the PR-keyed phantom rules *before* any merge predicate runs, so a PR already known settled costs zero merge-oracle calls on every later cycle — the ledger converts a repeated host read into a one-time one. Covered by `tests/test_settlement_reconciler.py`.

### Fetch-before-word gate

`gate_remediation_verdict` is the sibling write blocker, and the one member of this family that lives in `remediation_tracker.py` rather than `outcome_grounding.py`. Where the binds above correct a verdict against what git *shows*, this one refuses a verdict that never *looked*: a remediation `success`/`partial` whose verdict carries any `_FETCH_REQUIRED_NARRATIVES` marker — the two push markers plus the two Tend-clearable merge-block reason codes, i.e. every claim that the cure resolved on-branch and merely awaits a push — is force-downgraded to `partial` under a `[fetch-missing]` prefix unless a per-task `record_fetch_truth` marker proves `git fetch` + `--is-ancestor` ran before the status word was composed. It is the enforcement floor under the `MERGE_TRUTH_FIRST_PREAMBLE`'s fetch-before-word contract — nothing else in the loop prevents a status word from preceding git's verdict, so the prompt-level instruction alone would stay advisory.

The gate has a second, narrower arm over the same contract's *ownership fork*. Where `record_fetch_truth` proves the `git fetch` + `--is-ancestor` read ran, `record_obligation_fork_truth` proves the preamble's OWNERSHIP-FORK step ran — the `git rev-parse HEAD` vs `origin/<branch>` comparison that decides whether a push is still owed. An `owned_awaiting_push` verdict is therefore routed one of two ways: with no fork marker it is downgraded under a `[fork-missing]` prefix, because the verdict asserted an ownership conclusion the loop never measured; with the marker present and HEAD genuinely ahead it keeps the honest `[push-owed]` partial, whose bracket is its own and is deliberately distinct from every `Marker` value so a downstream `classify_lap_delivery` scan cannot misread a push-owed lap as a delivery.

### Red-root diagnosis

`red_root.diagnose_red_root` is the ordering guard these binds enforce after the fact: on every admitted CI-red or CI-pending own-PR remediation lap it runs the demanding gate (ruff → mypy, behind an injected-runner seam) as action zero — on the PR head: for a pure post-merge quality-gates directive right after the preflight checks the PR branch out and before its probe-merge, for every other directive (the pre-merge `ci_failure_on_head` route, conflicts, reviewer feedback) at dequeue via `_diagnose_red_root_on_pr_head`, which positions and restores the PR branch itself (#4216) — and records the concrete failing-gate blocker to the journal and a `red-root.md` artifact, so the demanding probe is known before the obligation-free is-ancestor read. Under `[loop] gate_environment_oracle_enabled` it is fed the cached runnability verdict (`gate_environment.read_verdict`, never refreshed): when `blames_missing_sibling` reads it `UNPROVISIONED`, the red gate's recorded blocker leads with the oracle's `format_verdict` line (ending in the repair) ahead of the gate's own first error, so an environment gap is named without laundering a genuine defect.

## Dropped-directive replay

The directive bridges listed in `CLAUDE.md` all write into an *empty* `next_task_directive` slot, so a fire-or-close directive raised while the slot is occupied is simply lost. Under `[loop] dropped_directive_replay_enabled` it is instead banked to `dropped_directives.jsonl` via `directive_ledger.offer_directive`; the lowest-precedence `replay_dropped_directive` gate re-offers the oldest still-live entry into a later empty slot, re-verifying liveness through `is_pr_settled` / `is_branch_merged_into_main` and pruning settled, landed, or aged entries. Offers are idempotent: a re-offer of the slot's current occupant is not a drop and is never banked, and a re-offer matching a banked row on text and grounding (`pr_numbers`, `shas`) leaves the original row — and its age-out clock — untouched.

## Pending-Plan Curation

`Memory.refine_plan()` historically had no production caller — `refined_at` stayed `None` and stale `pending_review` plans accumulated without ever being refreshed or self-pruned. The `curate_pending_plans` loop phase (proposal 060) closes that gap: one bounded refresh pass per cadence tick over the oldest unrefined pending plan.

### Opt-in gate

The phase is **disabled by default** and double-gated: both `[loop] curate_enabled = true` and a positive `[loop] curate_every` are required before it runs, so an autonomous LLM rewriting human-reviewable plans never turns on without the operator's say-so (mirroring how proposal 044's audit-stall actuator shipped behind `[audit] stall_block_enabled`). `_phase_will_run` applies the standard cadence machinery: skipped under `--smoke`, gated by the burn-rate throttle (`curate_pending_plans` is a member of `_BUDGET_GATED_PHASES`), and deduped via `_last_phase_iteration` so frozen iteration ticks don't re-fire it. Setting `curate_enabled = false` fully disables the phase without a code revert; `curate_every = 0` disables only the cadence, because under `[loop] plan_feedback_enabled` the phase still fires off-cadence while a pending plan holds unaddressed reviewer feedback (see [Reviewer feedback on pending plans](#reviewer-feedback-on-pending-plans)).

### Selection and verdict

`select_curation_target()` (`maestro/audit_checks.py`) is a pure, zero-SDK-cost selector: it filters to `status == "pending_review"`, prefers rows with `refined_at is None`, and sorts ascending by `created_at` with a stable `plan_id` tie-break. An optional grace period — `[loop] curate_min_plan_age_hours` (float hours, default `0.0` = no delay) — drops any plan whose `now - created_at` is below the floor before the sort (an empty/unparseable `created_at` is treated as not-yet-eligible), so a freshly-minted plan is not rewritten before the operator has read the original; both the phase-entry guard and the engine's own selection pass the same `now`/`min_age_hours` so they never disagree. With `[loop] plan_feedback_enabled` on, plans holding unaddressed reviewer feedback sort first and skip the grace floor (see [Reviewer feedback on pending plans](#reviewer-feedback-on-pending-plans)). The phase body (`agent.py` `_curate_pending_plans`) early-returns before opening a session when the selector yields `None`, so an empty queue costs nothing; otherwise it opens or resumes the high-effort slot-B session and delegates to `EvolutionEngine.curate_pending_plans()` — except under `[sdk] single_use_evolution_calls_enabled`, where it opens no slot-B session and the engine runs on its own single-use session.

**Input budget (#4476).** The stored plan fields substituted into the curate prompt are bounded by `curate_input_fits` (`maestro/prompts/curate_plan.py`): every field must sit within its write-boundary cap (legacy rows saved before the caps fail this), `proposed_changes` must hold at most `CURATE_PROPOSED_CHANGES_MAX_ITEMS` items, and the summed length — which includes `files_affected` — must stay under `CURATE_PLAN_INPUT_MAX_CHARS`, derived from those caps. `files_affected` carries no per-field gate (creation leaves it uncapped), so a broad-scope plan is excluded only by the summed budget. Truncation would be unsafe — a `refine` replaces `proposed_changes` and an `obsolete` drops the plan, so the model must never judge content it did not see — so an over-budget plan is never curated: `select_curation_target` drops it before both the feedback lane and the round-robin sort, `render_curate_prompt` raises `ValueError` on it as the hard boundary, and the `_curate_pending_plans` phase body logs one WARNING per cadence naming the excluded ids (ahead of its empty-queue guard, so it fires even when only over-budget plans pend), leaving them to the human's Approve/Reject. That WARNING is a log line, not a reviewer surface, and proposal-145 reviewer feedback on an over-budget plan is still recorded and acknowledged but never serviced — the reviewer must act on such a plan directly. The stored `proposed_changes` list is never count-capped, because the CLI-grounding and plan-scope guards read it whole.

The engine formats `CURATE_PLAN_PROMPT` (`maestro/prompts/curate_plan.py`) with the target's body plus the write-boundary field caps, runs one session-attached query, and parses a JSON verdict with `action: "refine" | "obsolete" | "keep"`:

- **refine** — only the fields the model actually returned (JSON `null` counts as omitted) are forwarded to `Memory.refine_plan()`, which stamps `refined_at`; an `evolution_note` is journaled and Thomas is alerted via `Notifier.notify_plan_refined` (best-effort, mirroring `submit_for_review`). The plan stays `pending_review` — the human still gives the final Approve/Reject on the refined body.
- **obsolete** — `Memory.mark_plan_obsolete(plan_id, reason)` self-prunes the plan into the terminal `obsolete` status, which never feeds rejection learning; journaled, no refined-notification.
- **keep** — no plan-body change; stamps `last_curated_at` and `curated_hash` (see below).

A malformed response (invalid JSON, non-object, missing or unrecognised `action`, or a verdict carrying no usable fields) is logged and skipped with no plan-body change (only `last_curated_at` and `curated_hash` are stamped, see below), consistent with `propose_plan`'s parse-failure handling. Cap or type violations on a real refine field propagate from the write boundary — fail loud.

**Skip unchanged plans (proposal 155 step 6).** `compute_curation_fingerprint` (`maestro/memory.py`) hashes a plan's reviewable content hash plus the sorted ids of every `reviewer_feedback` entry. Both curator write doors stamp it into `EvolutionPlan.curated_hash` under the plan lock: `Memory.touch_plan_curated` (keep, and the deterministic skips — malformed JSON, unknown action, over-cap refine) and `Memory.refine_plan` (from the post-refine row). `select_curation_target`'s normal lane drops a plan whose stamp equals its live fingerprint, so an unchanged backlog takes the zero-cost `None` return and no session opens; a content edit or a new feedback entry makes it eligible once. Marking feedback addressed does not move the fingerprint. The feedback-priority lane is exempt, so the three-strike release still progresses, and `[loop] curate_skip_serviced_enabled` still applies on top.

### Reviewer feedback on pending plans

Proposal 145 adds a third decision on a `pending_review` plan — **request changes** — alongside Approve and Reject, behind `[loop] plan_feedback_enabled` (default `false`).

- **Ledger.** Each request is a `PlanFeedback` entry on `EvolutionPlan.reviewer_feedback`. The ledger is bookkeeping, so it is excluded from `compute_plan_content_hash`; it is written only through `Memory.add_plan_feedback` (which accepts `pending_review` plans only) and bounded by the caps in `maestro/plan_feedback.py`.
- **Delivery.** Both surfaces write a `plan_feedback` `Message`; the loop owns the plan-row write. On Telegram, a reply to a review message threads back through the heading-line `[plan <id>@<hash prefix>]` marker that `parse_plan_ref` reads. On the dashboard, `POST /api/plans/{plan_id}/feedback` ("Request changes") writes the same message, refusing with 409 when `feedback_serviceable` is false or the unaddressed cap is reached.
- **Fold.** `_process_messages` folds those messages through `fold_feedback_messages` into `Memory.add_plan_feedback`, idempotent on the message id. It acknowledges each recorded entry, names the reason when one is refused, and never enqueues the message into `pending_user_requests`.
- **Trigger.** `select_curation_target` serves a feedback plan first, past the grace floor, and `LifecycleController.phase_will_run` fires `curate_pending_plans` off-cadence while feedback is pending. The off-cadence fire still requires `curate_enabled` (but not a positive `curate_every`), still pauses under the burn-rate throttle, and is still deduped by `_last_phase_iteration`.
- **Response contract.** `curate_with_feedback` requires every verdict to carry a `response`, downgrades a curator `obsolete` to `keep` (the reviewer asked for changes, not a prune), and stamps only the rendered entries addressed. Feedback written against an earlier body is flagged in the prompt by `render_feedback_section`, not refused.
- **Retry bound.** `Memory.record_feedback_attempt` counts failed passes per entry; at `MAX_FEEDBACK_CURATE_ATTEMPTS` the entry is released with `FEEDBACK_UNSERVICEABLE_RESPONSE`, so feedback the curator fails on never piles up; the per-plan unaddressed cap bounds the rest.
- **Exclusions.** An over-budget plan is never curated (see the Input budget paragraph above). The fold and the dashboard route do not check that budget, so feedback on such a plan is recorded and acknowledged but never serviced: no attempt is counted, so it is never released, and it keeps the off-cadence trigger armed until the human approves or rejects the plan. Feedback is not a rejection: it does not feed rejection learning or the rejection cooldown.

### Operator surface

The dashboard's pending-plan card already rendered `| Refined: <date>` when `refined_at` is set, so no UI change was needed — the phase populates the field. The Telegram refined-notification reuses the Approve/Reject keyboard, since the refined plan is still awaiting review.

### Backlog-saturation sweeps

The curate phase above refreshes one plan per tick; it does not drain a backlog. Three zero-SDK, no-approval sweeps run from `generate_task` at the top of each cycle, each retiring a `pending_review` plan through the owned terminal act `mark_plan_obsolete` (disposal, not rejection — an obsoleted plan never feeds rejection learning):

- **Cluster sweep** (`Memory.sweep_clustered_pending_plans()`, `[loop] pending_cluster_sweep_enabled`, default-on) — reuses the cluster detectors behind the submit-time guard (`[loop] pending_cluster_threshold` / `[loop] pending_cluster_max`) and obsoletes all but the newest member of every qualifying theme cluster, draining a self-fed backlog without routing the choice through a per-pop gate. Each retire is captured to the lever-attempts backend like the other sweeps.
- **Restatement sweep** (`Memory.sweep_restatement_pending_plans()`, `[loop] restatement_sweep_enabled`, default-on) — the pairwise complement: it obsoletes every pending plan restating a *strictly-newer* surviving pending plan (keeping the newest of each chain), reusing `[loop] duplicate_pending_plan_threshold` as the Jaccard cutoff rather than adding a knob, and capturing each fire to the lever-attempts backend. It catches restatement chains that never accumulate into a cluster of `pending_cluster_max` members.
- **Expiry sweep** (`Memory.sweep_expired_pending_plans()`, `[loop] plan_review_expiry_days`, default 21) — the sweeps above retire only *redundant* plans, so a genuinely-unique plan that is never reviewed would rot indefinitely against a moving tree. When the horizon is positive, every `pending_review` plan older than it is obsoleted; an approval moves a plan out of `pending_review` and is the explicit hold. Set `<= 0` to disable.

Every sweep fires `mark_plan_obsolete` through `lever_capture.fire_and_capture` with a `verify_obsolete_persisted` re-read, recording the lever's return AND the re-read (`lever_attempts.jsonl`, or the SQLite backend). A sweep reports — to the journal and the `OWNED_PRUNE` deed — only fires recorded `True`, so a member a concurrent dashboard approval moved out of `pending_review` between the sweep's snapshot and the locked write is recorded refused and never named as pruned.

These are the production-side complement to `submit_for_review`'s intake guards (the near-restatement refusal and the `[loop] pending_plan_submit_block_threshold` total-backlog cap): the guards cap what enters the queue, the sweeps drain what already sits in it.

## Fuel-gated evolve (proposal 155 step 4)

Self-initiated evolution spends only on closing a gap issue. `MaestroAgent.evolve` and `_phase_evolve` first call `MaestroAgent._admitted_evolution_fuel`, which delegates to `loop/self_health.admitted_evolution_fuel`, at zero SDK cost: `run_evolve_prestep` runs the self-health detectors, `select_fuel` reads the open issues once through `evolution_fuel.select_evolution_fuel`, and then, unless the fuel is a red `maestro:gate` (which bypasses all three), `_wip_owns_slot`, `_pre_mint_generation_verdict` and then the zero-SDK live-backlog check `_live_backlog_saturated` (the door's `pending_plan_submit_block_threshold` over the live plans, so a saturated backlog does not re-pay a refused `propose_plan` while the pre-mint gate is off) may stand the tick down (the pre-mint refusal still writes `GENERATION_STANDDOWN_DIRECTIVE` into an empty slot). A red `maestro:gate` plan is also exempt from both of the door's backlog-saturation arms (`submit_for_review`'s `exempt_saturation`), bounded to one live plan per gap. With no fuel the phase opens no slot-B session, makes no SDK call and runs no gate subprocess; the full `run_quality_gates` read that fed `reflect` is gone with it.

`select_evolution_fuel` keeps only trusted gap issues (`classify_gap_trust`), skips one with a live plan (`gap_has_live_plan`), one that has spent `[evolution_fuel] max_plans_per_gap` attempts (`count_gap_attempts`, journalled once as `gap-exhausted #N`) and one still inside a rejection cooldown (`gap_cooldown_until`), keeps only a class-1 gap while a gap-citing plan awaits review, and picks the lowest fuel class (`fuel_class_of`: a red gate, then a capability or toolchain gap, then any other gap), oldest first. An attempt is a rejected or merged plan citing the issue, a `failed` one whose `failure_count` has spent `max_implementation_attempts` (under it, implementation retries it, so it stays live, as does a `blocked`, `sliced`, `pending_review`, `approved` or `implemented` plan), or an `obsolete` one the door refused for its content; a saturation or `[deferred:cooldown:<id>]` refusal, and an approved original superseded by its multi-PR chain (whose slices carry the one attempt), are deferrals (`evolution_submission.gap_plan_disposition`).

`EvolutionEngine.propose_plan(gap=...)` prompts `Close this capability gap:` plus `evolution_fuel.render_gap_block` over `_gap_context_inputs` — the issue (its body — operator-written or re-derived evidence alike — fenced as untrusted data; an operator-written title too), the failing gate, earlier citing plans' end reasons, recent human rejections, uncited kept task branches, recently merged titles and the live targets — each input bounded by `GAP_CONTEXT_CAPS` with a truncation marker. `pin_gap_plan` sets the plan's `issue_number` (so the PR body's `Closes #N` closes the issue on merge; a non-final slice of a gap chain writes `Refs #N` instead, and a chain spends one gap attempt only once no slice is live), its `category` (`maintenance`) and `problem_ref = None`. `check_merged_plans` now also runs on every iteration that has an `implemented` plan, so a merged gap plan is marked merged within one tick. Implementation, self-review, the quality gates and human approval are unchanged, and implementing approved plans never consults fuel.

### Stuck-gap tripwire (proposal 155 step 5)

A gap that has spent `[evolution_fuel] max_plans_per_gap` attempts stops being fuel and becomes one build/buy/drop decision for Thomas. `select_evolution_fuel` skips any issue carrying `needs-decision` (`NEEDS_DECISION_LABEL`, read from the one listing). For a gap at the cap it reads the label's latest `unlabeled` event (`IssueTracker.label_removed_at`), and `_reset_point` decides whether that removal was Thomas's "build differently": a removal by an `[evolution_fuel] operator_github_logins` login counts; one by Maestro's own login counts only when Maestro's own record corroborates it — a `gap-decision #N: build` journal event or a `gap_opens` `closed_at` no earlier than the removal (less a clock-skew allowance) — because the bot token is shared with task sessions, whose `gh issue edit` is not action-gated; any other removal is logged and buys nothing. After a counted removal attempts are recounted only from that moment (`count_gap_attempts(since=...)`, a plan with an unparseable stamp still counting), and a gap back under the cap is ordinary fuel. Otherwise it adds `needs-decision` — the label write is the at-most-once fence for the ask — posts one fixed-text comment addressed to the operator (a failed comment is logged and journalled `gap-tripwire-comment-failed`), journals `gap-tripwire #N` and returns the gap in `FuelSelection.tripped`; a failed label write keeps the step-4 `gap-exhausted` skip (journalled once) and retries next tick. An unrecognised removal on a gap already journalled `gap-tripwire #N` is undone silently — label restored, no new comment, no new ask. `close_gap_issue` removes `needs-decision` from a gap it closes, and the door's reopen paths clear a label still left on a reopened issue (a failed removal, or a non-door close), so a reopened gap is fresh fuel with a fresh count. The tripwire is zero-SDK and adds no local state or config key.

`self_health.select_fuel` queues each trip on `_pending_gap_asks`; `evolve` and `_phase_evolve` drain it through `deliver_gap_decision_asks` right after the fuel read, fuelled or not. Each ask is a plain `[gap-decision #N]` message sent through `ask_thomas` (`format_gap_decision_ask`): build and buy are reply words; drop appears only as a link to the issue. `_process_messages` hands every Thomas reply threaded to a `[gap-decision #N]` question to `apply_gap_decision_reply` — consumed, never enqueued — which applies only the first reply that names build or buy (text after the decision word is journalled with it as guidance, and the applied row stamps the reply's id so a crash re-drain does not apply it twice). A reply whose host write failed is journalled `gap-decision-unapplied` and answered by a fresh `[gap-decision #N]` question; a reply naming no option gets a follow-up asking for build or buy. `apply_gap_decision` applies it: build removes the label (the count restarts), buy keeps the gap parked, and drop makes no host write, because only an operator closing the issue drops it (the door's `operator-abandoned`).

## Rejection-Aware Evolution

Rejected PRs trigger `learn_from_rejection()`. A 7-day cooldown prevents re-proposing rejected approaches. Rejection learning is best-effort-and-loud (failures crash the loop — see [loop-lifecycle.md](loop-lifecycle.md)).

### Structured rejection feedback

Every rejected evolution plan triggers a classifier `query()` (`effort="low"`, `caller="rejection_classifier"`) that tags the reason into one of six `RejectionCategory` values: `scope_too_large`, `wrong_approach`, `not_needed`, `quality_issue`, `duplicate`, `other`. A `RejectionRecord` is appended to `rejection_history.jsonl`.

The aggregate prompt splice went with `reflect` (proposal 155 step 4); the records feed the reality inventory's rejection categories, and a fuelled `propose_plan` sees the newest human rejections verbatim in its gap block.

Classifier token parsing scans all whitespace-split tokens and strips trailing punctuation, so decorated replies ("The category is scope_too_large.") still classify correctly. Classifier failures (rate limit, stream stall, parse error) fall back to `"other"` and are swallowed with `logger.warning` — the structured record is always persisted.

Idempotency is preserved by the existing realization-event guard in `learn_from_rejection()` (`Journal.read_events_by_type("realization")`), which short-circuits *before* the classifier runs so a duplicate invocation does not re-classify or re-record. No dashboard surface; `maestro measure-rejection-classes` reads the ledger.

## Failed-vs-Rejected Distinction

Plan implementations that fail (quality gates exhausted, non-transient exception) set `status="failed"` with an incremented `failure_count` and a `last_failure_at` / `last_failure_reason` snapshot (plus a copy of the message in `rejection_reason` for UI/dashboard continuity).

`failed` is distinct from `rejected` (which means a human, or a PR-close event, said no) and does NOT trigger `learn_from_rejection()` or the 7-day `submit_for_review()` cooldown — so a buggy LLM attempt no longer pollutes the self-model with false "this idea was wrong" realizations or blocks re-proposing the same idea for a week.

### API-error outcome guard

`_is_api_error_finding()` (in `maestro/loop/task_outcome.py`) is a deterministic pre-check that fires before the criteria-based `_assess_criteria_outcome` classifier. When the task finding text starts with a known API-error prefix — specific transport-shaped prefixes (`API Error:`, `HTTPError:`, `ConnectionError:`, `TimeoutError:`) match unconditionally, while the broader `Error:` prefix only matches single-line findings below a length threshold to avoid false-positives on narrative analysis — the outcome is forced to `failed` regardless of what acceptance criteria might say. This prevents an API error from being misclassified as "success" by a criteria assessor that matches on surface-level keywords in the error text. Zero SDK cost — pure string-prefix matching.

### Scheduling

`_implement_approved_plans` selects `status in {approved, failed with failure_count < max_implementation_attempts}` and sorts approved before failed (then by ascending `failure_count`) so fresh work runs before old retries. `EvolutionEngine.implement()`'s status guard accepts both `approved` and `failed` (defence-in-depth against being invoked on a `rejected` / `implemented` / `pending_review` plan) so failed-plan retries reach the implementation path.

`EvolutionEngine.implement()` refuses outright unless the working tree is clean *and* HEAD is `main`: `assert_clean_tree_for_mutation` reads `porcelain_status()` **before** `ensure_main_branch` positions HEAD — that helper's non-main arm discards uncommitted work, so probing after it would destroy the very edit the refusal protects — and `assert_on_main_for_mutation` then asserts the branch fact positioning only attempts. Both raise `vcs.DirtyWorkingTreeError`; the tree refusal quotes a bounded excerpt of the porcelain status so the operator knows what to clear. Without the pairing, a diff left on `main` by a crashed run or an operator's in-flight edit would ride onto the freshly cut evolution branch and be folded into the plan's commit by the unconditional `stage_all` in the implementation tail. Nothing is discarded — the refusal is the fix — and an unreadable tree or branch is treated exactly like a dirty or wrong one. Because the phase refuses before cutting a branch or calling the model, nothing about the plan was tested, so `is_environment_fault` classifies the refusal with the host faults: `implement_plan` logs the tree state at ERROR and re-raises it without spending an attempt, and the plan stays `approved`.

Proposal 124 adds one pre-cap skip: a plan an `INHERITED` convergence terminal *held* (see below) carries `inherited_hold_main_sha` — the `origin/main` head the base red was measured against. `plan_holds.plan_on_inherited_hold` (`maestro/loop/plan_holds.py`; both SHAs truthy and equal against a once-per-call `rev_parse("origin/main")`, mirroring the conflict cooldown's truthiness guards, no fetch) drops such a plan from `ready` before the `max_implementations_per_iteration` cap, so a held plan never occupies a slot re-buying the same base red. The moment the base advances the SHAs differ and the plan re-admits — the base-repair task landing being the designed release.

### Retry ceiling and notifications

The retry ceiling is `[loop] max_implementation_attempts` (default 3). Telegram notifies on every failure with `attempt N/M`, and a GitHub `bug` issue is opened only on the terminal attempt (`failure_count == max_implementation_attempts`).

Before a `failed` plan is re-implemented, `implement_plan` asks the host (`EvolutionEngine.find_existing_pr` → `CodeHost.find_evolution_pr_for_branch`) whether its `maestro/evolve/<plan_id>` branch already carries an open or merged PR; if so the plan is bound to it (`implemented` + `pr_url`, leaving merged-plan bookkeeping to `check_merged_plans`) rather than re-implemented into a duplicate, and a failed lookup defers the retry without spending an attempt (#4553). Likewise, a `gh pr create` that exits non-zero after printing this repo's PR URL (a failed follow-up such as the `--reviewer` request) is treated as a created PR.

Proposal 124 inherited hold — the exception where a `stuck` terminal does *not* demote. With `[loop] gate_observation_enabled` on, `converge_to_green`'s terminal classifies a red exit via `gate_observation.attribute` and records `ConvergenceResult.attribution`. On an `INHERITED` verdict (the red is the *base*'s failure, not this diff's) `implement_plan` *holds* the plan `approved` instead of demoting: it cleans up the branch (`implement()` recreates it from the repaired base on re-admission), stamps `inherited_hold_main_sha` (the current `origin/main` head, `None` when unmeasurable — still held, still incremented) and the incremented `inherited_hold_count` via `Memory.update_plan_inherited_hold`, and fills an *empty* `next_task_directive` (first-writer-wins, under `MAX_DIRECTIVE_CHARS`) with a bounded base-repair directive naming the inherited failures — leaving `status` at `approved` and `failure_count` untouched. The hold carries its own bound: after `max_implementation_attempts - 1` holds (two, at the default) the next `INHERITED` terminal demotes as usual, its `last_failure_reason` composed by `gate_observation.render_identities` from the inherited identities rather than a truncated `raw_output` tail. Because a hold leaves `failure_count` untouched, the hold bound and the ordinary retry ceiling **stack** rather than share a budget: the budget-spent demote starts `failure_count` fresh at `1`, so a plan whose base stays red across every attempt can see up to `2 × max_implementation_attempts - 1` (five, at the default — two holds then three demote-retries) `INHERITED` terminals before the terminal GitHub `bug` issue opens. This is intended — a hold is not a failed attempt, so it costs the plan nothing against the retry ceiling. `ATTRIBUTED` and `UNATTRIBUTABLE` keep today's demote *path* (no hold), but flag-on their non-inherited `last_failure_reason` is likewise composed by `gate_observation.render_identities` from the failure identities rather than the truncated `raw_output` tail; only the flag-off `None` keeps the demote record byte-for-byte.

Transient SDK failures (`STREAM_STALL`, `RATE_LIMIT`, `CLI_CRASH`, `STALE_SESSION`) re-raise without demotion so `run_loop` retries in place. Permanent environment faults (`is_environment_fault` — an `SDKError` with exit code 2/126/127/137, or a `DirtyWorkingTreeError`) likewise propagate un-demoted, out of `_implement_approved_plans` too, so the loop crashes loudly instead of re-attempting the plan every iteration. Every other non-transient failure inside `implement_plan` has already demoted + notified by the time they re-raise; `_implement_approved_plans` catches them at the boundary and continues with the next eligible plan so one plan's logic error cannot crash the loop or strand the queue. PR-closed-without-merge stays `rejected`.

### JSONL forward-compat

Legacy plan rows without `failure_count` / `last_failure_at` / `last_failure_reason` load as `0` / `None` / `None`. The proposal-124 hold fields `inherited_hold_main_sha` / `inherited_hold_count` load as `None` / `0`, and `_parse_plan_line` coerces a float-round-tripped `inherited_hold_count` back to `int`.

## Version Archive with Metrics Snapshots

On every detected evolution-plan merge (the `check_merged_plans` phase, after the usual milestone journal entry), `agent._snapshot_version(plan_id)` appends a `VersionRecord` to `version_archive.jsonl`. Each record snapshots:

- The last N tasks' success/failure counts.
- Rolling SDK usage (cost, calls, cache-hit rate, rate-limit hits).
- Recent error count from `build_diagnostic_snapshot()`.
- The PR's merge-commit sha (best-effort via `CodeHost.get_commit_sha_of_pr()`).

Observational only — no ancestor-forking or rollback.

A fuelled `propose_plan` lists the five newest merged titles in its gap block (`GAP_CONTEXT_CAPS["version_tail"]`). The dashboard `/api/versions` endpoint exposes the tail to the Versions tab.

Tuning:
- `[loop] version_archive_enabled` — default `true`.
- `[loop] version_archive_window_iterations` — default 10.

Snapshot failures are logged and swallowed — losing a snapshot costs telemetry, not correctness.

## Post-Implementation Quality Gate + Self-Review

After `implement()`, `run_quality_gates()` runs ruff/mypy/pytest. On failure, `evolution_quality.converge_to_green` drives `auto_fix()` in a progress-gated loop: it keeps fixing while the failing set strictly shrinks (`gate_convergence.plan_next_round`) and ends `green`, or `stuck` — on a round that made no progress or on reaching the ceiling backstop `max([loop] gate_convergence_ceiling, [loop] auto_fix_max_rounds)` — 20 rounds by default. `auto_fix_max_rounds` only raises that ceiling's floor; lowering it does not cap spend. Under `[loop] gate_observation_enabled` (proposal 124) each `converge_to_green` fix round's prompt carries the enumerated per-gate failures (`gate_observation.render_failure_report`) plus the shared `evolution_quality._attribute_review` attribution verdict in place of the front-truncated `raw_output` tail, and on an `INHERITED` verdict one sentence telling the fixer the red is the base's and not this plan's to fix so the round spends itself on the diff; flag-off (or no observation) the diagnosis is byte-identical to the pre-124 tail.

Before the gate loop, `self_review()` reviews the diff. By default it runs on the implementation session, so the reviewer sees the implementer's conversation; under `[loop] self_review_own_session_enabled` (default off) each round instead opens its own `high`-effort session via `single_use_call`, carrying the plan's action-gate hooks. Proposal 110 retired its fixed round cap: it now runs a progress-gated review-fix loop mirroring `converge_to_green` — it keeps reviewing while each round commits a fix and terminates on `LGTM` (proceed) or a no-progress stall / ceiling backstop (a `False` return the caller routes to the loud fail-loud terminal). Its terminal decision is owned by `_review_terminal`, the review-loop sibling of `converge_to_green`'s `_convergence_terminal`. Under `[loop] gate_observation_enabled` (proposal 124) a no-`LGTM`, no-commit round is a stall only once the gate has been read and found red or the bounded verify-only grace (`_VERIFY_ONLY_REVIEW_ROUND_BUDGET`, one round per `self_review`) is spent: `_review_terminal` re-reads the gate on that would-otherwise-be-stuck round and, when every gate is CLEAN, buys one further review round instead of demoting the plan on the strength of an undirtied tree — an approval and the ceiling both still outrank the grace, and flag-off the loop issues no extra gate run and is byte-identical. `[loop] self_review_max_rounds` (default 2) is no longer a hard cap; it only floors the convergence ceiling (`max` with `[loop] gate_convergence_ceiling`, default 20). Diffs over 50K chars are head-and-tail truncated.

### Uncalled-symbol gate

`loop/implementation.py::_check_uncalled_symbol_gate` is the blocking gate that runs *after* self-review and `converge_to_green`, so the reviewer's and every convergence round's `auto_fix` commits have already landed, and reads the final cumulative `base_hash → HEAD` diff rather than one round's — a definition still unwired after every review and fix round is the thing it is looking for (#4312). It parses the diff for added `def`/`class` lines and resolves each symbol's call sites through one batched `git grep` fork (one `-e <name>` per symbol, rows attributed back per symbol in-process). A reference anywhere in non-test code satisfies the gate — including the symbol's own module, excluding only its own definition line — so intra-module helpers, the normal shape of a decomposed feature, pass; only a symbol whose sole appearance is its own definition is flagged. The gate is off unless `[loop] uncalled_symbol_gate_enabled`, and passes while the uncalled count stays within `[loop] uncalled_symbol_max_allowed`.

It shares its logic with `evolution_quality._find_uncalled_symbols` by hand rather than a lift: both copies use module-level diff regexes and differ only in that `_find_uncalled_symbols` reads `engine._config` while the gate takes an injected `config`, so the two are kept in sync deliberately until a shared extraction lands. Carrying no gate observation, its block is an observation-less terminal, and `attempt_disposition.classify_attempt` necessarily returns `ABANDON` — the demote is reached only in that arm.

### Acceptance-criteria count bound

`EvolutionPlan.acceptance_criteria` holds up to 10 binding, testable invariants (the `propose_plan` schema asks for at least 1 via `minItems`, but no write door enforces that floor), extracted by `propose_plan()` before implementation and injected into both `self_review` and the PR body; `validate_success_criteria` rejects vacuous ones. The 10-item cap has a single enforcement owner, `types.py::validate_acceptance_criteria_count`, called at both persistence write doors (`save_evolution_plan`, `refine_plan`) and at the sole prompt renderer (`format_acceptance_criteria_block`) — the renderer is the choke that keeps an over-cap list out of context. The per-item length cap, `ACCEPTANCE_CRITERIA_ITEM_MAX_CHARS`, also lives in `maestro/types.py`: the creation paths truncate to it and `refine_plan` (plus the curator pre-check) rejects an over-cap criterion.

The read door is deliberately asymmetric: it loads a legacy over-cap row *intact* under one WARNING (deduped per `plan_id`) rather than truncating a contract a human already reviewed. `implement_plan` gates on the same bound before any SDK call and disposes such a plan `obsolete`, so the renderer's refusal can never escape as a loop crash. `auto_fix` stays rationale-blind throughout.

### Gap issues and the fuel owner (proposal 155)

Self-initiated evolution spends only on closing a *gap*: something Maestro's own health or capability is blocked on. Each gap is a GitHub issue carrying one of two labels (`gap:maestro`, `gap:capability`), and `maestro/evolution_fuel.py` is its one owner — the `gap_issue_owner` structural guard fails any other module under `maestro/` that spells a `gap:*` label or the `gap_opens` ledger (only `gap_store.py`'s table declaration is allowlisted).

- **Owner ids.** `parse_owner_id` full-matches a closed grammar (`maestro:gate`, `maestro:source_budget:<path.py>`, `maestro:toolchain:<need>`, `capability:(act_kind|completion_check):<name>`). `GAP_PREFIXES` maps each prefix to one label and the openers admitted for it. A title is `<owner_id> — <fixed summary>`, so no free text reaches a title and `owner_id_of_title` reads the key back.
- **One opener door.** `open_gap_issue` refuses an invalid owner id, an opener not admitted for the prefix, an empty or over-long `decision_ref`, tainted evidence passed unfenced, and evidence longer than `MAX_EVIDENCE_CHARS` — all before any host call. It considers only issues it opened itself (a `gap_opens` row for the owner id); a door issue whose gap label or door-shaped title was edited away is refused `gap-tampered`; an operator's standing hand close is `operator-abandoned`, and an unreadable closure is `closure-unknown` (fails closed). Otherwise it reuses an open door issue, reopens the newest closed one, or creates one. Each open or reopen writes one `gap_opens` row in `gaps.db` (`gap_store.build_gap_store`).
- **Trust.** A task session can label an issue as the bot, so a label proves nothing. `classify_gap_trust` returns `operator` when a login in `[evolution_fuel] operator_github_logins` applied the label, `rederived` when an open `gap_opens` row matches the owner id, issue number and an admitted opener with no standing operator hand close, and `unverified` otherwise. `admit_gap_issues` keeps the trusted issues oldest first and records one `gap-unverified` event per issue number.
- **Own login at startup.** `_build_agent` refuses (SystemExit) an `operator_github_logins` list naming the loop's own login. The `create_issue` in-process tool refuses any `gap:*` label, and the `close_issue` tool refuses a gap issue.
- **Self-health detectors.** `MaestroAgent.evolve` runs `loop/self_health.py::run_evolve_prestep` first, with no gate subprocess or SDK call. *Red main:* `observe_red_main` keeps the first-red clock in the `red_main_watch` row in `gaps.db`; `detect_red_main` opens `maestro:gate` once the same checks have stayed red for `[evolution_fuel] red_main_grace_hours`, and closes it only on a green read while no live plan is on an inherited hold. *Inherited hold:* `record_inherited_hold` opens or reuses the same `maestro:gate` issue (skipped while `[loop] evolve_every` is `0`). *Source budget:* `detect_source_budget` keeps at most one `maestro:source_budget:<path>` issue open, for the worst over-budget file.

## Health-Summary Noteworthy Gate

`maestro/stats.py` provides task-outcome-level health signals (`summarize_iteration_health`, `is_health_noteworthy`) that complement the log-level operational signals in `maestro/diagnostics.py`.

Wired into `contemplate()`: after the diagnostic snapshot is built and `get_recent_tasks(20)` is fetched, `is_health_noteworthy()` is evaluated. When it triggers (success rate <70% with ≥3 tasks, failure streak ≥3, error count ≥5, or cost spiking), `summarize_iteration_health()` is appended as a `## Health Summary` section. When not noteworthy, it is omitted entirely — no noise in normal operation.

Both functions are pure (no I/O) and the injection is wrapped in a try/except so a stats failure cannot block contemplation. When the diagnostic snapshot itself fails, health summary is also skipped (snapshot is `None`).

## No-op Task Rate Measurement

`classify_noop_task()` and `measure_noop_rate()` (in `maestro/audit_checks.py`) provide a dict-level no-op classifier and aggregation function for measuring the fraction of successful tasks that confirmed existing state without producing meaningful changes. The classifier performs case-insensitive substring matching of `result_summary` against seven patterns: `no remediation`, `already passing`, `already resolved`, `no-op`, `no code changes`, `confirmed existing state`, `already green`.

`measure_noop_rate()` filters to `outcome in ("success", "completed")`, classifies each task, and returns `{total_success, noop_count, noop_rate, by_source: {<source>: {total, noop, rate}}}` where `source` is derived from the task's `source` field (defaulting to `"queue"` when absent). The `measure-noops` CLI subcommand (`maestro measure-noops [--last N]`) reads `task_history.jsonl` and prints the formatted report.

### Experiment: no-op rate hypothesis

**Hypothesis:** At least 40% of successful tasks are no-ops.

**Procedure:** Ran `measure_noop_rate()` against the full `data/task_history.jsonl` (316 records, 257 successes) on 2026-05-26.

**Result:** 3.5% no-op rate (9/257). By source: `external` 5.5% (3/55), `self_directed` 3.0% (6/202). The dominant matched pattern was `no-op` (8 of 9 hits); all 9 were branch maintenance/rebase tasks. Cross-validation with the legacy `is_no_op_task()` classifier (different pattern vocabulary) also yielded 9 detections with only 2 overlapping; the union rate was 6.2% (16/257).

**Verdict:** Falsified — the observed rate is an order of magnitude below the 40% threshold. No-ops are a minor phenomenon confined to branch maintenance, not a systemic pattern.

This classifier complements the existing `is_no_op_task()` / `compute_no_op_rate()` pair (used by `health_check.summarize_health`) which uses a different pattern vocabulary (`_NO_OP_MARKERS`). The two classifiers are complementary, not redundant.

## Dream Phase

Every `dream_every` iterations, `_phase_dream` runs two zero-SDK passes: the phase-cost report refresh (`phase_cost_report.refresh_phase_cost_report`, best-effort) and the archive below. The phase makes no SDK call, so it is neither in `_BUDGET_GATED_PHASES` nor in the `external_delivery` focus profile's suppressed set; it stays in `DEDUPED_CADENCE_PHASES`, so a frozen throttled iteration runs the passes once, and it is skipped under `--smoke`. See [loop-lifecycle.md](loop-lifecycle.md) for phase ordering.

The revenue-charter retirement deleted the priced dream digest — `maestro/dreaming.py`, the `dream` / `dream_validate` callers (kept in `cost_tracking.RETIRED_CALLERS` so historical cost rows still roll up to "Dreaming"), the `read_dream_digest` tool, the `[loop]` digest knobs (`dream_journal_max`, `dream_task_max`, `dream_identity_max`, `dream_max_retries`, `dream_validation_enabled`, `dream_digest_enabled` — `dream_every` stays as the zero-SDK passes' cadence) and the SQLite dream-history ledger. An existing `dream_history.jsonl` (and a `state.db` `dream_history` table) stays on disk, operator-managed; nothing reads it. Legacy journal rows typed `dream` read as `reflection`, and rows tagged `triggered_by="dreaming"` load as operational events.

The dream cycle also runs `Memory.archive(threshold_days, retry_budget=...)` (gated by `[loop] archive_threshold_days`, default `0` = disabled). It splits the long-lived append-only JSONL state into hot + cold siblings so the hot files stay bounded: `task_history.jsonl`, `evolution_plans.jsonl`, and — because both are written on essentially every SDK call and otherwise grow without bound — the telemetry sidecars `cost_samples.jsonl` (one row per SDK call, the default `JsonlCostSampleStore`) and `usage.jsonl` (one `IterationUsage` row per iteration). Rows older than the threshold move to a `<file>.archive.jsonl` cold sibling; a row whose timestamp is missing or unparseable stays hot (`_record_timestamp` reads `timestamp`, `created_at`, then `started_at` — the key `usage.jsonl` rows carry). The threshold must exceed the longest hot-read window over `cost_samples.jsonl`, and the widest such reader is the dashboard, not a loop-internal one: `/api/cost-rates` / `/api/budget` (`dashboard/routes.py`) read `agent.cost_samples` with `window_hours` accepted up to 168h (7 days), wider than the loop-internal burn-rate `_iter_samples_in_window` (`budget_rate_window_hours`, default 1h) and count-bounded phase-report `_tail_cost_samples`. So the dashboard alone sets a floor of **> 7 days** for that file (the dashboard cap, raised further if `budget_rate_window_hours` is set above it); a day-scale `archive_threshold_days <= 7` sheds in-window rows to cold and the dashboard's up-to-7-day budget / cost-rate view silently under-reports spend. Plan rotation is status-scoped, not age-only: an aged `evolution_plans.jsonl` row rotates only when its status is in `ARCHIVABLE_PLAN_STATUSES` (`merged`, `rejected`, `obsolete`); a `failed` row rotates only once its `failure_count` has spent the `retry_budget` the dream phase passes (`max_implementation_attempts`); a `rejected` row rotates only once `rejection_learned` is set, so `_process_rejected_plans` still sees it; a `rejected`/`obsolete` row whose plan id is in the `open_pr_plan_ids` the dream phase derives from `_open_owned_pr_states` stays hot so Tend keeps servicing its PR (a failed listing passes `None`, holding every such row that carries a `pr_url`); a `task_history.jsonl` row cited as `source_task_id` by a plan that stays hot is held too, so `implement` still resolves its base branch; and a slice of a proposal outside `FINISHED_PROPOSAL_STATUSES` stays hot at any age. An aged `pending_review` plan is therefore already held hot by status, and `plan_review_expiry_days` — the horizon the expiry sweep scans for aged `pending_review` plans — stays in the validation floor as a second, independent guard. `Config` rejects at validation time any enabled threshold not strictly above the widest of the three windows (with the shipped defaults a 21-day floor, so 22 days is the smallest valid threshold). No reader ever reads the `.archive.jsonl` sibling — cold storage is operator-managed. The same holds for `cost_samples.cold.leak.jsonl`, where `ensure_schema`'s one-shot `move_leak_cost_samples` moves the pre-fence test-leak rows `cost_tracking.LEAK_FENCE` matches. The operator-facing `usage.jsonl` CLI readers are outside that constraint and cold-tolerant by design: the window-less `cost_for_task` (`maestro cost-per-task`) and the operator-chosen `cost-report --days N` / `burn-baseline --since`/`--compare` windows can span wider than the threshold, so a task or date already shed to cold reads as absent (`cost-per-task` prints "No usage data") — the accepted trade-off of opting archival in. `journal.jsonl` is deliberately excluded: the subjective record (journal-over-logs) is cold-archive-only-if-ever, never pruned. The SQLite `CostSampleBackend` is a separate never-pruned table, out of scope for the JSONL-sibling rotation.
